Orientation

What this course is

A frontend system-design expert can take an underspecified product prompt and, in under an hour, produce a defendable client architecture — including what they will not build.

Frontend system design is product ownership on the client

Backend system design asks: how do we store, replicate, and serve data at scale. Frontend system design asks: how do humans use a surface that is slow, hostile, and interruptible — a browser tab, a network that lies, a DOM that is expensive, and a team that will ship plugins into your page.

The unit of design is not “a React app.” It is a critical path: the first useful pixel, the first interaction that must feel instant, and the failure the user will actually see. If you cannot name those three, you are decorating a box diagram.

What you own in 45–60 minutes:

  • Users and jobs. Who, on which device, doing what how often.
  • The surface. Routes, chrome, overlays, empty and error states.
  • The contract. APIs, cache keys, events, authz. Not Kubernetes.
  • The runtime budget. JS kb, DOM nodes, long tasks, LCP element, INP on the money click.
  • Degrade paths. Poll if WS dies. Read-only if save conflicts. Hide the plugin if it throws.
Senior tell. You name two options you rejected and why. “We’ll use GraphQL + Redis + Kafka” with no client architecture is a fail at this level.
Interviewer prompt → users + job + device → critical path (first paint, first interaction, first failure) → rendering + shell + routes → state map (URL / server cache / local / ephemeral) → API + cache + races → perf + a11y + security + observe → trade-offs + what you would measure next week

Related files on this hub: Phase 2 (React runtime, folders, Profiler). Phase 3 (distributed systems — use it when the prompt becomes “fan-out notifications to 10M devices,” not when the prompt is “design the bell icon”).

What you will not do in a frontend interview

Do not start with a region × AZ × Kafka picture. If they wanted that, they said “design the notification platform.” If they said “design the notification inbox,” they want unread badges, pagination, mark-read, deep links, a11y live regions, and what happens when the socket drops.

Do not invent a company. Do not claim you shipped a specific Atlassian feature unless it is on your resume. Use “Jira-like” and “Confluence-like” as shape, and label practice questions as practice.

  • Skip inventing 12 microservices. One BFF + existing APIs is a valid senior start.
  • Skip picking Redux vs Zustand in minute two. Place the state first.
  • Skip “we’ll virtualize everything.” Virtualize the list you measured as large.
  • Skip CRDT unless they insist on multi-caret editing. Say the honest alternative (lock, version, last-write + diff).

How to run the hour

Interview framework

This is the spine of every case and every mock. If you freeze, return to the next unused step.

The 16-step loop you speak out loud

Memorize this until it is boring. In a 45-minute loop: steps 1–5 in ~8 minutes, 6–12 in ~25, 13–16 in ~10, leave 2 minutes for their follow-up. In 30 minutes, collapse 7–8 into the architecture box and still do 13–16. Interviewers hire the person who reaches failure and a11y, not the person who names 14 libraries.

Opening script (practice, not a canned bio). “I’ll confirm users and the money path, write NFRs, assume scale numbers you can correct, then design the client: shell, data, and the interaction that must stay fast. I’ll call out what I would not build in v1.”

Clarifying questions that change the design

Ask questions whose answers fork the architecture. “What’s the company’s QPS?” rarely forks a board UI. These do:

  • Is the first visit SEO-critical, or is this behind login?
  • Do we need character-level multiplayer editing, or is last-write + versions enough?
  • Are third-party apps in-process JS or sandboxed iframes?
  • Mobile: same app or a reduced surface?
  • How many entities are on screen in the p95 case? (Not “how many users exist.”)
  • Must unread badges be <1s fresh, or is 30s polling acceptable?
  • Offline: drafts only, or full mutation queue?

If they say “you decide,” pick the stricter interesting constraint and say so. Example: “I’ll assume logged-in, 400 visible cards, polling is OK, plugins are iframes, no CRDT.” Write it. They will correct you if they care.

Requirements and scale

Write NFRs that change code. Invent client-scale numbers. Invite correction.

Frontend NFRs are user-visible budgets

Backend NFRs are often latency, throughput, durability. Frontend NFRs are those plus main-thread time, memory per tab, and human time.

Scale that matters. “10M MAU” does not tell you whether to virtualize. “p95 board has 8k issues in filter and 400 DOM cards” does.

Capacity estimation for a client

Do the napkin math they expect, but on the client:

  • DOM. 400 cards × 30 nodes ≈ 12k nodes — usually fine. 8k cards × 30 nodes ≈ 240k nodes — virtualize or you will jank.
  • JSON. 10k issues × 2KB = 20MB parse. Don’t fetch the universe. Fields on the card vs fields on the overlay.
  • JS. 200KB gz main is a different product than 2MB gz. Editor and admin must not ride with the board.
  • Connections. One WS per tab × 10 tabs × 50k users is a backend problem — mention it, then return to the inbox UI.
  • Collaborators. 50 presence dots is a list. 500 caret streams on one document is a different product.

Hydration, mismatch, and when CSR is the adult answer

Hydration attaches listeners and resumes React (or similar) on server HTML. It fails when server HTML ≠ first client render: Date.now(), window, random IDs, locale that differs, a flag that flips after paint.

  • Use useId for label/input pairing across server and client.
  • Boot critical flags with the HTML, not a later /flags that rewrites chrome (CLS).
  • If the page is a tool behind login and the bundle is already large, CSR + HTTP cache + a skeleton can beat a fake-SSR story.

// Bad: server HTML says "Good morning", client hydrates "Good evening"
function Greeting() {
  const hour = new Date().getHours(); // mismatch risk
  return <p>{hour < 12 ? "Good morning" : "Good evening"}</p>;
}
// Better: render a stable shell, set the greeting after mount, or pass hour from the server.

Navigation

Routing and splitting

Shell stays small. Features load when the user is going there. The URL is shareable state.

App shell, routes, and what must not be in main.js

The shell is chrome that is always there: product switcher, nav, search trigger, help, user menu. It should be small, cached, and boring. Features are routes (and sometimes overlays).

shell (chrome, auth boot, flags) /home /board/:id ← virtualized list /issue/:id ← overlay or route, lazy /search /admin/* ← never in the board bundle /edit/:pageId ← editor chunk, not on read

Split at route first. Split at component when a route still contains an editor, a map, or a charting kit. Prefetch on hover/intent for the next likely route. Do not prefetch the admin graph from the board.

Waterfalls: shell waits on user, user waits on flags, flags wait on layout, layout waits on 12 widgets. Collapse with a BFF “bootstrap” or parallelize what is independent. Name this in the interview — it is how TTI dies.

const Board = lazy(() => import("./board/BoardPage"));
const Editor = lazy(() => import("./editor/EditorPage"));
// Prefetch editor only when the user clicks Edit, not on every page view.

The URL is a public API

If two people can share it, it belongs in the URL: board id, JQL, selected issue, tab, modal that is a real place, locale if it is not in the user profile. If it is a drag ghost or a caret, it does not.

Deep links are a requirement, not a nice-to-have. Back button is a requirement. Restore scroll on back is a requirement on feeds. Design the router before the store.

A Redux store that is the only place the selected issue lives is how you break share and back. Put ?selected=ISSUE-18 in the URL and treat the store as a cache of server data.

Placement

State architecture

“We use Redux” is not a design. The map of URL / cache / local / ephemeral is.

Four buckets, not one store

Every piece of state goes in exactly one bucket. If you cannot place it, you do not understand the product yet.

Ownership and writes

One writer per fact. The board snapshot is not allowed to invent a new description for an issue the overlay also edits. The overlay mutation updates the issue key; the board card reads the same key (or a projected field). Duplicated copies are how cards lie after save.

Optimistic UI: apply locally, send mutation, rollback on error, reconcile on 409. Never optimistic-delete a permission you have not confirmed if the cost of being wrong is high (payments, admin).

Server state

Data and caching

Keys, invalidation, abort, batching, and honest optimism. This is most of a senior FE design.

Cache keys, invalidation, and races

A cache key is the identity of a server fact. If two screens need the same issue, they share ["issue", id]. If the board needs a slimmer projection, either store the projection under a different key and update both on mutation, or store the issue once and select fields.

  • staleTime (client): how long you trust the memory cache before refetch.
  • Cache-Control / ETag (HTTP): how the browser/CDN trust the bytes.
  • They are not the same. You can have a warm React Query cache and still hit the network if you set staleTime to 0.
TypeScript
const keys = {
  board: (boardId: string, jql: string) => ["board", boardId, jql] as const,
  issue: (id: string) => ["issue", id] as const,
  comments: (id: string) => ["issue", id, "comments"] as const,
};
// After PATCH issue: invalidate issue(id) and any board that might show it.
// After rapid JQL: abort the previous fetch; ignore responses with old generation.

Races: the user types JQL faster than the network. Solutions that work: abort, generation counter, or “only apply if this is still the requested key.” Solutions that do not: hope.

type → debounce 150–300ms → gen++ → fetch(gen) response → if gen !== current: drop mutation → optimistic patch → PATCH → 200: keep / 4xx: rollback / 409: refetch

BFF, REST, GraphQL, batching

The client should not take 80 round trips to open a dashboard. A BFF (or a batch endpoint) exists when aggregation is cheaper on a server that already has cookies and service identity.

StyleStrengthFailure mode
REST resourcesClear cache keys, HTTP cachingOverfetch; chatty lists
GraphQLShape per screenUnbounded queries; cache is harder; still need keys
BFF view modelOne payload for a screenA new BFF per whim; versioning
Batch GETWidgets / cards by idNeed an id list first

Errors as data: a widget failure must not 500 the page. Per-section error boundaries and { error, data } in the BFF beat a single throw.

Pagination. Offset is simple and breaks when the list mutates. Cursor is the default for feeds. Virtualized boards often use “window + load more per column,” not infinite offset of 10k.

Optimistic updates without lying

Good optimistic: drag a card to a new column, PATCH, on failure snap back and toast. Bad optimistic: mark an invoice paid before the server agrees.

Every mutation you retry needs an idempotency key (clientMutationId). Double-click and flaky 200s are normal. The server must treat the same id as the same write.

async function moveIssue(issueId: string, to: ColumnId, clientMutationId: string) {

  try {

  } catch {

Freshness

Realtime

Choose a freshness SLA. Keep a REST source of truth. Degrade in public.

Poll, SSE, WebSocket, push — pick the freshness

Realtime is a freshness SLA, not a technology preference.

Presence vs document. Heartbeats must not setState on the issue body. Colocate presence. Throttle. A caret is ephemeral; a comment is not.

Degrade is the design

Write the sentence: “If the socket dies, the bell still opens, we poll every 30s, and we show ‘Live updates paused.’” That sentence is more senior than a box labeled Kafka.

Backpressure: if presence arrives at 20Hz, you sample to 1–2Hz for React. The canvas layer (if any) can take higher frequency in a ref.

Budgets

Performance architecture

Name the LCP element and the money interaction. Then pick virtualize / split / worker.

Vitals are architecture, not a Lighthouse trophy

The critical rendering path is still: bytes → parse HTML → CSSOM → render tree → layout → paint → composite. Your JS can steal the main thread at any point after it downloads.

VitalTypical FE causeTypical fix
LCPLate hero image, blocked HTML, huge JS before contentPriority image, SSR/edge HTML, less main JS
INPHandler does too much, huge rerender, layout thrashColocate, transition list, virtualize, yield, worker
CLSLate banner, no image size, webfont swapReserve space, boot flags early, font-display strategy

Virtualize when the p95 list is large and you measured it. Virtualization costs: scroll jump, measure, a11y (you must still provide a keyboard model and not lie about the document length). Paginate when the user thinks in pages. Window when they think in a board.

INP click → event delay (main thread busy) → processing (your handler + React render) → present delay (paint) Fix the longest of the three. Profiler + Performance panel. Not guess + memo.

Budgets, long tasks, and workers

A budget is a CI number: JS kb for the board route, LCP on a lab profile, INP on a RUM slice. Without it the bundle only grows.

Long tasks (>50ms) are how INP dies. Break work: idle callbacks, scheduling, workers for hash/encode/parse of large files. Do not setState every byte of an upload; rAF-throttle progress.

memo / useCallback are last. First: less work, smaller trees, smaller props, no fat context, virtualize the giant list. Phase 2 on this hub drills the React details — here you decide where the work is allowed to live.

Resilience

Offline and sync

Decide what works offline. Persist it. Conflict in the open.

Drafts, queues, and not lying

Offline is a product: which mutations are allowed with no network? Almost always drafts (comments, doc body). Rarely “move 400 issues and reconcile later” unless you have a real sync engine.

  • Persist drafts in IndexedDB, not only memory.
  • Queue mutations with idempotency keys. Show “waiting to send.”
  • On conflict: show both, or last-write with a toast and a link to history — do not silently clobber.
  • Service workers: cache the shell and immutable assets. Do not cache personalized HTML as if it were public.
online → optimistic + confirm offline → IDB draft / queue + banner reconnect → flush queue in order → 409 → conflict UI two tabs → BroadcastChannel or lock so you do not double-send

Multi-team UI

Design systems

Tokens, tight APIs, a11y in the kit, versioning. Not a folder of pretty buttons.

A design system is an API with versioning

Tokens (color, space, type, elevation) are the contract. Components compose tokens. Features must not invent hex. Theming is token swaps, not if (dark) in 400 files.

Component APIs: variants and slots beat 40 boolean props. Accessibility lives in the kit (focus rings, dialog, combobox) so product teams do not reimplement APG badly.

Contribution: RFC + visual review + a11y review + versioning. Breaking a Button padding is a semver event. A junk drawer of “just this once” variants is how the system dies.

Atlassian Design System (atlassian.design) is a public example of tokens and components — use it as taste, not as a script of interview answers.

Trust boundary

Auth and permissions

Pretty 403s. Ugly if you trust the client.

The client never grants power

The browser shows buttons. The server decides. A hidden “Delete project” is UX, not security. Design both: hide what you know is forbidden, still handle 403 as a first-class state.

Defense

Security architecture

Encode, sanitize, CSP, sandbox. Unprompted in every design.

XSS is the frontend security interview

React encodes text children. You still lose if you: dangerouslySetInnerHTML, markdown→HTML without a sanitizer, CSS url(), javascript: hrefs, open redirects, or plugin HTML.

  • Encode by default (text).
  • Sanitize if you must store HTML (allowlist).
  • CSP as depth (script-src, no unsafe-inline if you can, frame-ancestors).
  • Sandbox iframes for third-party apps (capability tokens, not the user’s session cookie if you can avoid it).

CSRF: cookie-authenticated mutations need a token, custom header, or SameSite strategy you can explain. CORS is not CSRF protection. Clickjacking: frame-ancestors.

TypeScript
// Never: title as HTML because a PM wanted bold
<h1>{issue.title}</h1>
// If you render stored markup:
<div dangerouslySetInnerHTML={{ __html: sanitize(storedHtml) }} />
Supply chain: lockfiles, least privilege in CI, don’t execute arbitrary package postinstall in prod builds. Mention it once; don’t spend the hour there unless they ask.

Operable

Accessibility as architecture

Name the pattern. Own focus. Don’t leave drag as the only move.

Accessibility is a keyboard and semantics design

POUR: perceivable, operable, understandable, robust. In a design interview you specify:

  • Semantic HTML first. ARIA when you invent a widget (combobox, grid, tabs).
  • Focus: trap in modal, restore on close, skip link, don’t steal on every rerender.
  • Keyboard model for the money path (board move, mention list, command palette).
  • Live regions: polite for “issue moved,” assertive only for errors that block.
  • Don’t use color alone for status. Don’t rely on drag without a keyboard alternative.

Use the WAI-ARIA APG patterns by name: combobox for typeahead, dialog for modal, grid or a well-explained list for boards. “I’ll add aria-label later” is how seniors fail.

Micro-frontends

Default to packages. Iframe untrusted apps. Federation is a last resort you can defend.

Micro-frontends are a people-scale tool

A modular monolith (packages, import rules, CI ownership) is the default. Runtime MFEs exist when independent deploy is worth the tax: duplicate React, CSS fights, shared nothing, performance.

Heavy I/O

Media, upload, search

Workers for CPU. Cursors for feeds. Combobox for typeahead.

Upload, images, and not freezing the tab

Multi-GB upload: chunk, resume, worker for hash, progress via rAF, don’t put the file in Redux. Direct-to-storage with a signed URL is normal; the browser must not stream 2GB through your Node BFF unless you have a reason.

Images: width/height or aspect-ratio (CLS), srcset, priority on LCP image only, lazy the rest. Don’t decode 40 hero-sized images offscreen.

async function hashInWorker(file: File): Promise<string> {
  const worker = new Worker(new URL("./hash.worker.ts", import.meta.url));
  return new Promise((resolve, reject) => {
    worker.onmessage = (e) => resolve(e.data.hash);
    worker.onerror = reject;
    worker.postMessage(file);
  });
}

News feed / social home

Practice case (45–60 min). Not a claimed official company question. Draw first, then read.

Users and job. Logged-in user catching up on a personalized stream on phone and desktop.

Functional. Infinite home feed, like/comment, composer, stories/rail optional in v2, deep link to a post.

Non-functional. LCP on first post media; INP on like and scroll; CLS from images; not SEO for the home stream.

Client-scale guesses (say them). p95: 20 posts in first paint, 2k in session, 1.5MB images if you are careless, 3 tabs.

Rendering. CSR after login. Public permalink pages can be SSR. Home is not SSG.

Architecture. Shell + FeedRoute. Virtualized list. PostCard cheap. Media lazy except first one or two. Composer lazy. Comments as overlay route.

State map. URL: / and /p/:id. Server cache: feed page cursors, post, like-state. Local: composer draft. Ephemeral: like burst animation.

API / events. GET /feed?cursor; POST /posts/:id/like (idempotent); GET /posts/:id. Optional WS for new-post badge only.

Cache and races. Key ['feed', cursor]. Don’t refetch the whole home on one like — patch the post key. Abort if they jump to a hashtag feed.

Performance. Virtualize; priority on LCP image; srcset; don’t hydrate a video player for every row.

Failures and degrade. Empty, muted, error per card. If like fails, revert. If feed 500, retry + cached last page.

Security. Encode captions. Authz on every post. No token in image URLs that leak private media.

Accessibility. List + article semantics; keyboard like; don’t trap scroll; alt on images.

Observe. LCP first media, INP like, feed error rate, time-to-first-byte of /feed.

Trade-offs (name what you rejected). Rejected: fetching 2k posts; WS for every like; SSR of the personalized home.

How you talk it. Start with first paint of post 1, then cursor + virtualize, then like as optimistic patch. Don’t draw Kafka.

Short answer. A short-lived, scoped credential for one slot, not the user’s full session cookie.

            Glossary

            App shell

            Always-on chrome. Must stay small.

            BFF

            Backend-for-frontend: a view-model or batch layer for one client.

            Bootstrap payload

            First response with user + critical flags to kill waterfalls.

            Cache key

            Identity of a server fact in the client cache.

            Capability token

            Short-lived scoped credential for a plugin slot.

            CLS

            Cumulative Layout Shift — visual jump.

            Combobox

            APG pattern for typeahead / command palette.

            Critical path

            First paint, first money interaction, first failure.

            CRDT / OT

            True multiplayer sync. Rarely a 45-minute implementation.

            CSR

            Client-side render. Honest for logged-in tools.

            Cursor pagination

            Stable paging for mutating lists and feeds.

            Degrade

            The job still completes when the fancy channel dies.

            Ephemeral state

            Drag, caret, hover — usually refs, not document store.

            Generation token

            Monotonic id so stale responses are dropped.

            Hydration

            Attaching client runtime to server HTML.

            Idempotency key

            clientMutationId so retries do not double-apply.

            If-Match

            Optimistic concurrency via version.

            INP

            Interaction to Next Paint — lag.

            Island

            Small interactive widget on mostly static HTML.

            ISR

            Incremental static regeneration — public pages at the edge.

            LCP

            Largest Contentful Paint — main content appeared.

            Modular monolith

            Packages and import rules without runtime MFEs.

            N+1 (client)

            One request per row/widget instead of a batch.

            SWR

            Show stale, revalidate in background — also a library name.

            SSR

            HTML for this request. Watch hydration cost.

            SSG

            Prebuilt HTML. CDN-friendly.

            staleTime

            How long a client cache is trusted before refetch. Not HTTP cache.

            Virtualize

            Render only visible rows. Costs measure + a11y work.
