Why this file exists

The job

You are the UI catalyst, not a dashboard contractor

The job is to shape how people experience observability across OpenShift and multi-cluster management — not to paint charts in isolation.

Backend teams own Prometheus, Loki, Tempo, Alertmanager. You own the single pane: time range, empty states, RBAC-aware lists, and jumps between signals. Product and UX sit in the same design conversation.

PM / UX ──► you (plugin + PF + a11y) metrics team logging team tracing team └── UIPlugin / ConsolePlugin ──► Observe menu

Lead means you propose a plugin boundary, a proxy, a feature flag, and a PatternFly pattern — not a new SPA. Upstream means the feature lands on GitHub first, then in the operator that installs it on a cluster.

React fluency is assumed. The people who move fastest can explain ConsolePlugin, UIPlugin, and why a PromQL range query, a Loki stream, and a Tempo trace share one troubleshooting journey.

Product map · tutorial

Observe surfaces

Learn the menu, the two operators, and which surface is the right first click. Repos come after you can teach this without notes.

Where users actually live: the Observe menu

OpenShift’s admin console is a left-nav of cluster tasks. Observe is the observability product inside that console. Your work is not a separate URL. It is pages, tabs, and panels under Observe (and sometimes a drawer on a workload page). If it does not show up there, it does not exist for most users.

Those pages are almost never compiled into the console binary. They are dynamic plugins enabled on the cluster. Some come with in-cluster monitoring by default. Others appear when the Cluster Observability Operator (COO) installs them from a UIPlugin.

Console (shell: nav, chrome, PF styles, auth) └── Observe ├── Metrics / alerting / targets (Prometheus, Alertmanager, Thanos) ├── Dashboards (Perses) (dashboard + datasource CRs) ├── Logs (LokiStack) ├── Traces (Tempo + OTel collector) ├── Troubleshooting panel (Korrel8r graph) └── Incidents (grouped alert timeline)

Each row is a different backend and often a different GitHub repo. Your job is one journey across them: same time range, same namespace, a jump that does not dump the user’s brain.

CMO vs COO — two operators, one menu

Two names will show up in every architecture discussion. They are easy to mash together and wrong to mash together.

Cluster Monitoring Operator (CMO)Cluster Observability Operator (COO)
JobDefault in-cluster Prometheus, Alertmanager, kube-state-metrics, node exporters — “is the cluster healthy?”Optional Observe extras: extra UI plugins, Perses, incidents, ACM wiring, logging/tracing UI install paths
Always there?On typical OpenShift, yes (unless someone turned monitoring off)No. Installed when the cluster wants the extra product
How UI appearsMonitoring plugin features that talk to the in-cluster Prometheus stackUIPlugin CR: COO deploys plugin + companions (e.g. Korrel8r, Perses)
Say this out loud. CMO answers ‘is cluster monitoring running?’ COO answers ‘which Observe UIs did we opt into?’ Users still only see the Observe menu.

If Perses is missing, you talk to COO / UIPlugin, not to Prometheus. If in-cluster metrics are missing, you talk to CMO. If the plugin name is missing from Console spec.plugins, you talk to GitOps / the console Operator — not Webpack.

What each surface is for (so you pick the right first click)

Metrics / graph. Aggregates over time: CPU, request rate, error ratio, p99. First click when the question is “how much / how often / is it getting worse?” Backing store: Prometheus (single cluster) or Thanos (long-term / many clusters).

Alerting / targets. Alertmanager silences, firing alerts, scrape targets that are down. First click when something is already paging. Incidents (below) sit above a flood of raw alerts.

Dashboards (Perses). Saved boards as Kubernetes objects. First click when the team already agreed “this is our SLO board,” not when you are still exploring a crash.

Logs. A specific event: stack trace, CrashLoop last lines, an auth denial. First click when you need the payload, not the average.

Traces. One request across services. First click when you know (or can search) a slow or failed call. Waterfall, not a chart of averages.

Troubleshooting panel. “This alert exists — what else is related?” Korrel8r graph. First click when the user is lost between signals.

Incidents. Group alert bursts into a timeline so a human is not staring at 4,000 firing rows. First click when “everything is on fire.”

CrashLoop → Logs (previous container), then restart metrics High p99 → Metrics, then trace (exemplar or TraceQL) Auth 401s → Logs + trace attributes (user, route) ‘Cluster is down’ → Incidents / Alertmanager, not a custom Grafana

Public code to skim later: openshift/monitoring-plugin, logging-view-plugin, distributed-tracing-console-plugin, troubleshooting-panel-console-plugin, rhobs/observability-operator. The tutorials on this page are enough to read those READMEs without drowning.

Cluster literacy

Kubernetes enough

This is not a Kubernetes course. It is the slice you need so plugin YAML, empty states, and “the UI disappeared” are not mysteries. Mark complete when you can read a ConsolePlugin and a RoleBinding without a cheatsheet.

The objects you will actually touch

You do not need to pass a CKA. You need to read a cluster the way a plugin author debugs: “is my UI even installed, and can this user reach Loki?”

A cluster is the whole computer. A namespace is a named folder inside it (shop, openshift-monitoring, your plugin’s namespace). Most Observe objects you care about are namespaced. Cluster-scoped things (Console, some operators) are global.

RBAC is why the same query is empty for one user

Kubernetes authorization is not “hide the button.” The API returns 403. Observe UIs that call Loki, Prometheus, or Tempo as the logged-in user (UserToken on the proxy) will show empty or error depending on that user’s RoleBindings.

  • A Subject is a user, group, or ServiceAccount.
  • A Role (namespace) or ClusterRole (cluster) lists verbs + resources (get/list/watch on pods, or a custom resource).
  • A RoleBinding attaches the Role to the Subject in one namespace.
YAML
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-pods
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: devs-read-pods
  namespace: shop
subjects:
  - kind: Group
    name: shop-devs
roleRef:
  kind: Role
  name: read-pods
  apiGroup: rbac.authorization.k8s.io

UI implication. Empty logs can mean “no lines” or “this user cannot list that namespace.” Those are different empty states. Copy must not say “no errors found” when the API said 403.

Loki often has a tenant (OrgID) as well as Kubernetes RBAC. Tempo has retention. Prometheus may have namespace-scoped access via kube-rbac-proxy. You translate those backend contracts into UI, you do not bypass them in the frontend.

Never send a cluster-admin token from the plugin ‘to make the demo work.’ UserToken exists so the graph shows what this user is allowed to see.

GitOps can undo a UI click

Many clusters reconcile the Console custom resource from git. The console Operator enables dynamic plugins listed in spec.plugins. If you toggle a plugin in the UI (or apply a CR by hand) and git does not contain that name, the next sync removes it.

YAML
apiVersion: operator.openshift.io/v1
kind: Console
metadata:
  name: cluster
spec:
  plugins:
    - monitoring
    - logging-view-plugin
    - troubleshooting-panel

This is the #1 “my plugin vanished overnight” story. It looks like a frontend regression. It is an operations contract. Your architecture one-pager should mention it.

Git --reconcile--> Console.spec.plugins | v console Operator enables those names only A live UI toggle not in git → next sync deletes it

Tutorial

Console plugins

Federation, extensions JSON, ConsolePlugin CR, proxy, enablement, local loop. After this section you should be able to walk a blank whiteboard through “how my page appears under Observe.”

Dynamic plugins: the console loads your JS at runtime

The OpenShift console is one React app. Teams cannot wait for a monolith release to add Observe pages. The solution is Webpack 5 module federation: the console (host) loads a remoteEntry file from your plugin at runtime and mounts the modules you exposed.

Your plugin build → dist/remoteEntry.js + chunks → HTTP server in the cluster (often a small Go binary) Console (host) reads ConsolePlugin CR → fetches remoteEntry → executes your page inside the console chrome You do not ship a second SPA. You do not iframe Grafana as the architecture.

That is why the template uses Yarn + Webpack 5, not Vite. Vite is a fine bundler for a standalone app. Here the contract is “federated remote the console already knows how to load.” Fighting it is a week of 404s on remoteEntry.

Metadata the console reads from your package:

JSON
{
  "name": "my-observe-plugin",
  "consolePlugin": {
    "displayName": "My Observe",
    "exposedModules": {
      "./MetricsPage": "./src/components/MetricsPage.tsx"
    }
  }
}

exposedModules keys are what console-extensions.json will point at. The path is a Webpack module, not a URL route by itself.

console-extensions.json is your nav and routes

The console does not import your router. You declare extensions: “put a nav item here,” “render this module at this path,” “add a tab on the pod page.” Shape (simplified teaching example — always match the template’s current types):

JSON
[
  {
    "type": "console.navigation/href",
    "properties": {
      "id": "observe-my-metrics",
      "name": "My metrics",
      "href": "/observe/my-metrics",
      "perspective": "admin",
      "section": "observe-section"
    }
  },
  {
    "type": "console.page/route",
    "properties": {
      "path": "/observe/my-metrics",
      "component": { "$codeRef": "MetricsPage" }
    }
  }
]

$codeRef must match an exposedModules key. If they disagree, the nav click is a blank page. That is the first thing to check after a “my page is empty” report.

Other extension types you will see in sibling plugins: tabs on existing pages, dashboards, flags that hide a nav item unless COO or CMO is present. Feature flags are how one repo serves “CMO-only metrics” vs “COO Perses” without two codebases.

Read one real console-extensions.json in monitoring-plugin after this tutorial. Do not memorize every type. Memorize: nav, route, codeRef, flag.

ConsolePlugin CR: install contract, field by field

A ConsolePlugin custom resource tells the console Operator: this plugin exists, here is the Service that serves its assets, here is what it may proxy to.

YAML
apiVersion: console.openshift.io/v1
kind: ConsolePlugin
metadata:
  name: example-observe
spec:
  displayName: Example Observe
  backend:
    service:
      name: example-plugin
      namespace: example
      port: 9443
      basePath: /
  proxy:
    - alias: loki
      objectRef:
        name: loki
        namespace: openshift-logging
        kind: Service
        port: 8080
      authorization: UserToken
      caCertificate: default
  • metadata.name is the name that must appear in Console spec.plugins.
  • backend.service is where remoteEntry.js is served (HTTPS, service CA).
  • proxy entries become console backend routes like /api/proxy/plugin/example-observe/loki/.... The browser never talks to Loki’s ClusterIP.
  • authorization: UserToken forwards the logged-in user’s token so RBAC applies. Impersonating cluster-admin from the plugin is a security bug.
Browser → console backend /api/proxy/plugin/<plugin>/<alias>/... → Service (Loki / Tempo / Korrel8r) TLS: service CA Auth: user token CORS hacks against ClusterIP are not the architecture.

Several Observe plugins ship a small Go server: static assets + sometimes extra proxy logic. You do not need to write Go on day 1. You do need to read one handler and know why HTTPS + service CA exists (the console will not fetch plaintext HTTP from a random pod).

Enabled on the cluster ≠ CR exists

Two switches, both required:

  1. The ConsolePlugin object exists (and its Service is healthy).
  2. The cluster Console resource lists that name under spec.plugins.

Admins can enable plugins in the UI. If GitOps owns Console, that click is undone on the next reconcile unless git is updated. COO’s UIPlugin is a third layer: it deploys the plugin + backends, but the Console list still has to include the name.

YAML
apiVersion: observability.openshift.io/v1alpha1
kind: UIPlugin
metadata:
  name: monitoring
spec:
  type: Monitoring
  monitoring:
    perses:
      enabled: true

UIPlugin says “COO, install this Observe extra.” ConsolePlugin says “console, load this remote.” Console spec.plugins says “yes, actually enable it.” Mixing the three names in a standup is how you debug for a day in the wrong repo.

Local loop: template, Yarn, console-in-a-container

The documented loop in openshift/console-plugin-template is:

  1. Clone the template. Keep Yarn + Webpack. Do not “just Vite it.”
  2. Install deps, start the plugin webpack-dev-server (it serves the federated build).
  3. Run the script that starts a console container pointed at your plugin URL (and usually at a real cluster API for k8s data).
  4. Open the console, enable the plugin if needed, hit your page.
yarn + webpack-dev-server (your remoteEntry on localhost) podman/docker console (host app, loads your remote) kubeconfig / oc (API for lists, or a CRC cluster) You are testing federation + PF, not a mocked iframe.

Blockers you should expect: podman vs Docker, Apple Silicon images, needing a cluster for anything beyond a static page, HTTPS mixed content. Write them down; do not stall the 30-day plan for three days on CRC. A static PF page in the template still teaches the contract.

Do not import PatternFly CSS in the plugin. The host already loaded PF. A second copy fights dark/light theme. Prefix any extra class with your plugin name. No element selectors on body.

Tutorial

PatternFly 6

Why PF 6, why you must not import PF CSS, three screens to build, a11y as a gate, i18n as Done. Tailwind is a defect here, not a preference.

PatternFly 6 is the house look — not a suggestion

OpenShift 4.19 unified perspectives and moved the console to PatternFly 6. Console 4.22 is PF 6. New plugins target PF 6. If you ship Tailwind, Bootstrap, or a SaaS-dashboard CSS file, the page will look foreign, fight dark theme, and fail review.

The console already loads PF base styles and theme tokens (including dark/light). Your plugin uses PF React components and CSS variables. If you import '@patternfly/patternfly/patternfly.css' (or any full PF CSS bundle) you double-load: fonts, resets, and tokens collide. That is a defect, not a shortcut.

Console host: PF 6 CSS + theme (light/dark) + masthead Your plugin: @patternfly/react-core components optional: a few prefixed classes Not allowed: Tailwind CDN, Bootstrap, import PF CSS, restyle body

SDK wrappers exist for things the console already does (page headers, list pages). Prefer them when you are on a list-of-resources screen. When you are on an Observe chart page, PF Toolbar + EmptyState + Alert + Spinner are the usual skeleton.

Build three screens the console already knows

If you can build these without custom CSS soup, you can read monitoring-plugin:

  1. Filterable table — Toolbar with SearchInput, Table, Pagination, EmptyState when rows.length === 0.
  2. Form — Form, FormGroup, TextInput, Select, helper text, invalid state. Submit does not trap focus.
  3. Chart + table fallback — a visual and a data table (a11y: charts are not the only representation).
TSX
import {
  Toolbar, ToolbarContent, SearchInput,
  EmptyState, EmptyStateBody, PageSection,
} from "@patternfly/react-core";

export function AlertList({ rows, q, setQ }: Props) {
  const filtered = rows.filter((r) => r.name.includes(q));
  return (
    <PageSection>
      <Toolbar>
        <ToolbarContent>
          <SearchInput value={q} onChange={(_, v) => setQ(v)} aria-label="Filter alerts" />
        </ToolbarContent>
      </Toolbar>
      {filtered.length === 0 ? (
        <EmptyState titleText="No alerts">
          <EmptyStateBody>Firing alerts for this namespace will show up here.</EmptyStateBody>
        </EmptyState>
      ) : (
        <table className="pf-v6-c-table">{/* or PF Table composable */}</table>
      )}
    </PageSection>
  );
}

Class prefix: if you must add a class, example-observe__foo, never .table or button. Element selectors leak into the console chrome.

Senior review comment to practice: ‘This is a custom div that PF already has as Toolbar / Pagination / EmptyState. Use the component so we inherit a11y and theme.’

Accessibility is a ship gate, not a polish pass

This job names accessibility. That means:

  • Keyboard. Tab order: time picker → filters → chart/table → row actions. No keyboard trap in the query bar.
  • Name, role, value. Icon-only buttons have aria-label. Custom widgets need a role. Do not reinvent a listbox.
  • Charts are not color-only. Pattern + label, or a table. Red vs green is insufficient.
  • Failures are announced. aria-live="polite" on “query timed out.” EmptyState title is a heading.
  • Contrast in both themes. PF tokens are the safe default; random hex is how you fail dark mode.

Practice: axe DevTools on your three screens, then a keyboard-only pass with the mouse unplugged. Fix the first five issues. That is the bar, not a 100-page WCAG essay.

Hard-coded English is a review block

Console plugins translate with react-i18next. Strings live in JSON locale files. A header that says <h1>Alerts</h1> skips the pipeline and fails review on this team even if the English is perfect.

TSX
import { useTranslation } from "react-i18next";

export function Title() {
  const { t } = useTranslation("plugin__example-observe");
  return <h1>{t("alerts.title")}</h1>;
}
JSON
{
  "alerts.title": "Alerts",
  "alerts.empty": "No alerts in this range"
}

Namespace names are plugin-specific (often plugin__<name>). Look up existing keys before adding a synonym. Interpolation for counts: t("showing", { shown: 20, total: 4812 }) — do not concatenate sentences in code.

Three signals

Definitions, first-click rules, join keys, incidents vs raw alerts. Query languages in the next sections are how you implement this picture.

Metric, log, trace — definitions you can teach

These words get used as synonyms in slides. They are not synonyms in the product.

SignalWhat one point meansQuestion it answersStore (typical here)
MetricA number aggregated over a window (rate, gauge, histogram bucket)How much / how often / is it worse?Prometheus / Thanos
LogAn event with a payload (string or JSON) at a timestampWhat exactly happened in this process?Loki
TraceA tree of spans for one request or jobWhere did this call spend time / fail?Tempo

A trace is not a better metric. You cannot graph SLO error ratio from one waterfall. A log is not a better trace — you will not reconstruct a 30-service call graph from grep. A metric will not give you the stack trace.

RED: Rate Error Duration → metrics first USE: Utilization Saturation Errors → metrics first Crash / exception / message → logs first This checkout is slow → traces first Related to this alert? → Korrel8r / troubleshooting

One journey, not three dump pages

Excellent Observe UI keeps time range + namespace + cluster while the user jumps. The join keys are boring on purpose:

  • Metrics ↔ traces: service.name, exemplar trace id, HTTP route.
  • Traces ↔ logs: trace_id / traceId on the log line (if the collector injected it), plus namespace + pod.
  • Logs ↔ workload: pod name, namespace, container (previous container for CrashLoop).
  • Alert → everything: alert labels (namespace, alertname, pod) into Korrel8r.

If those labels were never written (bad instrumentation), the UI cannot invent them. Your collaboration with backend is “we need this attribute on the span / this label on the metric,” not a new SPA.

Cardinality: a metric label with unbounded values (user id) will melt Prometheus and the chart. The UI must not present ‘group by user’ as a friendly chip.

When the cluster is on fire, do not open 4000 alerts

Alertmanager still fires alerts. The incidents surface (COO cluster-health analyzer) groups bursts into a timeline: fewer rows, a start/end, a component. It does not replace alerting rules. It replaces the human failure mode of staring at a wall of firing.

What you must not hide when you group: the underlying alerts still exist; severity; “this incident is 3 alerts, not 1 outage.” Empty state: “no incidents in range” vs “analyzer not installed.”

PromQL

You will not memorize every function. You will know counters vs gauges, rate vs irate, how a range query is parameterized, and which empty state you are in. That is enough to argue with a backend query in a design review.

Instant vs range: what the chart actually asks for

Prometheus stores time series: a metric name + labels (the identity) and samples (timestamp, value). The language is PromQL. The UI almost always sends a range query: start, end, and step. The backend returns one series per matching identity, with a point at each step.

KindWhat you getUI use
Instant queryOne value “now” (or at a timestamp) per seriesSingle-stat, table of current values
Range queryA matrix: series × timestampsLine/area charts, heatmaps
Browser time picker → start, end, step GET /api/v1/query_range?query=...&start=&end=&step= → { metric: {code:"500"}, values: [[t, v], ...] } Empty: no matching series. Error: parse / timeout. Partial: some series dropped.

A selector picks series. Labels are equality, regex, or not-equal:

PromQL
http_requests_total{job="checkout", code="200"}
http_requests_total{code=~"5.."}      # regex
http_requests_total{code!="200"}

Counters only go up (except on process restart). Graphing a raw counter looks like a staircase and lies on restarts. You almost always wrap counters in rate() or increase(). Gauges (CPU, memory, queue depth) you can plot raw or with avg_over_time.

If a backend engineer says ‘just graph http_requests_total,’ ask: is it a counter? If yes, the UI should offer rate, not the raw series, as the default.

rate, irate, histograms — the three you will type

rate(x[5m]) is “per-second average increase of counter x over the last 5 minutes,” computed at each step of a range query. Use it for graphs and SLOs. The window [5m] must be several scrapes long (if you scrape every 30s, 5m is fine; 10s is not).

irate(x[5m]) uses only the last two samples. It is spiky — useful for “what is happening in this instant,” misleading as a 6-hour SLO chart.

PromQL
# Requests per second, by status class
sum(rate(http_requests_total[5m])) by (code)

# Error ratio — same grouping in numerator and denominator
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))

# p99 latency if you have a histogram
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

by (label) keeps those labels and sums away the rest. without (label) is the inverse. The #1 PromQL bug in a UI is numerator and denominator grouped differently, so the ratio is nonsense. The #2 bug is grouping by a high-cardinality label (user id, pod uid, request id) — thousands of series, melted Prometheus, melted browser.

histogram_quantile needs the _bucket series and the le label. It is an estimate, not a true percentile of raw events. Recording rules exist so the UI does not recompute expensive queries on every zoom.

Good group-by: code, route, job, namespace Bad group-by: user_id, email, trace_id, pod_uid UI job: do not offer the bad ones as a chip. Warn if series count explodes.

When the time picker moves, abort the in-flight fetch (AbortController). Otherwise you paint a stale range on top of a new one. Cap the number of series you draw (for example 20) and say “12 more not shown.”

What a metrics page must show besides the line

PromQL can return:

  • No data — query is valid, nothing matched (wrong label, empty namespace).
  • Parse error — show the backend message; do not swallow it into “No data.”
  • Timeout / 502 — the query is too expensive or the proxy died.
  • Partial — some shards failed (common with Thanos). Show the series you have and a warning.

Each of those is a different PatternFly EmptyState or Alert. Color-only “red chart” is not enough. A screen reader needs a live region: “Query failed: timeout.”

Multi-cluster (ACM + Thanos) adds a cluster picker. ‘cluster’ is a first-class filter, not a footnote. A query that worked on one cluster can be empty on another because scrape configs differ.

LogQL

Selector, then line filter, then parser. Schema names differ. Empty vs 403 vs timeout are three products. That is the logging UI job in one paragraph — the rest of this section unpacks it.

Selector first, then grep — that order is the product

Loki stores logs as streams: a set of labels (like Prometheus) plus lines. LogQL starts with a stream selector in curly braces. That is the cheap index. Everything after it is a filter or parser on the line payload — more CPU, more scan.

LogQL
# 1. Pick streams (labels). Cheap if labels are the index.
{kubernetes_namespace_name="shop", app="checkout"}

# 2. Then filter lines. |= is substring. |~ is regex. != / !~ negate.
{kubernetes_namespace_name="shop", app="checkout"} |= "error"

# 3. Then parse structured lines so you can filter on fields.
{kubernetes_namespace_name="shop", app="checkout"}
  |= "error"
  | json
  | status >= 500

If you skip the selector and regex across every tenant, you can take down Loki the same way unbounded PromQL takes down Prometheus. The query bar should require or strongly suggest namespace / application labels before a free-text grep.

Good: {namespace, app, container} then |= "error" Bad: {job=~".+"} |~ "error" across the whole cluster UI: namespace picker first, not a blank grep box as the hero.

Line filters: |= "error" substring, |~ "err(or|s)" regex, != / !~ negate. After a parser (| json, | logfmt, | regexp), you can filter on extracted fields.

LogQL can also become a metric query (count of matching lines over time) with rate({...} |= "error" [5m]). That is how “errors/sec from logs” charts work — still a Loki query, not Prometheus.

viaq vs OTel: the same UI, different field names

OpenShift logging has lived through more than one schema. Older stacks emit viaq labels (you will see names like kubernetes_namespace_name, kubernetes_pod_name). Newer paths emit OpenTelemetry conventions (k8s.namespace.name, k8s.pod.name, service.name — dotted, semantic-conv style).

The logging plugin exposes a schema switch because a query written for viaq returns empty, not an error, on OTel streams. Empty is the worst failure mode: users think there are no logs.

text
viaq-ish:  {kubernetes_namespace_name="shop"} |= "error"
OTel-ish:  {k8s_namespace_name="shop"} |= "error"
           (exact label keys depend on the collector config)

UI job: remember the schema next to the query, or rewrite labels
when the user toggles the switch.

When you expand a line, show parsed JSON if present, not only the raw string. Link pod name → workload page. If a trace_id / traceId is on the line, that is the jump to traces — do not make the user copy-paste if the collector already injected it.

A 403 from Loki and ‘no matching streams’ must not share the same EmptyState. One is permissions. One is filters. Mixing them trains people to open tickets on the wrong team.

The log list is a virtualized product, not a <pre>

CrashLoop debugging is the flagship log journey: current container and previous container (the one that just died). If the UI only tails the new empty container, you hid the crash.

Lists are huge. Virtualize rows (render what is on screen). Do not dump 50k <div>s. Wrap long lines; keep a monospace option. Filter chips (severity, container) should compose with the LogQL bar, not fight it.

Live tail is a separate mode: a websocket or poll with pause. Pause must be obvious — otherwise the user’s scroll position is a lie.

Traces and OpenTelemetry

Collector in the middle, Tempo as the store, TraceQL to search, waterfall to read. Semantic conventions are how metrics, logs, and traces agree on names. Jaeger is history in this UI.

OpenTelemetry is the join key, Tempo is the store

A trace is one request (or job) as a tree of spans: each span is work in one service (or library) with a start, duration, status, and attributes. OpenTelemetry (OTel) is the instrumentation + collector pipeline that produces those spans (and can also emit metrics and logs). Tempo is the store the OpenShift tracing UI queries. Jaeger appears in old slides; you learn Tempo.

App SDKs / auto-instr → OTel Collector → Tempo (tail sample, attributes) Metrics scrape → Prometheus Logs → Loki Join keys: service.name, k8s.*, http.*, trace_id

Semantic conventions are the agreed attribute names: service.name, k8s.namespace.name, http.route, http.status_code. If two teams name the service “checkout” vs “Checkout-API,” correlation dies. The UI should show service.name as the primary identity, not a random process name.

An exemplar is a trace id stuck onto a metric sample. That is how a p99 spike on a chart becomes “open this trace.” If exemplars are missing, the jump is a TraceQL search with time window + service — harder, still doable.

OTel is not a React library. You will not import it in the plugin. You will display the fields the collector already wrote.

TraceQL: find the slow tree, then open the waterfall

TraceQL (Tempo) picks spansets. The curly-brace query is “spans that match these conditions.” Duration, status, resource attributes, and span attributes are the usual knobs.

TraceQL
# Slow checkouts
{ resource.service.name = "checkout" && duration > 2s }

# Failed spans on a route
{ resource.service.name = "checkout" && status = error && span.http.route = "/pay" }

# Find by attribute the logs also have
{ span.k8s.namespace.name = "shop" && duration > 1s }

Search results are a table (trace id, service, duration, start). Click → waterfall: parent/child spans on a time axis. The waterfall is UI, not another query language. You need: collapse/expand, span attributes panel, links to logs (by trace id) and to metrics (by service).

Status error on a span is not the same as HTTP 500 on a child. Show both. Span events (exceptions) belong in the attributes drawer.

Metrics (p99) --exemplar--> one TraceQL hit --> waterfall --> logs where trace_id = ... Time range and namespace should survive every jump.

When is a trace the wrong first click? Aggregates (error rate, saturation) — start in metrics. A CrashLoop with no incoming request — start in logs. Traces shine when you already know “this request / this job” or “this service is slow.”

Waterfall performance and missing tracing

A busy trace can have thousands of spans. Virtualize the waterfall. Do not layout 8k absolutely-positioned DOM nodes on first paint. Truncate with “show 500 more.”

If Tempo or the tracing plugin is not installed, the Observe → Traces item should say so (or not appear). A Korrel8r trace node that 404s is a worse experience than hiding the node with copy: “Tracing UI is not installed.”

Retention: Tempo may keep 24h. A jump from a 7-day metrics chart to traces must say “trace expired” instead of an empty table that looks like “no errors.”

Observe UX

The difference between a dashboard toy and this job: time range survives jumps, fetches abort, and empty/error/timeout/partial are designed. PatternFly already has EmptyState and Alert — use them.

The time picker is a product, not a date widget

Every Observe surface shares a time range (last 5m, 1h, 6h, custom). That range is part of the user’s mental context. Jumps (metrics → logs → traces) that drop the range feel broken even if each page is “correct.”

When the range changes:

  1. Abort in-flight fetches (AbortController). Late responses must not overwrite the new range.
  2. Reset “live tail / refresh” so you are not mixing a stream from the old window.
  3. Keep namespace, cluster, and severity filters. Only clear filters that are illegal in the new context.
TS
const ac = useRef<AbortController | null>(null);

function runQuery(range: TimeRange, query: string) {
  ac.current?.abort();
  ac.current = new AbortController();
  return fetch(url, { signal: ac.current.signal, ... });
}

Absolute vs relative: “last 30 minutes” should keep sliding on refresh; a custom absolute range should not. Label which mode you are in. Keyboard: the picker is in the tab order before the chart.

Empty, error, timeout, partial — four screens

Happy-path charts are the easy third of the job. The other two thirds are states:

StateCauseUI
EmptyValid query, zero series/lines/spansEmptyState: what was queried, one action (widen range, clear filter)
ErrorParse, 400, 403Alert with the message. 403 copy: permissions, not “no data.”
Timeout504, client abort after N secondsAlert + “narrow the query” + retry. Live region for a11y.
PartialThanos / Loki querier dropped a shardShow data + warning: “12 of 40 series unavailable.”
TSX
{status === "empty" && (
  <EmptyState titleText="No series in this range">
    <EmptyStateBody>
      Try the last 6 hours or drop the code="500" filter.
    </EmptyStateBody>
  </EmptyState>
)}
{status === "timeout" && (
  <Alert variant="danger" isInline title="Query timed out"
    role="status" aria-live="polite" />
)}
If you only design the line chart, PM will still call the page ‘done’ and on-call will hate you. Put these four states in the first mock, not in QA.

Cardinality and list size are UX bugs

A PromQL group-by on user_id can return 50k series. A log query without a namespace can scan the cluster. A trace waterfall can have 20k spans. The backend may survive. The console tab will not.

  • Cap series drawn (e.g. top 20 by magnitude). Text: “Showing 20 of 4,812.”
  • Refuse or warn on selectors that are obviously unbounded — do not silently freeze.
  • Virtualize tables and waterfalls.
  • Debounce the query bar; do not fire PromQL on every keystroke.
User types → debounce 300ms → validate → fetch (abortable) Paint: at most N series / rows If N exceeded: warning, not a frozen tab

Perses is an open-source dashboard app designed for cloud-native: dashboards and datasources are namespace-scoped custom resources. That matches RBAC (you can only see boards in namespaces you can get) and GitOps (the board is YAML in git, reviewable in a PR).

On OpenShift, COO wires Observe → Dashboards (Perses) when the UIPlugin enables it. The monitoring plugin does PatternFly theming so Perses does not look like a foreign iframe theme.

  name: checkout-slo
  namespace: shop

  display:
    name: Checkout SLO
  duration: 6h

---

  name: prometheus
  namespace: shop

  plugin:
    kind: PrometheusDatasource

      proxy:
        url: https://thanos-querier.openshift-monitoring.svc:9091

You do not need to memorize every panel JSON field. You need: namespaced, RBAC-aware list, empty state when CRD/COO is missing, and “this is the visualization direction.”

The editor in the console: create, rename, duplicate, edit panels. Datasources: Prometheus/Thanos, Loki, Tempo as documented for the version you target. If a datasource CR is missing, the board shows a configuration empty state, not a mysterious blank chart.

If you do one extra clone in week 3: perses/perses (or perses-dev). Create a dashboard as YAML. Import one Grafana JSON. That talk comes up constantly.

Correlation

Rules that connect signals, a panel that must not 404, tests on hrefs. This is the ‘unified workflow’ in concrete form.

Korrel8r is rules, not magic AI

Korrel8r is an open-source engine: given a starting object (an alert, a metric selector, a pod), rules produce related objects in other domains (metrics, logs, pods, netflows, alerts, traces — depending on what is installed). It is deterministic. It is not an LLM summarizing your cluster.

Start: Alert {alertname=CrashLoop, namespace=shop, pod=checkout-7d} rules → Log query for that pod → Metric selector (restarts) → Pod / ReplicaSet / Deployment → maybe netflow, maybe trace Each neighbour is a domain + a query string.

If Logging is not installed, log neighbours cannot be realized in the UI. The graph must not pretend they work. Missing plugin = honest copy, not a 404 on click.

The troubleshooting panel is a URL mapper with a graph

The troubleshooting panel plugin calls Korrel8r, draws a graph, and on click opens the right console URL with the query filled in. That mapping (Korrel8r domain → Observe path + query string) is the product. If the logs plugin route changes and the map does not, the graph still looks pretty and the click is wrong. Silent P1.

text
given:  node { domain: "log", query: "{namespace=shop,pod=checkout}" }
expect: /monitoring/logs?...   or whatever the current logging-view path is
test:   snapshot the href; fail CI if it drifts
missing logging plugin:  node shows “Logs UI not installed”, no 404

The panel repo calls out unit tests on those maps. Read them. When you change an Observe route, you are a consumer of this map even if you did not touch Korrel8r.

Clone later: korrel8r/korrel8r (rules) and openshift/troubleshooting-panel-console-plugin (graph + hrefs). AGENTS.md in the panel repo is a short, useful read.

Unified UI workflows in the job description means this: alert → related signals without the user inventing three queries. The graph is the UX; the tests are the quality bar.

Short answer. A Webpack 5 federated bundle the console loads at runtime, registered with a ConsolePlugin CR.

Short answer. So the console backend can reach in-cluster services (Loki, Tempo, Korrel8r) with TLS and optional user token.

Deep explanation. The browser must not CORS-hack cluster IPs. Default is HTTPS plus the service CA. Several plugins add a small Go server to serve assets and proxy.

7. What is an accessibility miss that will fail a senior review?

Short answer. Color-only charts, no keyboard path through the toolbar, unlabeled icon buttons, missing live region on query failure.

Deep explanation. WCAG is in the job. axe plus a keyboard pass. Name/role/value on custom widgets. i18n keys — hard-coded English in a header is a block.

Common misconception. a11y is a nice-to-have after GA.

Follow-up. How would you announce ‘query timed out’ to a screen reader?

signalsdomainQ8

8. When do you start with logs vs metrics vs traces?

Short answer. Logs: a specific event (crash, 401). Metrics: aggregates (error rate, p99). Traces: one request across services.

Deep explanation. CrashLoop → logs, then restart metrics. High p99 → metrics then trace. Auth failures → logs plus trace attributes.

Common misconception. Always open traces first because they are richest.

Follow-up. What do you open if ‘everything is on fire’?

signalsdomainQ9

9. Why is a high-cardinality label a UI bug as well as a backend bug?

Short answer. The chart invites unbounded series; Prometheus and the browser both melt.

Deep explanation. Do not offer user-id as a PromQL group-by. Cap series. Warn. Prefer recording rules for expensive queries.

Common misconception. The UI should run whatever query the user typed.

Follow-up. How do you abort work when the time picker moves?

querypromqlQ10

10. rate() vs irate() — when is rate() the default?

Short answer. rate() averages over the range; use it for graphs and SLOs. irate() uses the last two points — spiky, for instant troubleshooting.

Deep explanation. Counters need increase/rate, not a raw gauge plot. histogram_quantile needs a histogram. by/without must match the question.

Common misconception. irate is always more accurate.

Follow-up. Write PromQL for 5xx ratio without grouping by user.

querylogqlQ11

11. What is a LogQL stream selector vs a line filter?

Short answer. Selector picks streams (labels). Line filter then greps the payload. JSON unpack is after that.

Deep explanation. The logging plugin schema switch (viaq vs OTel) changes field names. Inventing {app=} on the wrong schema returns empty, not an error you can see.

Common misconception. LogQL is grep on every node disk.

Follow-up. Why might a filter that worked last year return nothing after OTel migration?

querytraceqlQ12

12. What is TraceQL for?

Short answer. Find traces in Tempo by service, duration, status, attributes — then open a waterfall.

Deep explanation. OTel semantic conventions (service.name, k8s, http) are the join keys with metrics and logs. Exemplars can jump metric → trace.

Common misconception. Jaeger is the current OpenShift tracing UI.

Follow-up. When is a trace the wrong first click?

persesdashboardsQ13

13. Why Perses instead of ‘just Grafana’ on this stack?

Short answer. Dashboards and datasources are namespace-scoped CRs — RBAC and GitOps. COO wires Observe → Dashboards (Perses).

Deep explanation. Grafana import exists as a migration. Visualization direction is Perses + PatternFly theming in monitoring-plugin, not a new Grafana plugin career.

Common misconception. Perses is a Grafana fork you must re-skin by hand.

Follow-up. Where does a Perses dashboard live as an object?

korrel8rcorrelationQ14

14. What does Korrel8r do for the troubleshooting panel?

Short answer. Rules connect alerts, metrics, logs, pods, netflows. The panel draws a graph and maps clicks to console URLs.

Deep explanation. If Logging is missing, log nodes will not be useful. URL maps need unit tests — a pretty graph with a 404 is a silent product bug.

Common misconception. Korrel8r is a replacement for Prometheus.

Follow-up. What repo owns the OpenShift URL mapping?

opscmoQ15

15. CMO vs COO in one minute.

Short answer. CMO is the default in-cluster Prometheus stack. COO is the meta-operator that adds optional Observe UIs, Perses, incidents, ACM wiring.

Deep explanation. Users still live under Observe. COO installs plugins from UIPlugin. CMO still answers ‘is cluster monitoring on?’

Common misconception. COO replaced Prometheus.

Follow-up. Which operator do you talk to if Perses is missing?

opsgitopsQ16

16. A plugin was enabled yesterday and is gone today. First question?

Short answer. Does GitOps own the Console CR? If yes, the name must be in git spec.plugins.

Deep explanation. A UI toggle without git is a race. Looks like a frontend regression. Check operators and Console spec before Webpack.

Common misconception. Always a bad webpack build.

Follow-up. Where do you look besides the plugin Deployment?

seniorleadQ17

17. What does ‘lead the UI’ mean here if you are not rewriting the console?

Short answer. Propose plugin boundaries, proxies, feature flags, and PF patterns — then land them upstream.

Deep explanation. You sit between signal teams, PM, and UX. Empty states and RBAC-aware lists are the product. A new SPA is usually the wrong architecture.

Common misconception. Lead means pick the chart library.

Follow-up. What artifact would you write before week 6?

seniorupstreamQ18

18. What does ‘own it through upstream’ imply for a PR?

Short answer. The feature lands on GitHub first (DCO sign-off, OWNERS), then in the operator that installs it.

Deep explanation. Downstream-only patches surprise the next rebase. Know backport norms. Tiny docs/test PRs teach the machine before a large UI change.

Common misconception. Ship only on the internal fork.

Follow-up. What is Signed-off-by for?

seniorreviewQ19

19. Name three review comments that are senior, not style nits.

Short answer. PF misuse, unbounded fetch/cardinality, missing i18n or a11y, proxy vs hardcoded service, GitOps Console spec.

Deep explanation. Lint is table stakes. You catch silent no-ops: URL maps, feature flags, empty/error/partial query states.

Common misconception. Rename a variable and approve.

Follow-up. What would you block a merge for on a chart PR?

plugini18nQ20

Short answer. Console plugins are translated with react-i18next. English in a header skips that pipeline.

Deep explanation. Keys live with the plugin. You will see this on every sibling repo. Treat it as part of Done.

Common misconception. English-only is fine for an internal plugin.

Follow-up. Where do you look for existing keys before adding a new one?

21. What is the incidents surface for?

Short answer. Group alert bursts into a timeline so humans are not staring at 4000 raw alerts.

Deep explanation. It is a COO cluster-health feature, not a replacement for Alertmanager. Start here when ‘everything is on fire.’

Common misconception. Incidents replace Prometheus rules.

Follow-up. When do you still open Alertmanager / metrics?

Short answer. Semantic conventions, collector as the pipeline, Tempo as the store, exemplars as metric→trace jumps.

Deep explanation. You do not need to write the collector config on day 1. You do need to know why service.name is the join key and why Jaeger is legacy talk.

Common misconception. OTel is a React library.

Follow-up. Name one attribute you would show on a trace search row.

Deep explanation. Perses is the Kubernetes-native board. Grafana JSON in is a bridge. Know that the conversation exists.

Common misconception. Grafana is the Observe dashboards page.

Deep explanation. Extensive URL-map tests exist for a reason. Missing sibling plugins (logging) need honest empty copy.

Write YAML: plugin name, backend service, one Loki proxy with UserToken. Then say how an admin enables it.

apiVersion: console.openshift.io/v1

metadata:
  name: example-observe
spec:
  displayName: Example Observe
  backend:
    service:
      name: example-plugin
      namespace: example
      port: 9443
  proxy:
    - objectRef:
        name: loki
        namespace: openshift-logging

# enable: Console spec.plugins += example-observe

            Language

            Glossary

            ACM

            Advanced Cluster Management. Multi-cluster; often Thanos for metrics and a different alerting path.

            Alertmanager

            Routes and groups Prometheus alerts. Incidents sit above raw alert floods.

            CMO

            Cluster Monitoring Operator — default in-cluster Prometheus stack on OpenShift.

            ConsolePlugin

            CR that registers a dynamic plugin: assets service, optional proxy, display name.

            COO

            Cluster Observability Operator — installs optional Observe UIs, Perses, incidents, related backends.

            CRC / OpenShift Local

            A laptop-sized OpenShift cluster for plugin loops.

            DCO

            Developer Certificate of Origin. Commits need Signed-off-by for many OpenShift repos.

            Dynamic plugin

            Webpack 5 module federation: the console loads your JS at runtime.

            Exemplar

            A trace id attached to a metric sample so the UI can jump metric → trace.

            GitOps Console spec

            If git owns the Console CR, plugin names must live there or a sync disables them.

            Korrel8r

            Correlation engine: rules that link alerts, metrics, logs, pods, netflows.

            LogQL

            Loki query language. Stream selector, then line filters, then unpack.

            Loki / LokiStack

            Log store. Observe → Logs talks to it through a plugin proxy.

            OTel

            OpenTelemetry: collector pipeline + semantic conventions. Not a React library.

            OWNERS

            File that lists who can approve a repo area. Read it before you ping randomly.

            PatternFly 6

            OpenShift console design system from 4.19+. Do not import its CSS in a plugin.

            Perses

            Cloud-native dashboards as Kubernetes CRs. Observe → Dashboards (Perses).

            PromQL

            Prometheus query language. Instant vs range; rate on counters.

            spec.plugins

            Console Operator list of enabled dynamic plugins.

            spec.proxy

            ConsolePlugin field: console backend proxies to an in-cluster Service.

            Tempo

            Trace store used with the current tracing UI. Jaeger is legacy conversation.

            Thanos

            Long-term / multi-cluster metrics path (often with ACM).

            TraceQL

            Tempo’s language to find traces by service, duration, attributes.

            Troubleshooting panel

            Console graph UI over Korrel8r results; clicks must map to real routes.

            UIPlugin

            COO CR that selects which Observe UI extras to install.

            viaq

            Legacy OpenShift logging schema. OTel schema is the other switch in the logs UI.

            WCAG

            Accessibility standard. Keyboard, contrast, name/role/value — in the job, not polish.
