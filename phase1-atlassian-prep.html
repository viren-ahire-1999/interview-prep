1. Big O — interview-ready analysis

Big O is a language for how work grows as input grows, ignoring constants and lower-order terms. Interviewers want two things: (1) you can read your own code and assign a class, (2) you can use that class to choose a better structure.

Mental model

Ask: if n doubles, does the work stay the same, grow a little, grow linearly, or explode? That single question separates O(1) from O(log n) from O(n) from O(n²) from exponential.

TypeScript
function binarySearch(a: number[], t: number): number {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {            // halves each step → O(log n)
    const mid = (lo + hi) >> 1;
    if (a[mid] === t) return mid;
    if (a[mid] < t) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

function maxVal(a: number[]): number {
  let m = -Infinity;
  for (const x of a) if (x > m) m = x; // one pass → O(n)
  return m;
}

function sortedCopy(a: number[]): number[] {

}

  return false;
}

How to analyze nested loops

Multiply independent iterations: for i in 0..n around for j in 0..n is O(n²). If the inner loop is j = i..n, it is still O(n²) (the 1/2 is a constant). If the inner loop is binary search, you get O(n log n). If the inner loop walks a shrinking window that only moves forward across the whole algorithm, it may collapse to O(n) — that is the sliding-window argument.

Amortized complexity

Amortized means average cost per operation over a worst-case sequence, not “average input.” Dynamic array (JS Array.push) is O(1) amortized: most pushes are cheap; rare resizes copy 2k items, but that cost is paid off by the next k cheap pushes. Hash table rehash is the same story.

Average vs worst case

HashMap lookup is O(1) average, O(n) worst if everything collides. In interviews, say: “Engineered hash maps are treated as O(1) expected; I would mention the theoretical worst case if the interviewer is probing.” Quicksort is O(n log n) expected, O(n²) worst (sorted input + naive pivot). Heapsort/mergesort give deterministic O(n log n).

Interview answers

  • HashMap lookup? Expected O(1) time, O(n) space for n keys.
  • Why is binary search O(log n)? Each comparison discards half the remaining range. Starting from n, you can halve only about log₂ n times before one element remains.
  • Why is sorting usually O(n log n)? Comparison sorts have an Ω(n log n) lower bound: there are n! orderings, and each comparison has 2 outcomes, so you need ~ log₂(n!) ≈ n log n comparisons. Counting/radix sort can beat that when keys are integers with extra structure.
  • Space complexity? Extra memory besides the input. Recursion depth counts. In-place reverse is O(1) extra; generating a new array is O(n).
Senior bar: After coding, state time and space, then say what you would change if n were 10⁸ or if you were memory-constrained. That is the Atlassian-style trade-off sentence.

2. Arrays

What it is. A contiguous (or contiguous-feeling) indexed sequence. In JavaScript, Array is a specialized object with a length and index keys; for interview purposes treat it as a dynamic array with O(1) index and O(1) amortized push.

When to use it. Order matters, you need random access, or you will scan linearly. Most interview inputs start as arrays.

Mental model. Index is an address. You can jump to a[i] instantly, but inserting at the front shifts everyone — O(n).

Common patterns. Prefix/suffix passes, in-place two-pointer writes, treating the array as a hash via index (cyclic sort / marking), 2D grids as arrays of arrays.

When not to use it. You need O(1) insert/delete in the middle (use a list or map). You need ordered keys (use a tree / sort once). You need uniqueness with no order (use Set).

Complexity. Index O(1). Scan O(n). Unshift/splice-at-0 O(n). Sort O(n log n).

TypeScript
// In-place compact: write unique values forward
function compactSorted(a: number[]): number {
  if (a.length === 0) return 0;
  let w = 1;
  for (let r = 1; r < a.length; r++) {
    if (a[r] !== a[w - 1]) a[w++] = a[r];
  }
  return w;
}

Common mistakes. Off-by-one on i < n vs i <= n-1. Mutating while iterating. Assuming sort() is numeric (it is lexicographic unless you pass a comparator).

Edge cases. Empty array, single element, all duplicates, already sorted, integer overflow if you ever used 32-bit (JS number is IEEE-754; still mention overflow if the prompt is language-agnostic).

3. Strings

What it is. An immutable sequence of UTF-16 code units in JavaScript. s[i] and s.length are fine for interview ASCII/Unicode-BMP problems. Grapheme clusters (emoji) are almost never the point in DSA rounds.

When to use string-specific thinking. Anagrams, palindromes, windows over characters, parsing, run-length, prefix/suffix of words.

Mental model. A string is an array of characters you cannot mutate. Building with += in a loop can be O(n²) in naive implementations; prefer array.push then join('') when constructing large strings.

Common patterns. Frequency maps of 26 letters, sliding window on unique chars, two pointers from ends, sort-as-key for anagrams, KMP/Z only if they explicitly want it (rare at Atlassian).

When not. Do not explode a string into recursion without a bound. Do not use regex as a substitute for a linear scan in an interview unless it clarifies parsing.

TypeScript
function isPalindrome(s: string): boolean {
  const t = s.toLowerCase().replace(/[^a-z0-9]/g, "");
  let i = 0, j = t.length - 1;
  while (i < j) {
    if (t[i] !== t[j]) return false;
    i++; j--;
  }
  return true;
}

Mistakes. Forgetting case/punctuation in palindromes. Using sort on strings of length n inside an O(n) loop (becomes O(n² log n)). Confusing index of a character with its code.

4. HashMap

What it is. An associative array: key → value with expected O(1) get/set/delete. In JS: Map (any key, insertion order) or object (string/symbol keys). Prefer Map in TypeScript interviews unless you need a JSON object.

Why it helps. It turns “have I seen this before?” from a scan (O(n)) into a lookup (O(1)). That is the most common Easy→Medium upgrade in screening interviews.

When to use it. Complements (Two Sum), grouping (anagrams), counting (top K), last-seen index (longest unique substring), prefix-sum complements (subarray sum K), graph adjacency.

Mental model. Hash the key, land in a bucket, compare. You pay memory to buy time. If you cannot define a stable key (e.g. unsorted list as key), the map will not save you until you canonicalize.

When it breaks down. Keys that are mutable and then mutated. Huge key spaces you cannot afford to store. Need for ordered range queries (use sort + two pointers or a tree). Need for “next greater” (stack) rather than “have I seen.”

Complexity. Average O(1) per op, O(n) space. Worst O(n) per op theoretically.

TypeScript
function twoSum(nums: number[], target: number): [number, number] {
  const seen = new Map<number, number>(); // value → index
  for (let i = 0; i < nums.length; i++) {
    const want = target - nums[i];
    const j = seen.get(want);
    if (j !== undefined) return [j, i];
    seen.set(nums[i], i);
  }
  throw new Error("no pair");
}

Interview recognition. Words like “pair,” “complement,” “group,” “count,” “last index,” “first unique,” “is there a previous value that…”

Mistakes. Using the object itself as a key without canonicalization. Forgetting that object keys stringify. Overwriting an index you still needed (Two Sum: store after lookup).

5. Set

What it is. A HashMap that only stores keys. JS Set has O(1) average has/add/delete and insertion order.

When to use it. Dedup, membership, “start of a sequence” tests (Longest Consecutive), visited nodes in a graph when you do not need extra payload.

When not. You need the associated value (use Map). You need the k-th smallest (use sort/heap). You need multiset counts (use Map).

TypeScript
function hasDuplicate(nums: number[]): boolean {
  const s = new Set<number>();
  for (const x of nums) {
    if (s.has(x)) return true;
    s.add(x);
  }
  return false;
}

Trap. new Set(nums).size !== nums.length is a valid one-liner for duplicates, but say the O(n) time / O(n) space out loud. Sorting first is O(n log n) time, O(1) extra if in-place — mention that trade-off.

6. Two Pointers

What it is. Two indices moving through a sequence under an invariant, usually toward each other or in the same direction at different speeds.

When to use it. Sorted arrays (Two Sum II, 3Sum). Palindromes. In-place partitioning. Fast/slow on lists. Container-with-water (greedy move of the shorter side).

Mental model. Each move must discard a region that cannot contain a better answer. If you cannot justify the discard, you do not have a two-pointer proof — you have a hope.

When not. Unsorted pair-sum without extra memory (need HashMap or sort first). Non-monotonic constraints where moving a pointer can skip the optimum.

Complexity. Typically O(n) after an O(n log n) sort, O(1) extra.

TypeScript
function maxArea(h: number[]): number {
  let i = 0, j = h.length - 1, best = 0;
  while (i < j) {
    best = Math.max(best, Math.min(h[i], h[j]) * (j - i));
    if (h[i] < h[j]) i++; else j--; // shorter line cannot win later with this partner
  }
  return best;
}

Mistakes. Forgetting to skip duplicates in 3Sum. Moving both pointers in one step and skipping the answer. Using two pointers on unsorted data and claiming O(n).

7. Sliding Window

What it is. A contiguous segment [left, right] that you expand and shrink so that a constraint stays valid. The window only moves forward — each index enters and leaves at most once.

When to use it. Longest/shortest subarray or substring with a constraint: at most K distinct, no repeats, sum ≥ target, contains all chars of t, anagram of p.

Mental model / invariant. After every right++, repair the window with left++ until it is valid (or until it is minimal-valid, depending on the problem). The invariant is “window always represents the best candidate ending at right” or “window is the smallest valid covering right.”

When not. Subarrays that are not contiguous. Constraints that are not repairable by moving left (e.g. arbitrary subset sum — that is DP or prefix+map). Need the actual subarray list of all answers that overlap in complex ways.

Complexity. O(n) time, O(Σ) space for the alphabet or the map of counts.

TypeScript
function lengthOfLongestSubstring(s: string): number {
  const last = new Map<string, number>();
  let left = 0, best = 0;
  for (let r = 0; r < s.length; r++) {
    const prev = last.get(s[r]);
    if (prev !== undefined && prev >= left) left = prev + 1;
    last.set(s[r], r);
    best = Math.max(best, r - left + 1);
  }
  return best;
}

Mistakes. Updating left incorrectly when a character was seen before the window. Forgetting to count “need” vs “have” in min-window. Using a nested O(n) shrink that rescans instead of O(1) updates.

8. Prefix Sum

What it is. Precompute pref[i] = a[0]+…+a[i-1] so any range sum is pref[r]-pref[l] in O(1). The 2D analog is a summed-area table.

When to use it. Many range-sum queries. “How many subarrays sum to K” (map of prefix frequencies). Equilibrium / pivot index. Difference arrays for range updates (inverse idea).

Mental model. A subarray sum is the difference of two prefixes. If you need pref[r] - pref[l] = K, then pref[l] = pref[r] - K — look that up in a map.

When not. You need min/max of a range with updates (segment tree — out of Phase 1 scope). The constraint is about distinct characters (window), not sums.

TypeScript
function subarraySum(nums: number[], k: number): number {
  const freq = new Map<number, number>([[0, 1]]);
  let pref = 0, ans = 0;
  for (const x of nums) {
    pref += x;
    ans += freq.get(pref - k) ?? 0;
    freq.set(pref, (freq.get(pref) ?? 0) + 1);
  }
  return ans;
}

Trap. Initialize the map with prefix 0 seen once — the subarray that starts at index 0. Negative numbers make sliding window on sums invalid; prefix+map still works.

9. Stack

What it is. LIFO. JS array push/pop. The algorithmic power is monotonic stacks: keep indices in increasing or decreasing order of values so the top is the previous candidate.

When to use it. Parentheses / path simplification. Calculator / RPN. Next greater/smaller element. Histogram rectangle. Nested structures (HTML-ish, file paths). Undo.

When not. You need the oldest item first (queue/BFS). You need random access to the middle.

TypeScript
function dailyTemperatures(t: number[]): number[] {
  const ans = Array(t.length).fill(0);
  const st: number[] = []; // indices, temps decreasing
  for (let i = 0; i < t.length; i++) {
    while (st.length && t[i] > t[st[st.length - 1]]) {
      const j = st.pop()!;
      ans[j] = i - j;
    }
    st.push(i);
  }
  return ans;
}

Complexity. Each index pushed/popped once → O(n).

Mistakes. Storing values instead of indices when you need distance. Popping the equality case incorrectly on histogram.

10. Queue

What it is. FIFO. In JS interviews, use an array with a read index (head++) or a circular buffer. shift() is O(n) — mention that and avoid it on large queues.

When to use it. BFS, sliding-window maximum (deque), task scheduling, level-order trees, multi-source infection (oranges).

When not. DFS/recursion already gives you a stack. You need priority (heap), not arrival order.

TypeScript
class Queue<T> {
  private a: T[] = [];
  private h = 0;
  push(x: T) { this.a.push(x); }
  shift(): T | undefined {
    if (this.h >= this.a.length) return undefined;
    const v = this.a[this.h++];
    if (this.h > 32 && this.h * 2 > this.a.length) {
      this.a = this.a.slice(this.h); this.h = 0;
    }
    return v;
  }
  get length() { return this.a.length - this.h; }
}

11. Binary Search

What it is. Repeatedly cut a monotonic search space in half. The space can be indices of a sorted array, or the space of answers (minimum speed, minimum capacity) when feasible(x) is monotonic.

Mental model. Maintain an invariant: the answer lives in [lo, hi]. After testing mid, discard the half that cannot contain it. Overflow-safe mid: lo + ((hi-lo)>>1) (JS numbers are floats; still a good habit).

When not. The predicate is not monotonic (“exists a subarray of length k with property that is not monotone in k”). Unsorted data with no other structure.

TypeScript
function firstTrue(n: number, ok: (x: number) => boolean): number {
  let lo = 0, hi = n; // answer in [0, n]
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (ok(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

Interview questions. Why O(log n)? What if duplicates? How do you search a rotated array? How do you binary-search the answer for Koko?

Mistakes. Infinite loops from lo = mid when lo and hi are adjacent. Off-by-one on “insert position.” Forgetting the array must be sorted (or the predicate monotone).

12. Linked List

What it is. Nodes with val and next (sometimes prev). O(1) insert/delete given a pointer; O(n) access by index.

When to use list thinking. Reverse, merge, cycle, reorder, add-two-numbers, remove nth from end. LRU uses a doubly linked list + HashMap (see exercises).

Mental model. Draw boxes and arrows. Use a dummy head so the first node is not special. Keep a prev when you will relink.

TypeScript
class ListNode {
  val: number;
  next: ListNode | null;
  constructor(val = 0, next: ListNode | null = null) {
    this.val = val; this.next = next;
  }
}
function reverseList(head: ListNode | null): ListNode | null {
  let prev: ListNode | null = null, cur = head;
  while (cur) {
    const nxt = cur.next;
    cur.next = prev;
    prev = cur;
    cur = nxt;
  }
  return prev;
}

Mistakes. Losing next before rewiring. Off-by-one on n-from-end. Detecting a cycle but not the start (Phase 1: detecting is enough unless asked).

13. Trees

What it is. Hierarchical nodes. Interview default: binary tree with left/right. Recursion matches the structure: solve children, combine.

Mental model. Each call has a job (preorder work), delegates, then combines (postorder work). Height is 1+max(child heights). Diameter is max of left-height+right-height over all nodes.

Traversals. Preorder (node, L, R), inorder (L, node, R), postorder (L, R, node), level-order (BFS queue).

TypeScript
function maxDepth(root: TreeNode | null): number {
  if (!root) return 0;
  return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
}

Complexity. Visit each node once: O(n) time, O(h) stack space (h = height; worst n, balanced log n).

When not to recurse blindly. Skewed trees of 10⁵ nodes can overflow the JS stack. Mention converting to explicit stack if asked about production limits.

14. Binary Search Trees

What it is. For every node, left subtree < node < right subtree (or ≤, confirm duplicates policy). Inorder traversal is sorted.

When the BST property matters. Validate BST (need bounds, not just “left < node < right”). LCA: walk down, going left/right together. Kth smallest: inorder count. Search/insert/delete in O(h).

When not. An ordinary binary tree question (invert, diameter) does not use BST order. Using a BST to get O(log n) in an interview is rare unless you implement it; usually you sort or hash instead.

TypeScript
function isValidBST(root: TreeNode | null, lo = -Infinity, hi = Infinity): boolean {
  if (!root) return true;
  if (root.val <= lo || root.val >= hi) return false;
  return isValidBST(root.left, lo, root.val) && isValidBST(root.right, root.val, hi);
}

Trap. Checking only immediate children accepts invalid trees (e.g. right-left grandchild too small).

15. DFS

What it is. Go deep before wide. Recursion or explicit stack. On grids: flood fill. On graphs: color states (unseen / visiting / done) to detect cycles.

When to use it. Connected components (islands), existence paths, topological sort (DFS finish times), tree problems, backtracking (subsets/permutations — light touch in Phase 1).

When not. Shortest path in an unweighted graph (BFS). You need level-by-level time (oranges).

TypeScript
function numIslands(grid: string[][]): number {
  const rows = grid.length, cols = grid[0]?.length ?? 0;
  const dfs = (r: number, c: number) => {
    if (r < 0 || c < 0 || r >= rows || c >= cols || grid[r][c] !== "1") return;
    grid[r][c] = "0";
    dfs(r + 1, c); dfs(r - 1, c); dfs(r, c + 1); dfs(r, c - 1);
  };
  let n = 0;
  for (let r = 0; r < rows; r++)
    for (let c = 0; c < cols; c++)
      if (grid[r][c] === "1") { n++; dfs(r, c); }
  return n;
}

Mistakes. Not marking visited before recursing (infinite loops). Forgetting all four directions. Mutating input without asking (say you will restore or copy if they care).

16. BFS

What it is. Explore by distance from the source using a queue. First time you reach a node is the shortest path in an unweighted graph.

When to use it. Level order. Shortest path (word ladder, maze). Multi-source (oranges: all rotten start at once). Bipartite check. Clone graph (also DFS + map).

TypeScript
function orangesRotting(grid: number[][]): number {
  const q: [number, number][] = [];
  let fresh = 0, minutes = 0;
  for (let r = 0; r < grid.length; r++)
    for (let c = 0; c < grid[0].length; c++) {
      if (grid[r][c] === 2) q.push([r, c]);
      if (grid[r][c] === 1) fresh++;
    }
  const dirs = [[1,0],[-1,0],[0,1],[0,-1]];
  let head = 0;
  while (head < q.length && fresh) {
    const size = q.length - head;
    for (let s = 0; s < size; s++) {
      const [r, c] = q[head++];
      for (const [dr, dc] of dirs) {
        const nr = r + dr, nc = c + dc;
        if (grid[nr]?.[nc] === 1) {
          grid[nr][nc] = 2; fresh--; q.push([nr, nc]);
        }
      }
    }
    minutes++;
  }
  return fresh ? -1 : minutes;
}

Mistakes. Not processing level size when you need minutes. Using shift() in a tight loop. Forgetting multi-source initialization.

17. Heap / Priority Queue

What it is. A binary heap gives O(log n) push/pop and O(1) peek of min or max. JavaScript has no built-in heap; in interviews you may (1) sort O(n log n) when n is small, (2) implement a tiny binary heap, (3) say “I would use a PriorityQueue” and write the API. For Phase 1, implement a min-heap of ~30 lines or sort when K is unconstrained.

When to use it. Top K, running median (two heaps), merge K lists, scheduling by time, “always take the current best.”

When not. You need the full sort anyway. K = n. You only need min/max of a static array (one pass).

TypeScript
class MinHeap {
  a: number[] = [];
  size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x: number) {
    this.a.push(x); this.up(this.a.length - 1);
  }
  pop(): number {
    const top = this.a[0], last = this.a.pop()!;
    if (this.a.length) { this.a[0] = last; this.down(0); }
    return top;
  }
  private up(i: number) {
    while (i) {
      const p = (i - 1) >> 1;
      if (this.a[p] <= this.a[i]) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]]; i = p;
    }
  }
  private down(i: number) {
    for (;;) {
      let s = i, l = i * 2 + 1, r = l + 1;
      if (l < this.a.length && this.a[l] < this.a[s]) s = l;
      if (r < this.a.length && this.a[r] < this.a[s]) s = r;
      if (s === i) break;
      [this.a[s], this.a[i]] = [this.a[i], this.a[s]]; i = s;
    }
  }
}

Top K pattern. Keep a min-heap of size K of the largest items seen: if heap.size < K or x > peek, push and maybe pop. That is O(n log K).

  • HashMap get: expected O(1), worst O(n), space O(n).

function minSubArrayLen(target: number, nums: number[]): number {
  let left = 0, sum = 0, best = Infinity;
  for (let r = 0; r < nums.length; r++) {
    sum += nums[r];
    while (sum >= target) {
      best = Math.min(best, r - left + 1);
      sum -= nums[left++];
    }
  }
  return best === Infinity ? 0 : best;
}

function search(a: number[], t: number): number {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    const m = (lo + hi) >> 1;
    if (a[m] === t) return m;
    if (a[m] < t) lo = m + 1;
    else hi = m - 1;
  }
  return -1;
}

function levelOrder(root: TreeNode | null): number[][] {
  if (!root) return [];
  const out: number[][] = [], q = [root];
  let h = 0;
  while (h < q.length) {
    const n = q.length - h, row: number[] = [];
    for (let i = 0; i < n; i++) {
      const node = q[h++];
      row.push(node.val);
      if (node.left) q.push(node.left);
      if (node.right) q.push(node.right);
    }
    out.push(row);
  }
  return out;
}

function canFinish(n: number, edges: number[][]): boolean {
  const g: number[][] = Array.from({ length: n }, () => []);
  for (const [a, b] of edges) g[b].push(a);
  const st = Array(n).fill(0); // 0 unseen, 1 visiting, 2 done
  const dfs = (u: number): boolean => {
    if (st[u] === 1) return false;
    if (st[u] === 2) return true;
    st[u] = 1;
    for (const v of g[u]) if (!dfs(v)) return false;
    st[u] = 2;
    return true;
  };

  return true;
}

function diameterOfBinaryTree(root: TreeNode | null): number {
  let best = 0;
  const height = (n: TreeNode | null): number => {

EASY hashmap-lookup arrays

Two Sum

Why this problem matters. The canonical HashMap complement problem. If you cannot do this in 8 minutes with a clean explanation, you are not ready for a screen.

Problem (original summary). Given integers nums and a target, return any two distinct indices i, j such that nums[i] + nums[j] equals target. Exactly one solution exists.

Example. Input: nums = [2,7,11,15], target = 9 → Output: [0,1].

Constraints (typical). 2 ≤ n ≤ 10^4; values and target typically in 32-bit range.

For each value x, you need target − x. Have you already seen that complement?

Brute force. Try every pair (i, j), i < j. O(n²) time, O(1) space.

Optimal approach. One pass Map from value → index. Before inserting nums[i], look up target − nums[i].

Step-by-step reasoning. i=0: 2, need 7, miss, store 2→0. i=1: 7, need 2, found at 0. Return [0,1]. Storing after the lookup allows using each index once.

Time / space. O(n) time expected, O(n) space.

Common mistakes. Two-pass that accidentally uses the same index twice. Sorting and losing original indices.

Edge cases. Negatives; pair at the ends; duplicate values that sum to target (e.g. [3,3], 6).

Follow-ups. Return all pairs? 3Sum? What if the array is sorted? (two pointers, O(1) extra).

Interviewer discussion. I would mention the sort+two-pointer trade-off if memory were tighter. I would not use a nested loop on 10^4 without commenting that it is a fallback.

TypeScript
function twoSum(nums: number[], target: number): [number, number] {
  const seen = new Map<number, number>();
  for (let i = 0; i < nums.length; i++) {
    const j = seen.get(target - nums[i]);
    if (j !== undefined) return [j, i];
    seen.set(nums[i], i);
  }
  throw new Error("no pair");
}

Group Anagrams

Why this problem matters. Canonical keys. Senior candidates pick a key that is O(L) not O(L log L) when the alphabet is small.

Problem (original summary). Group words that are anagrams of each other. Order of groups and words inside a group can be anything.

Example. Input: strs = ["eat","tea","tan","ate","nat","bat"] → Output: [["eat","tea","ate"],["tan","nat"],["bat"]].

Constraints (typical). n words, each length L; n*L up to ~10^4–10^5.

Two words are in the same group iff they share a canonical key: sorted string or count signature.

Brute force. For each word, compare to every group leader with an anagram check. O(n² L).

Optimal approach. Map from key → list. Key = sorted(word) O(L log L) or 26-count joined O(L).

Step-by-step reasoning. Choose a key function that is identical exactly for anagrams. Push each word into map[key]. Return Object.values.

Time / space. O(n L log L) with sort keys, or O(n L) with count keys. Space O(n L).

Common mistakes. Using the word itself as the key. Mutating the original strings.

Edge cases. Empty string word; all unique; all one group.

Follow-ups. Very large alphabet? Need a hash of counts instead of a string key.

Interviewer discussion. I would write the sort key first (clear), then mention the count signature if they want tighter time.

function groupAnagrams(strs: string[]): string[][] {
  const map = new Map<string, string[]>();
  for (const w of strs) {
    const key = w.split("").sort().join("");
    const bucket = map.get(key);
    if (bucket) bucket.push(w);
    else map.set(key, [w]);
  }
  return [...map.values()];
}

Why this problem matters. Count then select. Teaches heap-of-size-K vs bucket sort vs full sort.

Problem (original summary). Return the k values that appear most often. Order among the k does not matter.

Example. Input: nums = [1,1,1,2,2,3], k = 2 → Output: [1,2].

Constraints (typical). k is in [1, number of unique values]; n up to 10^5.

  const freq = new Map<number, number>();
  for (const x of nums) freq.set(x, (freq.get(x) ?? 0) + 1);

Product of Array Except Self

Why this problem matters. Prefix/suffix without the division cop-out. Tests whether you can do two passes cleanly.

Problem (original summary). Return answer[i] = product of all nums[j] for j ≠ i. Do not use division. O(n) time.

Example. Input: nums = [1,2,3,4] → Output: [24,12,8,6].

Constraints (typical). n ≥ 2; values may include 0 (one zero or many zeros changes the pattern).

answer[i] = (product of left of i) × (product of right of i).

Brute force. For each i multiply the rest. O(n²). Division by nums[i] fails when zeros exist and is disallowed.

Optimal approach. First pass: answer[i] = left product. Second pass: multiply a running right product.

Step-by-step reasoning. Left: ans[0]=1, ans[i]=ans[i-1]*nums[i-1]. Right: r=1, for i from n-1..0: ans[i]*=r; r*=nums[i].

Time / space. O(n) time, O(1) extra if the output array does not count.

Common mistakes. Using division. Off-by-one on left[i]. Not handling zeros if you took the division path.

function threeSum(nums: number[]): number[][] {
  nums.sort((a, b) => a - b);
  const out: number[][] = [];
  for (let i = 0; i < nums.length - 2; i++) {
    if (i && nums[i] === nums[i - 1]) continue;
    let L = i + 1, R = nums.length - 1;
    while (L < R) {
      const s = nums[i] + nums[L] + nums[R];
      if (s === 0) {
        out.push([nums[i], nums[L], nums[R]]);
        L++; R--;
        while (L < R && nums[L] === nums[L - 1]) L++;
        while (L < R && nums[R] === nums[R + 1]) R--;
      } else if (s < 0) L++;
      else R--;
    }
  }
  return out;
}

function evalRPN(tokens: string[]): number {
  const st: number[] = [];
  for (const t of tokens) {
    if (t === "+" || t === "-" || t === "*" || t === "/") {
      const b = st.pop()!, a = st.pop()!;

function buildTree(preorder: number[], inorder: number[]): TreeNode | null {

class MedianFinder {
  data: number[] = [];
  addNum(x: number) {
    const a = this.data;
    let lo = 0, hi = a.length;
    while (lo < hi) {
      const m = (lo + hi) >> 1;
      if (a[m] <= x) lo = m + 1; else hi = m;
    }
    a.splice(lo, 0, x);
  }
  findMedian(): number {
    const a = this.data, n = a.length;
    return n % 2 ? a[n >> 1] : (a[n / 2 - 1] + a[n / 2]) / 2;
  }
}

  if (!node) return null;

function orangesRotting(grid: number[][]): number {
  const R = grid.length, C = grid[0].length, q: [number, number][] = [];
  let fresh = 0, mins = 0, h = 0;
  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++) {
      if (grid[r][c] === 2) q.push([r, c]);
      if (grid[r][c] === 1) fresh++;
    }
  const dirs = [[1, 0], [-1, 0], [0, 1], [0, -1]];
  while (h < q.length && fresh) {
    const size = q.length - h;
    for (let i = 0; i < size; i++) {
      const [r, c] = q[h++];
      for (const [dr, dc] of dirs) {
        const nr = r + dr, nc = c + dc;
        if (grid[nr]?.[nc] === 1) {
          grid[nr][nc] = 2; fresh--; q.push([nr, nc]);
        }
      }
    }
    mins++;
  }
  return fresh ? -1 : mins;
}

function pacificAtlantic(h: number[][]): number[][] {

  const pac = Array.from({ length: R }, () => Array(C).fill(false));
  const atl = Array.from({ length: R }, () => Array(C).fill(false));
  const dirs = [[1, 0], [-1, 0], [0, 1], [0, -1]];

    return s;
  };
  const seen = new Set<number>();

function merge(intervals: number[][]): number[][] {
  intervals.sort((a, b) => a[0] - b[0]);
  const out: number[][] = [intervals[0].slice()];
  for (let i = 1; i < intervals.length; i++) {
    const last = out[out.length - 1], [s, e] = intervals[i];
    if (s <= last[1]) last[1] = Math.max(last[1], e);

function insert(intervals: number[][], nw: number[]): number[][] {
  const out: number[][] = [];
  let i = 0, n = intervals.length;
  while (i < n && intervals[i][1] < nw[0]) out.push(intervals[i++]);
  while (i < n && intervals[i][0] <= nw[1]) {

function spiralOrder(a: number[][]): number[] {
  const out: number[] = [];
  let t = 0, b = a.length - 1, l = 0, r = a[0].length - 1;
  while (t <= b && l <= r) {
    for (let j = l; j <= r; j++) out.push(a[t][j]); t++;
    for (let i = t; i <= b; i++) out.push(a[i][r]); r--;
    if (t <= b) { for (let j = r; j >= l; j--) out.push(a[b][j]); b--; }
    if (l <= r) { for (let i = b; i >= t; i--) out.push(a[i][l]); l++; }
  }
  return out;
}

function exist(board: string[][], word: string): boolean {
  const R = board.length, C = board[0].length;
  const dfs = (r: number, c: number, k: number): boolean => {
    if (k === word.length) return true;
    if (r < 0 || c < 0 || r >= R || c >= C || board[r][c] !== word[k]) return false;
    const ch = board[r][c]; board[r][c] = "#";
    const ok = dfs(r+1,c,k+1) || dfs(r-1,c,k+1) || dfs(r,c+1,k+1) || dfs(r,c-1,k+1);
    board[r][c] = ch;
    return ok;
  };
  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++)
      if (dfs(r, c, 0)) return true;
  return false;
}

Runtime fundamentals

JavaScript is single-threaded at the language level: one call stack runs one piece of your code at a time. Concurrency comes from the host (browser or Node) which owns Web APIs / libuv, queues, and the event loop.

Execution context

Every time you enter a function (or the script), the engine creates an execution context: a box that holds a lexical environment (scope), a this binding (for non-arrows), and a pointer to the current instruction. The global execution context (GEC) is created first and lives until the page / process dies.

Call stack

Contexts are stacked. A calls B calls C: C is on top, then B, then A, then GEC. return or a throw pops. Stack overflow is this structure growing without bound (unbounded recursion).

Heap

Objects, closures, and most arrays live on the heap. The stack stores primitives and references to heap objects. When no reference remains, GC may reclaim the object — not instantly, and not if a closure or detached listener still points at it.

Event loop (browser) Call stack Heap +--------+ +----------+ | C() | | objects | | B() | | closures | | A() | | DOM ... | | GEC | +----------+ +--------+ Host: timers, fetch, DOM, rAF Microtask queue | Task queue

Lexical environment vs variable environment. ES spec: a function has a lexical environment (let/const/functions, and the outer pointer) and historically a variable environment for var. Mentally: var is function-scoped and hoisted as undefined; let/const are block-scoped and hoisted into the TDZ.

JavaScript
function outer(x) {
  const y = 2;          // in outer's lexical environment
  return function inner() {
    return x + y;       // inner's [[Environment]] points at outer's LE
  };
}
const f = outer(1);     // outer's frame is gone from the stack
f();                    // 3 — heap still holds {x:1, y:2} because f closed over it

Hoisting and the Temporal Dead Zone

Hoisting means the engine creates bindings before running the body. It does not mean values are available.

  • var x: binding exists in the function, initialized to undefined at instantiate time. Assignments stay in place.
  • let/const: binding exists in the block but is uninitialized until the declaration line. Access before that is a ReferenceError (TDZ).
  • Function declarations: fully initialized (the function object) in the scope. Callable above their line in the same scope (not inside a block in sloppy ways — prefer not to rely on block-level function hoisting).
  • Function expressions / arrows assigned to const: the name is in TDZ until the line runs.
JavaScript
console.log(a); // undefined
var a = 1;
console.log(b); // ReferenceError
let b = 2;
foo();          // works
function foo() {}
bar();          // TypeError: bar is not a function (bar is undefined)
var bar = function () {};

TDZ starts at the beginning of the block and ends when the initializer runs. const must have an initializer; let may not (then it becomes undefined after the line).

Interview trap: typeof undeclared is "undefined", but typeof of a let in TDZ throws. typeof is not always safe.

Closures

A closure is a function plus the lexical environment it was created in. It is not a special type — every function has an [[Environment]] slot. You observe a closure when the inner function outlives the stack frame that created it.

Why it matters in production. React function components close over props/state from the render that created them (stale closures). Module-level caches close over maps. Event handlers close over elements. Private state in factories is a closure, not a keyword.

JavaScript
function makeBank() {
  let balance = 0; // not reachable except via the returned methods
  return {
    deposit: (n) => { balance += n; },
    get: () => balance,
  };
}
const acct = makeBank();
acct.deposit(10);
acct.get(); // 10 — balance is heap-retained by the two methods

Loop trap. var i in a loop is one binding. All closures see the final i. let i creates a new binding per iteration.

Memory. If a long-lived function closes over a large object you no longer need, that object cannot be collected. Fix: null the reference, close over a smaller field, or unregister the handler. This is a real leak pattern in SPAs.

Prototype system

Every ordinary object has an internal [[Prototype]] (exposed as Object.getPrototypeOf / __proto__). Property lookup: own properties first, then walk the chain until null.

JavaScript
const proto = { greet() { return "hi " + this.name; } };
const user = Object.create(proto);
user.name = "Vi";
user.greet(); // "hi Vi" — greet found on proto, this is user
Object.getPrototypeOf(user) === proto; // true
user instanceof Object; // true — walks the chain to Object.prototype

instanceof checks whether Ctor.prototype is on the object's prototype chain. It can be fooled by realms (iframes) and by mutated .prototype.

Constructor functions vs class. class is mostly syntax: methods land on .prototype, constructor is the function, extends wires [[Prototype]] of both the constructor and the prototype object. Classes are strict and not callable without new.

JavaScript
class Animal {
  constructor(name) { this.name = name; }
  speak() { return this.name; }
}
class Dog extends Animal {
  speak() { return super.speak() + " woof"; }
}
const d = new Dog("Rex");
d.speak();
Object.getPrototypeOf(d) === Dog.prototype;
Object.getPrototypeOf(Dog.prototype) === Animal.prototype;
Object.getPrototypeOf(Dog) === Animal; // constructor inheritance

Object.create(null) is a dictionary with no prototype — useful to avoid toString key collisions. Prefer Map in modern TS.

Async JavaScript: promises and await

A Promise is a thenable state machine: pending → fulfilled or rejected, then frozen. then/catch/finally schedule microtasks. The host (timers, I/O) schedules tasks.

What await does. await x wraps x in Promise.resolve, suspends the async function (returns a pending promise to the caller), and resumes the rest of the function as a microtask when x settles. It does not block the thread. Other tasks and microtasks can run while you are awaiting.

JavaScript
async function sample() {
  const a = await 1;          // microtask resume, a === 1
  const b = await Promise.resolve(2);
  return a + b;
}
sample().then(console.log);   // schedules more microtasks
console.log("sync");          // runs first
HelperBehavior
Promise.allFulfill when all fulfill; reject on first reject; [] → [] immediately
allSettledWait for all; never rejects for child rejects
raceFirst settle wins (fulfill or reject)
anyFirst fulfill wins; reject AggregateError if all reject

Long then chains are hard to debug and can hide sequential waterfalls that should have been Promise.all. Prefer async/await plus explicit concurrency.

Browser rendering pipeline

A frame is approximately: process input → JS → style → layout (reflow) → paint → composite. The compositor can move already-painted layers on the GPU (transform/opacity) without layout.

  • Style: compute computed styles (CSSOM + DOM).
  • Layout: geometry. Reading offsetHeight, getBoundingClientRect, scrollTop can flush pending layout (layout thrashing if you interleave writes and reads).
  • Paint: fill pixels for layers.
  • Composite: stitch layers.

requestAnimationFrame(cb) runs cb before the next paint, so visual updates stay vsynced. It is not a timer. Long tasks (>50ms) block input and rendering — split work, use workers, debounce handlers.

Forced reflow example: in a loop, set el.style.width then read el.offsetWidth. Batch writes, then read once.

Memory and leaks

JS engines use generational mark-and-sweep / tracing GC. You do not free objects. You drop references.

Leak patterns that show up in React/Node interviews:

  • Forgotten addEventListener / setInterval after unmount.
  • Detached DOM nodes still referenced from a JS cache or closure.
  • Global caches that grow without eviction (unbounded Map).
  • Closures holding the entire props object when they needed one field.
  • Console logging large objects in DevTools (retains them).
  • Unbounded Promise chains or queues in a worker.

Debug: Memory panel heap snapshots, comparison after a suspected interaction, look for Detached HTMLElement and growing retainer paths. WeakMap/WeakRef when the cache should not own the key.

Advanced language features

Iterators. An object with next() → { value, done }. Iterables have [Symbol.iterator](). for...of, spread, and destructuring use this protocol. Arrays are iterable; objects are not unless you define it.

Generators. function* returns a generator. yield pauses. Useful for lazy sequences and cooperative cancellation. async function* yields promises.

Symbols. Unique keys. Well-known symbols (Symbol.iterator, toStringTag) hook the language. They are not copied by JSON.stringify.

WeakMap / WeakSet. Keys (WM) / values (WS objects) are weakly held. Not enumerable. Use for private metadata on objects you do not own, or caches that should die with the key.

Proxy / Reflect. Intercept get/set/apply/etc. Reflect is the default-behavior twin so you can forward traps correctly. Use cases: observable state, validation, negative-index arrays. Cost: they are slower and debugging is harder — do not sprinkle them everywhere.

JavaScript
const wm = new WeakMap();
function tag(el, meta) { wm.set(el, meta); }
function getTag(el) { return wm.get(el); } // dies with el

const handler = {
  get(t, p, r) { return Reflect.get(t, p, r); },
  set(t, p, v, r) { return Reflect.set(t, p, v, r); },
};
const proxied = new Proxy({ x: 1 }, handler);

The strongest JS section

Event Loop — Beginner to Advanced

If you can narrate the queues, you will beat most senior frontend candidates who only have a slogan (“JS is async”). Draw this on a whiteboard in every mock.

The pieces

  • Call stack — currently running JS. Nothing else in your JS runs until this is empty (except workers).
  • Heap — objects. Not a queue.
  • Web APIs / host — setTimeout, fetch, DOM events, Node I/O. They complete off-stack, then enqueue a callback.
  • Task queue (macrotasks): timer callbacks, message events, I/O, rendering-related tasks. One task per turn.
  • Microtask queue: Promise jobs, queueMicrotask, MutationObserver. Drain the entire queue whenever the stack is empty, before the next task, and after every task.
  • Rendering — opportunity between tasks (not between microtasks). Infinite microtasks starve rendering and input (the “microtask death loop”).
while (eventLoopAlive) { const task = taskQueue.takeNext(); // one macrotask run(task); while (microtaskQueue.nonEmpty()) { // ALL of them run(microtaskQueue.takeNext()); } if (needsRendering && frameDue) { runRAFCallbacks(); style / layout / paint / composite } }

Exact ordering you should recite

  1. Run synchronous script / current function to completion.
  2. If the stack is empty, run all microtasks (including ones those microtasks enqueue).
  3. Take the oldest task. Run it. Go to 2.
  4. The browser may render if a frame is due and you are not starving it with microtasks.
Promise callbacks are not “async magic.” They are jobs on a queue with a higher priority than timer tasks. await is syntax for “return to the caller and resume this function as a job when the thenable settles.”

1. Classic timeout vs promise

console.log("D");

Answer. A D C B

Queue execution. Sync: A, schedule timer task, schedule microtask C, D. Stack empty → drain microtasks (C) → next task (B).

Why. Promise.then is a microtask. setTimeout(0) is a task (macrotask). Microtasks run before the next task.

Common misconception. Thinking setTimeout(0) runs before promises because 0 means now.

Queue execution. S sync. Microtask P1 runs, its then queues P2 still as a microtask. Drain P2. Then T.

beginner closures Q1

1. What is a closure?

Short answer. A function bundled with the lexical environment in which it was created.

Detailed explanation. Every function has an [[Environment]] pointer. When that function is invoked later, free variables resolve through that chain — even if the outer stack frame is gone. Closures are how JS implements private state, partial application, and React hooks' remembered callbacks.

Short answer. Where a name resolves is determined by where the function is written, not where it is called.

Implement debounce

Requirements. debounce(fn, wait) returns a function that delays fn until wait ms have passed without another call. Include cancel() if you can.

Starter.

TypeScript
function debounce<T extends (...a: any[]) => void>(fn: T, wait: number): T & { cancel(): void } {
  // TODO
}

Expected behavior. Rapid calls at t=0,10,20 with wait=50 → fn runs once around t=70 with the last args.

Hints. Store a timer id. On each call, clearTimeout and setTimeout. Preserve this and args.

TypeScript
function debounce<T extends (...a: any[]) => void>(fn: T, wait: number) {
  let t: ReturnType<typeof setTimeout> | undefined;
  const wrapped = function (this: unknown, ...args: Parameters<T>) {
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), wait);
  };
  wrapped.cancel = () => clearTimeout(t);
  return wrapped as T & { cancel(): void };
}

Explanation. Trailing debounce is a closure over timer + last this/args. Leading fires immediately then ignores until quiet.

Complexity. O(1) per call besides the scheduled fn.

Follow-up interview questions. Leading vs trailing. maxWait (lodash). React: cancel on unmount.

Implement throttle

Requirements. throttle(fn, wait) ensures fn runs at most once per wait ms. Trailing call with last args is a nice extra.

Starter.

TypeScript
function throttle<T extends (...a: any[]) => void>(fn: T, wait: number): T {
  // TODO
}

Expected behavior. Calls every 10ms for 300ms with wait=100 → about 3–4 invocations, not 30.

Hints. Record lastRan. If now-lastRan >= wait, run. Else schedule a trailing timeout.

TypeScript
function throttle<T extends (...a: any[]) => void>(fn: T, wait: number) {
  let last = 0, t: ReturnType<typeof setTimeout> | undefined;
  return function (this: unknown, ...args: Parameters<T>) {
    const now = Date.now();
    const remaining = wait - (now - last);
    if (remaining <= 0) {
      clearTimeout(t); t = undefined;
      last = now; fn.apply(this, args);
    } else if (!t) {
      t = setTimeout(() => {
        last = Date.now(); t = undefined; fn.apply(this, args);
      }, remaining);
    }
  } as T;
}

Explanation. Throttle guarantees a maximum rate. Scroll/mousemove. Debounce waits for silence (search).

Complexity. O(1) per call.

Follow-up interview questions. leading:false. Difference vs debounce for scroll.

TypeScript
function memoize<T extends (...a: any[]) => any>(
  fn: T,
  key = (...a: any[]) => JSON.stringify(a)
): T {
  const cache = new Map<string, ReturnType<T>>();
  return function (this: unknown, ...args: Parameters<T>) {
    const k = key(...args);
    if (cache.has(k)) return cache.get(k)!;
    const v = fn.apply(this, args);

TypeScript
function promiseAll<T>(items: (T | Promise<T>)[]): Promise<T[]> {
  return new Promise((resolve, reject) => {
    const list = [...items];
    if (!list.length) { resolve([]); return; }
    const out: T[] = Array(list.length);
    let left = list.length;
    list.forEach((item, i) => {
      Promise.resolve(item).then((v) => {
        out[i] = v;
        if (--left === 0) resolve(out);
      }, reject);
    });
  });
}

Simplified Promise

Requirements. MiniPromise with then and a constructor (executor). Support resolve with a value (not thenable chaining if you need to cut scope).

Starter.

TypeScript
class MiniPromise {
  constructor(exec: (res: (v: unknown) => void, rej: (e: unknown) => void) => void) {}
  then(onF?: (v: unknown) => unknown, onR?: (e: unknown) => unknown): MiniPromise { throw 0; }
}

Expected behavior. new MiniPromise((r)=>r(1)).then(console.log) logs 1 as a microtask. Then is chainable at a basic level.

Hints. State pending|fulfilled|rejected. Queue reactions. Flush via queueMicrotask. then always returns a new MiniPromise.

TypeScript
type Handler = { onF?: (v: unknown) => unknown; onR?: (e: unknown) => unknown; resolve: (v: unknown) => void; reject: (e: unknown) => void };
class MiniPromise {
  private state: "pending" | "fulfilled" | "rejected" = "pending";
  private value: unknown;
  private q: Handler[] = [];
  constructor(exec: (res: (v: unknown) => void, rej: (e: unknown) => void) => void) {
    const settle = (st: "fulfilled" | "rejected", v: unknown) => {
      if (this.state !== "pending") return;
      this.state = st; this.value = v;
      queueMicrotask(() => this.flush());
    };
    try { exec((v) => settle("fulfilled", v), (e) => settle("rejected", e)); }
    catch (e) { settle("rejected", e); }
  }
  then(onF?: (v: unknown) => unknown, onR?: (e: unknown) => unknown) {
    return new MiniPromise((resolve, reject) => {
      this.q.push({ onF, onR, resolve, reject });
      if (this.state !== "pending") queueMicrotask(() => this.flush());
    });
  }
  private flush() {
    if (this.state === "pending") return;
    const jobs = this.q.splice(0);
    for (const h of jobs) {
      const fn = this.state === "fulfilled" ? h.onF : h.onR;
      try {
        if (!fn) (this.state === "fulfilled" ? h.resolve : h.reject)(this.value);
        else h.resolve(fn(this.value));
      } catch (e) { h.reject(e); }
    }
  }
}

Explanation. You are proving you understand jobs, immutability after settle, and that then always returns a new promise.

Complexity. Each then is O(1) enqueue.

Follow-up interview questions. Thenables. catch. finally. Unhandled rejection.

}

Expected behavior. on('x', fn); emit('x', 1) calls fn(1). off removes. once fires a single time.

TypeScript
class Emitter {
  private m = new Map<string, Function[]>();
  on(ev: string, fn: Function) {
    const a = this.m.get(ev) ?? [];
    a.push(fn); this.m.set(ev, a);
    return () => this.off(ev, fn);
  }
  off(ev: string, fn: Function) {
    const a = this.m.get(ev); if (!a) return;
    this.m.set(ev, a.filter((f) => f !== fn));
  }
  once(ev: string, fn: Function) {
    const wrap = (...a: unknown[]) => { this.off(ev, wrap); fn(...a); };
    this.on(ev, wrap);
  }
  emit(ev: string, ...args: unknown[]) {
    for (const fn of (this.m.get(ev) ?? []).slice()) fn(...args);
  }
}

Explanation. Pub/sub vs callbacks: many subscribers, lifecycle off, avoid tight coupling. Snapshot prevents skip/double bugs.

Complexity. emit O(listeners).

Follow-up interview questions. Wildcard events. Error in one listener (should others run?).

LRU cache

Requirements. capacity n. get(key) and put(key,val) O(1). Evict least recently used on overflow.

Starter.

class LRU {
  constructor(private cap: number) {}
  get(k: string): number | undefined { return; }
  put(k: string, v: number) {}
}

Expected behavior. cap 2: put a,b,c evicts a. get(b) then put d evicts c if b was refreshed.

Hints. Map insertion order in JS is LRU-friendly: delete+set moves to end. Evict map.keys().next().

TypeScript
class LRU {
  private map = new Map<string, number>();
  constructor(private cap: number) {}
  get(k: string) {
    if (!this.map.has(k)) return undefined;
    const v = this.map.get(k)!;
    this.map.delete(k); this.map.set(k, v);
    return v;
  }
  put(k: string, v: number) {
    if (this.map.has(k)) this.map.delete(k);
    this.map.set(k, v);
    if (this.map.size > this.cap) this.map.delete(this.map.keys().next().value!);
  }
}

Explanation. Frontend-adjacent: image caches, parsed module caches, in-memory API caches. Interviewers love Map order.

Complexity. O(1) average get/put.

Follow-up interview questions. TTL. Persistence. Why Map not object (order + any keys).

  let last: unknown;
  for (let i = 0; i <= opts.retries; i++) {
    try { return await fn(); }

      if (i === opts.retries) break;

    // TODO
  };
}

Expected behavior. n=2, five tasks of 50ms → ~150ms total, never 3 running.

Hints. active count + queue of resolve starters. After each finish, dequeue.

TypeScript
function limit(n: number) {
  let active = 0;
  const q: (() => void)[] = [];
  const next = () => { active--; q.shift()?.(); };
  return function <T>(task: () => Promise<T>): Promise<T> {
    return new Promise<T>((resolve, reject) => {
      const run = () => {
        active++;
        task().then(resolve, reject).finally(next);
      };
      if (active < n) run();
      else q.push(run);
    });
  };
}

Explanation. Browsers limit HTTP/2 streams; you still want app-level limits for fan-out fetches. Pair with Promise.all on the wrapped tasks.

Complexity. O(1) extra per task besides the queue.

Follow-up interview questions. Fairness. Priority. Abort queued work.

How you talk

Interview Communication Practice

Atlassian senior interviews grade how you think, not only the final code. Silence looks like stuck. Narration looks like leadership. Use this 10-step script until it is muscle memory.

1

Clarify requirements

“I’ll first clarify the constraints. Is the array sorted? Can values be negative? Should I return indices or values? What should I do if there is no answer — throw, null, or empty?”

Ask about duplicates, stability, mutation, integer overflow, and whether they want a function signature in TypeScript.

2

State assumptions

“I’ll assume inputs fit in memory, n can be 10⁵ so I need linear or n log n, and I may allocate O(n) extra unless you want in-place.”

Write assumptions at the top of the editor. If they are wrong, the interviewer will correct you now, not after 20 minutes.

3

Describe brute force

“The brute-force approach would be to try every pair. That is O(n²) time and O(1) extra. It’s correct, and I’d ship it if n were 20.”

Brute force proves you understand the problem. Seniors do not skip it; they dismiss it with a reason.

4

Identify the bottleneck

“The bottleneck is repeated lookup — for each i I rescan the rest of the array for the complement.”

Name the wasted work: repeated scans, repeated sorts, repeated height computations, single-source BFS that should have been multi-source.

5

Derive the optimal approach

“To reduce this from O(n²) to O(n), I’ll use a HashMap from value to index. As I scan, I ask whether target − x is already stored.”

Name the pattern. State the invariant in one sentence. If you cannot, you are not ready to code.

6

Explain the data structure

“Map gives expected O(1) get/set. I’ll mention worst-case O(n) if they care; in practice V8’s Map is fine. Space is O(n).”

If you choose a heap in JS, say you will sort if n is small, or implement a 30-line heap, or use a PriorityQueue API.

7

Code while communicating

“I’m creating the map. I’m looking up the complement before I insert so I don’t use the same index twice. I’ll name variables so you can read this without me.”

Do not go silent for five minutes. If you need quiet, say “I need 60 seconds to write the loop, then I’ll narrate.” Use TypeScript types as documentation.

8

Test edge cases

“Empty input — I’ll guard. Single element. Duplicates: [3,3] target 6. Negatives. Already-sorted. I’ll walk the example line by line.”

Dry-run the example they gave you. Then one mean case. Fix bugs before they point them out.

9

Explain complexity

“Time O(n) expected, space O(n). If memory were tight I would sort and two-pointer in O(n log n) time and O(1) extra, but I’d lose original indices unless I store pairs.”

10

Discuss alternatives

“I could binary-search each complement after sorting — worse. I could use two pointers if you allowed me to sort. In production I would extract the map into a well-named helper and add a test for the duplicate-index case.”

This is the senior beat: trade-offs, testability, what you would not do.

Two Sum — full spoken script (practice this verbatim once)

“I’ll first clarify: return any valid pair of indices? Are there negatives? Exactly one solution — good. I won’t mutate the input. Brute force is nested loops, O(n²). The bottleneck is scanning for the complement. I’ll keep a Map from value to index. For each x, if target−x is in the map, return those indices; otherwise store x. That is O(n) time and O(n) space.
