Foundations

Frontend Architecture Fundamentals

Senior interviews are won by talking about arrows, ownership, and failure modes — not by reciting “we use React.”

Boundaries, coupling, cohesion, contracts

Mental model. A frontend architecture is a set of allowed dependencies. If any file can import any other file, you do not have an architecture — you have a pile. Seniors design the arrows, not the folder names.

Coupling is how much A must change when B changes. Cohesion is how much the pieces inside a module serve one reason to change. You want high cohesion, low coupling, and dependency direction that points inward toward stable policy (UI → application use-cases → domain types → infrastructure adapters).

A boundary is a line where a contract exists: a TypeScript public export, an event, an HTTP API, a design-system package. Crossing a boundary without the contract is a bug, even if TypeScript compiles.

UI components --> feature hooks / use-cases | | v v design system domain types + ports | v adapters (HTTP, analytics, flags)

Extensibility is cheap when new features add modules that implement a port. Maintainability dies when every feature reaches into every other feature’s Redux slice or CSS global.

Interview. “How do you keep 20 engineers from creating a dependency mess?” Answer: package boundaries + lint (dependency-cruiser / eslint-plugin-import) + a small number of public barrels + code review that rejects cross-feature deep imports. Not “we use monorepo.”

Atlassian-shaped products last a decade. The architecture that ships the next plugin without rewriting issue-view is the architecture that wins.

Trade-off sentence to practice: “I’d start with a modular monolith, feature folders, and enforced import rules. I would not split deployables until a team is blocked on release cadence or a runtime isolation requirement (plugins, different SLO)."

Production React

React Architecture

Beyond “components and hooks”: the shell, the ports, and the lines features may not cross.

Architecting a production React application

A production React app is a composition root plus feature modules. The shell owns routing, providers (auth, flags, query client, theme), and error boundaries. Features own screens and their hooks. Shared infrastructure is imported, never copy-pasted.

app/boot QueryClient + Auth + Flags + Theme + Router | +-- ErrorBoundary (route) +-- pages/IssuePage --> features/issue-view +-- pages/BoardPage --> features/board | +-- widgets (presentational) +-- useIssue(id) --> api/issues (port) +-- analytics.track +-- flags.isOn('issue-ai')
  • Component boundaries: a component that both fetches and paints a 400-line JSX file is not a boundary. Split “data + policy” (hook) from “view” (props in, events out).
  • Smart vs presentational: still useful if you treat “smart” as a hook, not a class container. Presentational components are the design-system and widgets; they are easy to Storybook and a11y-test.
  • Service / API client: one HTTP client (timeouts, correlation ID, 401 refresh, error mapping). Features call issuesApi.get(id), not fetch inline.
  • Context boundaries: split providers by change rate (theme vs current-user vs live-board). One mega-context is a re-render bomb.
  • Error boundaries: at route and at expensive widgets (board, editor). A plugin crash must not white-screen Jira. Pair with an error-reporting client and a fallback UI.
  • Routing: URL is a public API. Filters, selected issue, and tab belong in the URL if they are shareable. Nested routes for issue-in-board.
  • Feature flags: evaluated at the edge of a feature, not sprinkled as if (flag) in 40 files. Server-driven flags; never assume the client is the source of truth for entitlements.
  • Config / env: build-time public env vs runtime config endpoint (different CDN builds per realm). Do not bake tenant URLs you cannot change.
  • Permissions: hide and disable in UI, enforce on the server. Frontend permission hooks are UX, not security.
  • Analytics / logging: a telemetry port. Features emit intent (“issue_transitioned”), the adapter maps to the vendor. PII policy lives in the adapter.

Component design and composition

A component API is a contract. Prefer composition (Modal.Header) over boolean soup (isLarge isDanger showFooter hideClose). Headless primitives (focus trap, listbox) + styled skins scale across brands.

Common mistake: exporting a 60-prop Table that every product forks. Better: headless row model + slots + a few product tables that compose it.

Interview takeaway: show you can say no to a prop and propose a slot instead.

APIs

Component Design

A component is a public API. Seniors design the contract first: what is owned, what is composed, what is forbidden.

Component contracts, composition, and ownership

Mental model. Every exported component has callers you do not control. Props are a versioned interface. A boolean that exists only for one product screen is a smell; a slot or a smaller primitive is usually the fix.

Three layers (use all three, do not collapse them)

  1. Headless primitive — focus, keyboard, roles, open/close state. No pixels. Example: a listbox that speaks the APG pattern.
  2. Styled primitive — tokens, density, icons. Example: Menu that looks like your DS.
  3. Product pattern — domain meaning. Example: IssueStatusLozenge knows statuses, not a generic Badge variant="purple" used 40 ways.
IssuePage -> IssueHeader (product pattern) -> Heading + Lozenge + AvatarStack (DS composites) -> Text, Pressable, FocusRing (primitives) IssuePage owns data + permissions. IssueHeader owns layout of that slice. Lozenge owns color + a11y name, not Jira workflow rules.

Smart vs presentational — the 2026 version

Do not recreate 2016 “container components” as classes. Smart is a hook or a thin route module: useIssue(id) returns data + permissions + actions. Presentational receives props and fires events. The presentational layer is what you Storybook, screenshot, and a11y-test without MSW.

A 400-line component that fetches, branches on flags, and paints the page is not “pragmatic.” It is an untestable ownership blob. Split when a file has two reasons to change (data policy vs visual layout).

Many teams

Frontend Scalability

Scale here means people and time, not only QPS. A 200ms INP and a 20-minute CI are both scalability bugs.

Scaling the codebase with teams

  • Ownership: CODEOWNERS per feature package. Review load is a first-class SLO.
  • Build: incremental tsc / project references, affected-test (Nx/Turborepo). A 5-minute main build that is 40 minutes on a Friday afternoon is an architecture problem.
  • Shared kernel: keep it small. The more that lives in shared/, the more you recreate a monolith with extra steps.
  • Compatibility: design-system and entity types version like public APIs. Deprecate, don’t break on a Tuesday.
  • Runtime scale: code-split by route and by heavy widgets (editor, board). Do not download admin settings JS on the issue view.

Practice question: “How would you structure a React monorepo used by 20 teams?” — packages by domain, one app shell, enforced deps, shared DS, CI affected graph, RFC process for kernel changes.

Runtime

React Internals

You do not need to recite source file names. You do need a model that explains Strict Mode double-invoke, transitions, and why “setState in render” is a footgun.

Elements, Fiber, render, commit, scheduling

Simple model. createElement / JSX produces a plain object (an element): { type, props, key }. React’s runtime walks that description and maintains a parallel tree of Fibers — work-in-progress units that remember state, effects, and the real DOM node. “Virtual DOM” as a full-tree-diff myth is outdated; reconciliation is Fiber-vs-Fiber, guided by type and key.

Deeper model. There are typically two Fiber trees: current (what’s on screen) and work-in-progress (the render being built). Render can be interrupted and thrown away. Commit is synchronous and applies DOM + refs + layout effects.

JSX -> Element (immutable description) | v scheduleUpdate (lane / priority) | v RENDER (interruptible) -- reconcile, call function components work-in-progress Fiber tree | | (may restart if a higher-priority update arrives) v COMMIT (sync) mutation (DOM) layout effects (useLayoutEffect) paint passive effects (useEffect)

What happens when setState() is called

  1. Update creation. React stores an update (and a lane) on the Fiber. In 18, multiple updates in the same event are batched. In 18+, many async updates batch too.
  2. Scheduling. The scheduler decides when to start a render. Urgent (click) vs transition (list filter). This is why typing can stay responsive while a large list updates.
  3. Render. Function components run. Hooks read the WIP Fiber. This must be pure enough to retry. Do not put DOM writes or subscriptions here.
  4. Reconciliation. Child elements are matched to existing Fibers by position, type, and key. Same type+key: update. Different type or key: unmount old, mount new (state reset).
  5. Before commit. The WIP tree may be discarded. Effects have not run. The DOM is still the previous commit.
  6. Commit. DOM mutations. useLayoutEffect (read layout, sync). Browser paints. Then useEffect (subscriptions, network, logging).

Why render is interruptible. A 30ms component tree on the main thread would wreck INP. Concurrent rendering yields to input. If you treat render as “this definitely happened,” your side effects in the function body will double-fire in Strict Mode and tear in concurrent features.

Suspense (conceptual). A component throws a thenable; React shows a fallback Fiber and continues siblings it can. Data libraries integrate by throwing promises. Do not invent a custom Suspense cache in an interview unless you can discuss tearing and cache identity.

Refs are the escape hatch that does not schedule a render. useLayoutEffect vs useEffect: layout is for “measure then mutate before paint” (tooltip position). Passive is for “talk to the world after paint.”

Senior sentence: “I treat render as a calculation that can run extra times. I put world-changing work in effects or event handlers, and I pick priority with transitions when the update is large and non-urgent."

Batching, lanes, transitions, Suspense

Batching. React 18+ flushes many setState calls in the same event, timeout, promise, and native handler as one render. You almost never need flushSync. Use it only when the next line must read the DOM (measure a node you just forced). Overusing flushSync destroys INP.

Lanes / priorities (mental model, not source names). Updates are not a FIFO queue of “the next render.” They have urgency. A click that opens a menu is urgent. Filtering 10k issues is usually a transition: keep the typed characters instant, mark the list update as interruptible. If a higher-priority update arrives, the WIP list render can be thrown away and restarted.

TypeScript
const [isPending, startTransition] = useTransition();
function onJqlChange(next: string) {
  setDraft(next);                 // urgent: the input
  startTransition(() => {
    setAppliedJql(next);          // interruptible: the board
  });
}
// useDeferredValue(appliedJql) is the “one value, two speeds” variant
// when you do not control the setter (e.g. a library prop).

useTransition vs useDeferredValue. Transition wraps your setState. Deferred wraps a value you already have so a child can lag. Do not wrap everything. If the list is 20 rows, a transition is ceremony.

Suspense (conceptual). A child is not ready. It “suspends” (throws a thenable). React keeps showing the nearest fallback and can continue siblings. Data libraries integrate by throwing a promise tied to a cache key. Pitfalls seniors mention: cache identity (two caches = two waterfalls), tearing if you read a mutable store during render, and using Suspense as a substitute for an error boundary (errors need ErrorBoundary).

Effects model. Render calculates the next screen. useLayoutEffect runs after DOM mutation, before paint — measure, then sync-set. useEffect runs after paint — subscribe, fetch, log. Strict Mode in development mounts → unmounts → remounts to prove your cleanup is real. If you “fetch in useEffect” without abort, you will double-fetch in dev and race in prod.

Interview: “What can happen before commit?” Answer: another render can start; the WIP tree can be discarded; no DOM writes; no effects. That is why you do not put side effects in the function body.

Identity

React Reconciliation

If you can teach keys with a board-card example, you are at the senior bar for this topic.

Reconciliation rules

React does not “diff the whole page.” It walks the tree and, at each Fiber, asks: is this the same component instance as last time?

  • Same type + same key (default key = position): update. Props change, state stays, DOM is patched.
  • Different type or different key: unmount old (effects cleanup, state gone), mount new.
  • Lists: keys let React match across reorder. Missing keys → index matching → state bugs.

Parent re-render does not mean the DOM changes. If child props are referentially equal and the child is memoized, even the function may not run. If it runs and returns the same host elements, commit may still skip DOM work.

Practice

1. Same type, key A → key B

TypeScript
function Box({ id }: { id: string }) {
  const [n, setN] = useState(0);

}

<Box key="A" id="A" />
// next:

Expected behavior. The Fiber is thrown away. State n resets to 0. DOM node is remounted. Effects clean up and re-run.

Interview takeaway. Key is part of identity. Changing it is an unmount + mount, not a prop change.

Practice

2. Index keys on a reorderable list

TypeScript
items.map((item, i) => <Row key={i} item={item} />)
// User deletes index 0. Every later row keeps key i but gets a new item.

Expected behavior. React reuses Fibers by index. Uncontrolled inputs and local state slide to the wrong row. You will ship a bug that looks like “React is broken.”

Interview takeaway. Stable IDs as keys. Index keys only for static lists that never reorder or prepend.

Practice

3. Unstable key (Math.random or new UUID each render)

TypeScript
<Row key={Math.random()} />

Expected behavior. Every render remounts the row. State lost. Effects thrash. Focus lost. CPU waste.

Interview takeaway. Keys must be stable across renders for the same logical entity.

Practice

4. Conditional changes component type at the same position

TypeScript

Interview takeaway. Type is identity. To preserve state, keep the same type and toggle props, or lift state.

Server state

Server State / Data Fetching

Libraries (TanStack Query, SWR, Relay, Apollo) are adapters over one architecture: a keyed cache, a stale policy, and a way to invalidate. Learn the architecture; the library is an implementation.

Request lifecycle and cache

Lifecycle: idle → fetching → success | error. Retries with backoff on idempotent GETs. Mutations need an explicit policy (retry POST is dangerous without idempotency keys).

Cache key is the identity of a query: ["issue", id], ["search", jql, page]. If two screens use the same key, they share data. That is a feature (dedupe) and a bug (accidental coupling) — design keys like APIs.

  • Stale vs fresh: stale-while-revalidate shows last data and refetches. Fresh means do not hit network. staleTime is a product decision (issue detail: 30s; presence: 0).
  • Invalidation: after transitionIssue, invalidate ["issue", id] and ["board", boardId]. Over-invalidation thrashes; under-invalidation lies to users.
  • Optimistic updates: write cache immediately, rollback on failure. Only when the happy path is obvious and conflict is rare — or you show a merge UI.
  • Pagination / infinite: page params in the key, or an infinite query that concatenates pages. Don’t put 10k issues in one GET.
  • Prefetch: on hover/route intent. Cheap for issue titles; expensive for full editor payload.
  • Dedup: in-flight map: same key, one network call. All waiters share the promise.
  • Cancellation / races: AbortController on unmount or key change. Also a generation token: ignore responses older than the latest requested JQL. Both, not one.
TypeScript
let gen = 0;
async function search(jql: string, ac: AbortSignal) {
  const my = ++gen;
  const res = await issuesApi.search(jql, { signal: ac });
  if (my !== gen) return; // stale generation
  setRows(res);
}

GraphQL clients add a normalized cache (entities by id). Great for overlapping issue objects; costly to reason about (gc, stale fields). REST + a document cache is simpler until overlap hurts.

Do not couple the interview to one library. Say: “I’d use a keyed server cache with SWR, explicit mutation invalidation, and abort+generation to prevent races."

Judgment

React Performance

useMemo everywhere is not a strategy. It is a tax. Profile, then apply the cheapest structural fix (colocate state, split context, virtualize, split the bundle).

Render cost vs commit cost vs JS cost

A render is JS. A commit is DOM + layout. Users feel INP (handler + render + paint) and LCP (bytes + main thread). Optimizing the wrong one is common.

Unnecessary renders happen when a parent re-renders and children are not isolated, or context value identity changes. They are free if the subtree is tiny; they are death if 8,000 rows run function bodies.

memo / useMemo / useCallback: they skip work when deps are referentially equal. They add work to compare deps and allocate the hook. They fail when you pass inline objects/functions from an un-memoized parent. They hide bugs when you put the wrong deps.

Performance Debugging

Practice the first click in DevTools. Seniors do not start with useMemo; they start with a recording.

A React table with 20,000 rows is slow

1. Symptoms. Scroll jank, INP > 200ms, fans spin.

2. Possible causes. Full render of 20k rows; no virtualization; expensive cells; inline objects; layout thrash on resize.

3–6. Debugging. React Profiler: commit duration on scroll. Performance panel: long tasks. Why did this render? Use React DevTools Profiler + browser Performance + Network. Record a 3s interaction, not a 30s guess.

7–8. Fixes and trade-offs. Virtualize (window + overscan). Memo cells. Don’t measure layout per row. Paginate if the product allows. Trade-off: jump-to-row and a11y need extra work (aria-rowcount, tab stops).

Typing in a search box causes lag

1. Symptoms. Each keystroke feels sticky.

2. Possible causes. Each change filters 20k in the same component as the input; no debounce; no transition; context updates the world.

3–6. Debugging. Profiler on keydown. See if the input’s parent is the board root. Use React DevTools Profiler + browser Performance + Network. Record a 3s interaction, not a 30s guess.

7–8. Fixes and trade-offs. Colocate input state. Debounce the query (not the input paint). useTransition for the list. Web worker if the filter is heavy. Trade-off: debounce vs feeling of live search.

Entire app re-renders when a small context value changes

1. Symptoms. Profiler shows all consumers on a theme toggle or a single ticket patch.

2. Possible causes. Fat context; new object each render; tickets in the same provider as theme.

3–6. Debugging. Highlight updates in React DevTools. Search who consumes the context. Use React DevTools Profiler + browser Performance + Network. Record a 3s interaction, not a 30s guess.

7–8. Fixes and trade-offs. Split providers. Selector store. Trade-off: more provider nesting vs a store library.

Initial JS is 5 MB

1. Symptoms. Poor TTI/LCP on mid-range laptops. Atlassian-like plugin bundles.

Page takes 4 seconds to become interactive

1. Symptoms. Users click, nothing happens. LCP maybe OK if a hero image is fast.

Host

Browser Architecture

From URL to pixels

URL -> DNS -> TCP + TLS -> HTTP request / response -> HTML bytes -> tokenizer / parser --> DOM -> CSS (blocking) --> CSSOM -> DOM + CSSOM --> render tree -> layout (reflow) -> paint -> composite (GPU layers) JS can block parse (sync scripts) or run after (defer/module) rAF / input sit between tasks, not between microtasks

Critical rendering path: anything that delays first paint or LCP: TTFB, render-blocking CSS, sync JS, late hero image, font-display:block. preload the LCP image and critical font. prefetch the next route. lazy below-the-fold and non-critical JS. Resource hints are not magic if the main thread is busy.

Priorities: browsers now have Fetch Priority. Mark the LCP image high; mark analytics low. HTTP/2 multiplexing does not save you from 400KB of unused JS.

Networking & Caching

HTTP versions and cache layers

HTTP/1.1: few connections, head-of-line blocking. HTTP/2: multiplex on one TLS connection (still HOL at TCP). HTTP/3/QUIC: better loss recovery. You still pay TLS and TTFB. CDNs terminate TLS close to the user and cache GET/HEAD at the edge.

Compression: Brotli for static text; Gzip fallback. Don’t compress already-compressed images.

Resilience

Offline / Resilience

Degraded and offline-first

Offline-first means the UI works on a cache and a queue, not that every Atlassian product must work on a plane. Confluence drafts: yes. Jira board realtime: degrade to “last known + reconnect.”

  • Service worker: cache app shell; never blindly cache authenticated HTML.
  • Retry GET with exponential backoff + jitter. Mutations: idempotency key, finite retries, dead-letter UI.
  • Request dedupe (in-flight map) plus optimistic UI when rollback is cheap.
  • Eventual consistency: show “saved locally” vs “on server.” Two tabs: last-write-wins or merge (CRDT/OT only if you must).
  • Graceful degradation: hide presence avatars; keep typing; disable drag if sync is down.

Multi-team UI

Design Systems

Tokens, APIs, versioning, adoption

Foundations: color / space / type tokens -> primitives (Pressable, Text, FocusRing) -> composites (Button, Modal, Menu) -> product patterns (IssueLozenge) Docs + a11y contract + visual regression Package: @acme/ds semver + codemods for breaks

Tokens are the language (not hex in 40 repos). Component APIs prefer composition. Theming via tokens + CSS variables, not a React context that re-renders the world. Accessibility is in the primitive (keyboard, roles), not a “phase 2” add-on.

Versioning: treat the DS like a public API. Breaking a Button padding is a major. Provide a second major and a migration lint. Visual regression (Chromatic/Playwright screenshots) on primitives. Documentation is how 12 teams adopt without Slack archaeology.

MUI vs custom vs headless (Radix/React Aria): buy primitives when a11y is hard (listbox, combobox); own tokens and product composites. A full custom DS is justified when brand + density + plugin theming (Atlassian-like) is the product.

CSS architecture: CSS variables for tokens; avoid deep descendant selectors that leak across plugins. Shadow DOM only if you truly isolate third-party CSS.

Multi-team adoption (the hard part)

  • Package architecture: tokens package (no React), primitives, composites, icons. Apps depend downward. Features do not import another feature’s CSS.
  • Documentation: do / don’t, a11y notes, token mapping. A DS without docs is a Sketch file in npm form.
  • Testing: unit on logic, RTL on keyboard, visual regression on primitives, axe in CI for the kitchen-sink page.
  • Breaking changes: major + codemod + dual-run. “Just change Button” is how you stall 12 teams.
  • Theming: CSS variables on :root / [data-theme], not a React theme object that re-renders Jira.

MUI / Chakra: fast start, theming escape hatches, you inherit their a11y and their bundle. Custom DS: justified when density, plugins, and brand are the product (Atlassian-shaped). Headless (React Aria / Radix) + your tokens is the usual senior compromise.

Practice: “Design a design system for 8 product teams.” Lead with tokens, versioning, a11y in primitives, and an RFC for kernel changes — not a component gallery screenshot.

Micro-frontends

When MFEs earn their complexity

MFEs exist to buy independent deploy and team autonomy. They cost duplicate runtime, shared-dep hell, inconsistent UX, and debugging across bundles. Atlassian-like plugin iframes are a form of isolation — not the same as “five webpack Module Federations on one issue page.”

Integration: build-time compose (simple, coupled releases) vs runtime (Module Federation, iframes, web components). Shared React must be a singleton or you break hooks. Auth: one session cookie at the parent; never N copies of JWT in localStorage. Routing: a parent router or path convention. State: pass IDs and events, do not share a Redux store across deployables.

Decision: start modular monolith. Split a deployable when a team is blocked on release cadence and the runtime contract is small (admin settings ≠ issue field). Refuse MFE as a resume-driven rewrite.

Runtime details seniors get asked

  • Module Federation (concept): a host loads remotes at runtime. You must singleton React (and usually the router / DS). Version skew of React = hook crashes. Treat shared deps as a compatibility contract, not “npm will work it out.”
  • Build-time compose: packages imported into one bundle. Independent code, one deploy. Cheaper than federation; not independent release.
  • iframe plugins: strongest isolation, worst integration (resize, a11y, theme, auth via postMessage). Correct for untrusted apps. Wrong for your own issue header.
  • Communication: custom events or a tiny typed bus of IDs. Do not share a Redux store across deployables — you have created a distributed monolith with extra latency.
  • Auth: parent session cookie; remotes call APIs with the same origin or a BFF. N copies of JWT in localStorage is an XSS farm.
  • Performance cost: duplicate copies of React/lodash, waterfalls of remoteEntry, layout shift when a remote loads late. Budget remotes like third-party scripts.

When NOT to use MFEs: one product, one domain object (Issue), one design language, teams that already share a weekly release. Split packages, not deploys.

Observability

Logs, metrics, traces, RUM

Frontend observability is how you debug “works on my machine” at 10M users. Logs (structured, sampled). Metrics (INP, API error rate, cache hit). Traces (click → fetch → downstream). Error tracking (stack + release). Session replay (privacy-reviewed). Correlation IDs: generate on the client or take from the edge; send on every API call; show in the support dialog.

Practice: “Users say the Jira issue page is randomly slow.”

  1. Define slow (INP? LCP? a specific click? a tenant?).
  2. Slice RUM by browser, release, plugin count, issue size, region.
  3. Find a trace for a slow session; look at long tasks vs API p95 vs render.
  4. Check if a plugin iframe or a large ADF document correlates.
  5. Reproduce with Performance + React Profiler on a large fixture.
  6. Fix the dominant bucket (often: no virtualization, sync parse, waterfall).
  7. Ship a mark/measure around the interaction; verify the metric moves.

fundamentalsreactQ1

1. What exactly causes a React re-render?

Short answer. A state/context/store update on that Fiber (or a parent render that reaches it).

Deep explanation. Function components re-run when React renders their Fiber. That happens after setState, a context value change they consume, a store subscription fire, or a parent render unless memo bails out. Props changing is usually because the parent rendered.

Common misconception. “Props changed” as a mystical force independent of the parent.

Senior follow-up. Does a parent re-render always change the DOM?

fundamentalsreactQ2

2. Does a parent re-render always mean the DOM changes?

Short answer. No. Render is JS. Commit patches the DOM only when host fibers differ.

Deep explanation. A child can run and return the same elements; React skips DOM work. memo can skip the child function entirely if props are equal.

Common misconception. Re-render = DOM update.

Senior follow-up. How do you see the difference in DevTools?

internalsreactQ3

3. What happens when setState is called?

Short answer. Create an update, schedule a lane, render (interruptible), reconcile, commit DOM + effects.

Deep explanation. See Internals section. Batching may merge updates. Render can be thrown away. Effects run after paint (except layout).

Common misconception. setState writes the DOM immediately.

Senior follow-up. What can happen before commit?

internalsreactQ4

4. Why can rendering be interrupted?

Short answer. So urgent input can run; large updates yield.

Deep explanation. Concurrent React schedules work in lanes. Transitions are interruptible. That is why render must be pure enough to retry.

Common misconception. React 18 always paints every render attempt.

Senior follow-up. What is a transition vs an urgent update?

Short answer. A linked work unit: type, pending props, state, effects, DOM pointer, return/child/sibling.

Common misconception. Fiber is the virtual DOM array.

Senior follow-up. Where is hook state stored?

function Autocomplete({ search }: { search: (q: string, s: AbortSignal) => Promise<string[]> }) {
  const [q, setQ] = useState("");
  const [items, setItems] = useState<string[]>([]);
  const [open, setOpen] = useState(false);
  useEffect(() => {
    const ac = new AbortController();
    const t = setTimeout(async () => {
      if (!q) { setItems([]); return; }
      try { setItems(await search(q, ac.signal)); setOpen(true); } catch (e) { if ((e as any).name !== "AbortError") throw e; }
    }, 150);
    return () => { clearTimeout(t); ac.abort(); };
  }, [q, search]);
  return (
    <div>
      <input role="combobox" aria-expanded={open} aria-controls="ac-list" value={q} onChange={(e) => setQ(e.target.value)} />
      <ul id="ac-list" role="listbox">{items.map((it) => <li key={it} role="option">{it}</li>)}</ul>
    </div>
  );
}

function Infinite({ fetchPage }: any) {
  const [items, setItems] = useState<any[]>([]);
  const [cursor, setCursor] = useState<string | null>(null);
  const [done, setDone] = useState(false);
  const load = useRef(false);

function Modal({ open, onClose, title, children }: any) {
  const ref = useRef<HTMLDivElement>(null);
  const prev = useRef<HTMLElement | null>(null);
  useEffect(() => {
    if (!open) return;
    prev.current = document.activeElement as HTMLElement;
    const el = ref.current; el?.querySelector<HTMLElement>("button, [href], input")?.focus();
    const onKey = (e: KeyboardEvent) => { if (e.key === "Escape") onClose(); };
    document.addEventListener("keydown", onKey);
    return () => { document.removeEventListener("keydown", onKey); prev.current?.focus(); };

        <h2>{title}</h2>{children}<button type="button" onClick={onClose}>Close</button>

}

async function upload(file: File, api: any) {
  const size = 5 * 1024 * 1024;
  const id = await api.init(file.name, file.size);
  const parts = Math.ceil(file.size / size);
  const limit = 3; let active = 0; const q: (() => void)[] = [];
  const run = (fn: () => Promise<void>) => new Promise<void>((res, rej) => {
    const start = () => { active++; fn().then(res, rej).finally(() => { active--; q.shift()?.(); }); };
    if (active < limit) start(); else q.push(start);
  });
  await Promise.all(Array.from({ length: parts }, (_, i) => run(async () => {
    const blob = file.slice(i * size, (i + 1) * size);
    const etag = await api.putPart(id, i, blob);
    await idb.set(`${id}:${i}`, etag);
  })));
  await api.complete(id);
}

class QueryCache {
  private m = new Map<string, { data?: unknown; exp: number; inflight?: Promise<unknown> }>();
  get<T>(key: string, fetcher: () => Promise<T>): Promise<T> {
    const now = Date.now(); const hit = this.m.get(key);
    if (hit?.data !== undefined && hit.exp > now) return Promise.resolve(hit.data as T);
    if (hit?.inflight) return hit.inflight as Promise<T>;
    const inflight = fetcher().then((data) => { this.m.set(key, { data, exp: now + 10_000 }); return data; });

Why, not what

Architecture Decision Records

Practice answering “Why this architecture?” Template: Context → Decision → Alternatives → Trade-offs → Consequences. Redux/GraphQL/MFE/SSR are not automatically correct.

ADR: Redux vs Context

Context. Multiple teams, growing issue view, some want a store.

Decision. Default: server cache + URL + local + split context. Redux Toolkit only if many writers need a single event log / debug story.

Alternatives. Context-only; Zustand; Redux; signals.

Trade-offs. Context is simpler until values churn. Redux is not automatically better; a god-store is worse than fat context.

Consequences. If we pick Redux, tickets still do not live there — they live in the query cache.

ADR: REST vs GraphQL

Context. Issue page needs issue + comments + watchers.

Decision. REST + BFF with partial success and timeouts. GraphQL if we will staff a graph and many clients need custom shapes.

Alternatives. Client N+1; GraphQL; BFF REST; tRPC.

Trade-offs. GraphQL is not automatically better; first-paint mega-queries are a failure mode.

Consequences. Measure TTFB. Split extras from LCP path.

ADR: Monolith vs micro-frontends

Context. 20 engineers, one product, plugins exist.

Decision. Modular monolith + iframe plugins for untrusted code. No Module Federation rewrite.

Alternatives. One SPA; MFE runtime; iframes only.

Trade-offs. MFEs are not automatically better. Plugins already give isolation.

Consequences. Revisit if a team is blocked on release cadence and the contract is small.

ADR: CSR vs SSR

Context. Logged-in issue view vs marketing.

Decision. CSR + skeleton for the app; SSR/ISR for public docs/marketing. Hydration cost is real.

Alternatives. CSR; SSR; streaming RSC.

Trade-offs. SSR is not automatically faster INP. Hydration can hurt.

Consequences. Revisit if LCP of body text is the metric and HTML helps.

ADR: Client cache vs server/CDN cache

Context. Issue JSON vs hashed JS vs HTML.

Decision. Hashed assets: CDN immutable. User JSON: app cache + short HTTP. HTML: private/no-store.

Alternatives. Cache everything at CDN; cache nothing; SW for all.

Trade-offs. Invalidation vs hit-rate. No instant global consistency.

Consequences. Wrong HTML cache is a SEV.

ADR: Local vs global state

Context. Modal, filters, user, issues.

Decision. Decision tree: server → URL → nearest parent → local. Global is a last resort.

Alternatives. All Redux; all local; all URL.

Trade-offs. Global is not automatically scalable.

Consequences. Document the tree in the README of the feature.

ADR: WebSocket vs polling

Context. Board presence and remote moves.

Decision. Poll 15–30s if freshness allows; WS if presence/moves are product-critical; always REST catch-up.

Alternatives. WS only; SSE; poll; Firestore.

Trade-offs. WS is not automatically ‘realtime senior.’ Infra and degrade matter.

Consequences. Measure disconnects before celebrating.

ADR: Pagination vs infinite scroll

Context. Search vs feed.

Decision. Search/admin: numbered or cursor pages in the URL. Feeds: infinite + virtualize + load-more fallback.

Alternatives. Always infinite; always pages.

Trade-offs. Infinite is not automatically better UX (a11y, memory, share).

Consequences. Virtualize either.

ADR: MUI vs custom DS

Context. Need buttons now; 12 teams later.

Decision. Headless a11y primitives + custom tokens/composites. Full MUI if time-to-market dominates and theming is enough.

Alternatives. MUI; fully custom; copy Atlassian DS.

Trade-offs. Custom is not automatically more senior.

Consequences. A11y of combobox is the buy-vs-build hinge.
