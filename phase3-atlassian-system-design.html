Foundations

System Design Fundamentals

You already design frontends. Phase 3 is the same judgment applied to data, networks, and other people’s failures.

What system design actually is

Mental model. System design is the craft of choosing boundaries, contracts, and failure policies under constraints of people, money, and physics. It is not a catalog of logos. A senior answer names the user, the critical path, the number, the thing that breaks first, and the option you rejected.

WordMeans in an interviewHow you measure it
FunctionalWhat the product doesAPIs, entities, user stories
Non-functionalHow well it must do itp99 latency, availability, RPO/RTO
ScalabilityCost of 10× load is roughly linear, not a rewriteRPS headroom, shard plan
ReliabilityCorrect enough under failureError budget, retries, degradation

LatencyTime for one requestp50/p95/p99, not the average

ConsistencyWhich reads see which writesSay the workflow, not “strong”
DurabilityA write that was acked is not lostReplicas, fsync, backups

Jira-shaped example. “Transition issue” is functional. “p99 < 300ms for the writer, watchers notified within 30s, never show a status the user is not allowed to see” are NFRs. If you optimize notification latency by writing the email in the request path, you have traded availability of the click for a Slack-outage-shaped failure.

Senior trade-off sentence: “I’d rather the transition succeed and the email be late than the transition fail because SES is down. That is an explicit consistency and availability choice, not a missing queue."

Interview. Start with users and the one workflow that must not be wrong. Do not start with Kubernetes.

How you talk

System Design Interview Framework

45–60 minutes is a conversation with a clock, not a textbook. Spend ~8 min clarify+estimate, ~12 min high-level, ~20 min deep dive, ~10 min failures/trade-offs. Practice questions in this file use this spine.

Clarify requirements

“I’ll first clarify whether consistency or availability matters more for this workflow.”

One happy path + 2–3 must-have adjacent flows. Park the rest.

“I’ll treat plugins / AI / mobile as follow-ups unless you want them in scope.”

“Who can see an issue — that constraint will shape the data model more than the cache.”

“I’ll assume peak and say if that changes the architecture. Challenge me if the number is wrong.”

“The URL and the error model are part of the design, not decoration.”

“I’ll draw the request path first, then the async path.”

Entities, keys, what is source of truth.

“Search and cache are derived. Permissions live in the source of truth.”

The one or two components that make this problem hard.

“At this scale, this component is the likely bottleneck.”

What, where, TTL, invalidation, stampede.

“I’d cache the read-heavy snapshot and invalidate on write — and say what stale means.”

“I would not shard on day one unless the estimate forces it.”

Numbers

Capacity Estimation

A wrong number with a clear method beats a precise number with no units. Do the ten drills.

Formulas and a worked 10M-user example

Write units every line. Interviewers forgive arithmetic if the method is visible.

Worked example. 10 million registered, 1 million DAU, 100 requests/user/day, 10% of daily traffic in the peak hour, 20:1 reads, 2 KB average JSON.

Daily requests     = 1e6 * 100 = 1e8
Avg RPS            = 1e8 / 86400 ≈ 1,160
Peak-hour requests = 0.10 * 1e8 = 1e7

Writes             ≈ 2,780 / 21 ≈ 130 WPS (if 20:1)

At ~3k peak RPS a modular monolith + Postgres primary + read replicas + Redis is a default. You do not need Kafka to survive 3k RPS. You need Kafka (or a log) when multiple independent consumers, replay, or huge fan-out appear.

What happens at 10× (30k peak RPS)? Connection pools, lock contention, and a hot tenant matter before “we didn’t have Kubernetes.”

Exercise 1

Estimate 1

10M users, 1M DAU, 100 req/user/day, peak = 10% of daily in 1 hour

Worked answer. Daily req = 1e6 × 100 = 1e8. Avg RPS = 1e8 / 86400 ≈ 1,160. Peak hour req = 0.10 × 1e8 = 1e7. Peak RPS ≈ 1e7/3600 ≈ 2,780.

Interview note. Always state the seconds approximation: 86400 ≈ 10^5 if you need a back-of-envelope (then you get ~1,000 RPS — say you rounded).

Exercise 2

Estimate 2

Jira-like: 200k DAU, 40 pages/user/day, 8 API calls/page, peak 3×

Worked answer. Daily API = 2e5 × 40 × 8 = 6.4e7. Avg RPS ≈ 740. Peak ≈ 2,200.

Interview note. Pages ≠ API calls. Frontends amplify.

Exercise 3

Estimate 3

Comments: 5% of API writes, 2 KB each, keep 5 years, 3 replicas

Worked answer. Writes/day = 0.05 × 6.4e7 ≈ 3.2e6. Bytes/day ≈ 6.4 GB. Year ≈ 2.3 TB. 5y ≈ 12 TB. ×3 replicas ≈ 36 TB plus indexes (~1.5–2×).

Interview note. Indexes and history matter. Say the multiplier.

Exercise 4

Estimate 4

Cache: 20% of issue reads are unique/day, 50 KB payload, 80% hit target

Worked answer. If 50M issue reads/day and 20% unique → 10M keys × 50KB = 500 GB working set. You will not hold it all; cache the hot 5–10% (25–50 GB) and accept misses.

Interview note. Working set ≠ cardinality. Hot keys dominate.

Exercise 5

Estimate 5

Upload: 10k attachments/day, average 8 MB, 1% are 1 GB

Worked answer. Typical bytes/day ≈ 80 GB. Tail: 100 files × 1 GB = 100 GB. Bandwidth out of origin is not the same as user upload (they hit object storage).

Interview note. Design the API server out of the byte path. Pre-signed PUT to object storage.

Exercise 6

Estimate 6

Chat: 50k concurrent WS, 1 msg/user/min, 200 byte messages, fan-out 10

Worked answer. Ingress 50k/60 ≈ 833 msg/s. Egress 8,330 msg/s. Connections are the scarce resource, not bytes.

Interview note. Quote connection count and fan-out before you quote Kafka.

Exercise 7

Estimate 7

Search: 10% of reads, 200ms p95 budget, 2M docs

Worked answer. Search RPS ≈ 0.1 × 740 ≈ 74 average. You still isolate it so a reindex cannot take the issue API down.

Interview note. Low RPS can still be a reliability island.

Exercise 8

Estimate 8

Multi-tenant: 5k tenants, one tenant is 30% of traffic

Worked answer. Hot tenant is a shard/key design problem. Average RPS is a lie for that tenant.

Interview note. Always ask: is traffic uniform? Atlassian-like products are not.

Exercise 9

Estimate 9

Notifications: 1 event → 20 watchers, 10% email

Worked answer. If 50 transitions/s → 1,000 watcher fan-out/s → 100 emails/s. That is a queue + rate limit, not a for-loop in the request.

Interview note. Fan-out is the number that surprises people.

Exercise 10

Estimate 10

Read/write 20:1 on issue GET vs PATCH

Worked answer. Replicas help GETs. PATCHes still hit primary. Cache helps the 20, invalidation is the write cost.

Interview note. Read-heavy is not 'easy' if every write must wake 20 cached copies.

Contracts

API Design

Frontends are clients of contracts. Senior design names resources, failure modes, and the protocol that matches the access pattern — not the trendiest transport.

REST — mental model and resource design

Mental model. REST is not “JSON over HTTP.” It is a style where named resources (issues, comments, transitions) are manipulated with a small verb set, and the server owns authorization and invariants. URLs are bookmarks for humans and clients; they are not the security boundary.

Technical. Safe methods (GET, HEAD, OPTIONS) should not change server state. Idempotent methods (PUT, DELETE) can be retried without double effect. POST creates or triggers workflows where the client does not supply the final URL. Use nouns in paths, verbs in HTTP methods — POST /issues/{id}/transitions, not POST /moveIssue.

typescript
// Jira-like issue resource (tenant-scoped)
const res = await fetch("/rest/api/3/issue/PROJ-42", {
  headers: {
    Authorization: `Bearer ${token}`,
    "X-Atlassian-Token": "no-check", // CSRF on cookie auth in real Jira
    Accept: "application/json",
  },
});
if (res.status === 404) { /* issue missing OR no permission — same shape */ }
const issue = await res.json();

Production example. Confluence page REST returns a stable id and a human title. Clients cache by id; search and backlinks are separate derived views. If you expose GET /pages/by-slug/{slug}, document that slug changes on rename and that slug is not globally unique across spaces without a composite key.

Trade-offs. REST’s strength is cacheability, predictable URLs, and incremental adoption. Its weakness is chatty UIs that need five round trips for one screen — that is a client/BFF problem, not an automatic reason to switch protocols.

Interview. “Design issue + comment APIs.” Start with resources, error model, pagination, and who may call what — not HTTP status trivia.

Mistake: treating 404 as ‘not found’ only. In multi-tenant products, 404 often means ‘not found OR forbidden’ to avoid leaking existence.

Pagination, filtering, sorting, versioning

Mental model. Pagination is a contract about stable iteration over a moving dataset. Filtering and sorting change which rows qualify; pagination must not assume the dataset is frozen while the client walks pages.

Technical — offset vs cursor.

StyleGood forBreaks when
Offset/limitAdmin exports, small tables, “page 3 of admin UI”Deep offsets on large tables (sort + skip scans), concurrent inserts/deletes shift windows
Keyset/cursorInfinite scroll, issue activity feeds, comment threadsSort key not unique — tie-breaker required; opaque cursors need versioning on schema change
typescript
// Cursor pagination client — always follow nextPage, never invent offsets
type Page<T> = {{ values: T[]; nextPage?: string }};

async function* listComments(issueKey: string) {{
  let cursor: string | undefined;
  do {{
    const qs = cursor ? `?cursor=${{encodeURIComponent(cursor)}}` : "";
    const page: Page<Comment> = await get(`/issues/${{issueKey}}/comments${{qs}}`);
    for (const c of page.values) yield c;
    cursor = page.nextPage;
  }} while (cursor);
}}

Filtering. Prefer explicit query params with an allow-list: project=PROJ&status=In Progress&assignee=me. For complex filters (Jira JQL-shaped), a POST /search with a structured body beats infinitely long GET URLs — and makes caching policy explicit (usually none on search).

Versioning. Path version (/v3/) for breaking changes; additive JSON fields are not a version bump. Sunset headers + dual-write period beat breaking mobile clients silently.

Production example. Issue search sorted by updated DESC: cursor is (updated_at, id) encoded — never cursor on updated alone or two issues updated in the same millisecond swap order between pages.

Trade-offs. Cursors are harder for “jump to page 17” UX. If the product needs that, expose offset for shallow pages only and cursor for deep feeds — and say so.

Interview. “Paginate millions of rows?” Keyset on indexed sort key + tie-breaker; avoid OFFSET 1000000.

Errors, idempotency, retries, rate limits

Mental model. Distributed clients will retry. Your API must decide which retries are safe, which errors are actionable, and how overload presents itself.

Technical — error model. Return a stable machine code, human message, optional field errors, and a correlation id. Same shape for 4xx and 5xx.

json
{
  "error": "transition_invalid",
  "message": "Cannot transition from Done to In Progress",
  "fields": { "status": "Issue is closed" },
  "correlationId": "9f3c2a1b-..."
}

Idempotency. POST that creates billable side effects (create issue, post comment, transition) should accept Idempotency-Key. Store key → response mapping with TTL; duplicate key returns original 201/409, not a second row.

typescript
await fetch("/rest/api/3/issue/PROJ-42/transitions", {{
  method: "POST",
  headers: {{
    "Content-Type": "application/json",
    "Idempotency-Key": clientRequestId, // UUID from the UI action
  }},
  body: JSON.stringify({{ transition: {{ id: "31" }} }}),
}});

Retries. Retry GET and idempotent PUT/DELETE on 502/503/504 with exponential backoff + jitter. Do not blindly retry POST unless idempotency keys exist. Honor Retry-After on 429/503.

Rate limiting. Return 429 with Retry-After and a code like rate_limit_exceeded. Limit per tenant + per user + per endpoint class (search vs CRUD). Atlassian-scale integrations hit API tokens — document burst vs sustained.

Production example. Automation rule fires 500 transitions/minute during bulk import. Without per-tenant limits, one customer degrades transition latency for everyone on the shard.

Trade-offs. Strict rate limits protect the fleet but frustrate power users; offer bulk endpoints or async jobs instead of raising limits without isolation.

Interview. “What happens if the client retries transition twice?” Walk idempotency key + server-side state machine + 409 on illegal second transition.

Mistake: retrying POST without idempotency keys — that is how duplicate Jira comments get created.

Authentication and authorization on the server

Mental model. Authentication proves who. Authorization proves what they may do on which row. The UI hiding a button is not authorization.

Technical. Bearer tokens (OAuth 2.0), scoped API tokens, and session cookies each imply different CSRF and caching rules. Every handler resolves principal → tenant membership → resource ACL → action.

Production example. GET /issue/PROJ-42: resolve issue’s tenant_id and project; check issue:read in that project. Cross-tenant id guessing must 404/403 consistently. Comment create requires comment:add and issue not in archived state — enforce in the service, not only in JQL.

Trade-offs. RBAC is operable; ABAC (field-level, issue security levels) is expressive but expensive to evaluate per row. Cache permission snapshots with short TTL and invalidate on role change — never cache “allowed forever.”

Interview. “User A shares a link; user B opens it.” Explain org boundary, issue security scheme, and why the API must re-check on every request.

Mistake: putting tenant_id only in the JWT claim without verifying it matches the resource row on every query.

GraphQL — when it earns the complexity

Mental model. GraphQL is a query language for a graph of resolvers, usually one HTTP endpoint. It solves over-fetching and under-fetching for product-shaped reads — not every API.

Technical. Client specifies the tree; server resolves fields. Danger: N+1 queries if each issue’s assignee triggers a separate DB round trip. Mitigate with batch loaders (DataLoader), JOINs at the service layer, or persisted queries.

graphql
query IssueBoard($project: ID!) {{
  project(id: $project) {{
    issues(first: 50, after: $cursor) {{
      nodes {{
        key
        summary
        assignee {{ displayName avatarUrl }}
        commentCount
      }}
      pageInfo {{ endCursor hasNextPage }}
    }}
  }}
}}

Production example. Jira issue view first paint: GraphQL can fetch issue + fields + permissions + three comments in one round trip. But search, bulk export, and webhooks remain REST/event-shaped — GraphQL rarely replaces the whole surface.

Trade-offs — GraphQL is not automatically better.

  • Caching at CDN edge is harder than GET-with-URL REST.
  • Complexity moves to resolvers, rate limiting per field, and query cost analysis.
  • Public third-party integrations often prefer stable REST OpenAPI docs.
  • A thin BFF aggregating 3 REST calls may be simpler than GraphQL for one frontend team.

Interview. “REST + BFF vs GraphQL for issue page?” Compare team count, client diversity, cache needs, and operability — pick one and name what you would not do.

Mistake: adopting GraphQL because ‘the frontend wants one request’ without a query cost budget — a single anonymous query can still take the database down.

gRPC and internal service contracts

Mental model. gRPC is a binary, contract-first RPC framework (Protobuf on HTTP/2). It shines inside the datacenter: low latency, strong schemas, streaming.

Technical. .proto files version fields with numbered tags; never reuse field numbers. Unary for request/response; server streaming for large result sets; client/bidi streaming for real-time ingestion.

Production example. Issue indexing pipeline: IssueService.StreamChanges pushes change events to search workers. Browser clients still use JSON REST — gRPC-web is optional and adds operational weight.

Trade-offs. Excellent for service-to-service; poor default for public browser APIs without a gateway. Debugging with curl is harder — invest in grpcurl, reflection, and good status details.

Interview. “When gRPC over REST internally?” Schema evolution, streaming, and typed codegen — not ‘because Google uses it.’

WebSockets vs SSE

Mental model. Both push server → client. WebSockets are bidirectional full-duplex; SSE is unidirectional text/event-stream over HTTP.

Browser Edge/API | SSE: GET /events (long-lived HTTP) |<-------------------- text/event-stream | | WS: Upgrade: websocket |<=======================> bidirectional frames

Technical. SSE: auto reconnect, works through many corporate proxies, one-way fan-out (issue updated, comment added). WebSockets: typing presence, collaborative cursors, binary frames — but sticky sessions, connection limits, and custom heartbeat.

Production example. Confluence live edit cursors → WebSocket or CRDT channel. “Issue PROJ-42 status changed” toast on a board → SSE or polling with ETag is often enough. Jira does not need a persistent socket on every tab for read-mostly boards.

Trade-offs — WebSockets are not automatically better than SSE.

  • SSE is simpler to operate (standard HTTP load balancing, retry built in).
  • WebSockets cost one connection per tab — 50k concurrent users is a capacity line item.
  • If the client only listens, SSE + POST for commands keeps auth and idempotency familiar.

Interview. “Realtime board updates?” Ask freshness SLA (seconds vs ms), bidirectional need, and mobile background behavior — then pick SSE, WS, or short polling.

Mistake: opening a WebSocket per micro-widget on the issue page — connection storms dominate.

Source of truth

Database Design

Postgres-shaped OLTP is the default backbone for issue trackers. Design for tenant isolation, measured indexes, and honest write paths before reaching for shards.

Relational mental model — tables, keys, tenants

Mental model. Postgres is row storage with ACID transactions and declarative constraints. The schema is the contract that outlives any single service deploy.

Technical. Primary keys identify rows. Foreign keys enforce referential integrity (or deliberate ON DELETE rules). Every multi-tenant table carries tenant_id and queries filter on it — composite keys and indexes lead with tenant_id.

sql
CREATE TABLE tenants (
  id         UUID PRIMARY KEY,
  slug       TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE projects (
  id         UUID PRIMARY KEY,
  tenant_id  UUID NOT NULL REFERENCES tenants(id),
  key        TEXT NOT NULL,              -- e.g. 'PROJ'
  name       TEXT NOT NULL,
  UNIQUE (tenant_id, key)
);

CREATE TABLE issues (
  id           UUID PRIMARY KEY,
  tenant_id    UUID NOT NULL REFERENCES tenants(id),
  project_id   UUID NOT NULL REFERENCES projects(id),
  issue_number INT NOT NULL,             -- per-project sequence
  summary      TEXT NOT NULL,
  status       TEXT NOT NULL,
  assignee_id  UUID,
  updated_at   TIMESTAMPTZ NOT NULL,
  UNIQUE (tenant_id, project_id, issue_number)
);

CREATE TABLE comments (
  id         UUID PRIMARY KEY,
  tenant_id  UUID NOT NULL REFERENCES tenants(id),
  issue_id   UUID NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  author_id  UUID NOT NULL,
  body       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE watchers (
  tenant_id  UUID NOT NULL REFERENCES tenants(id),
  issue_id   UUID NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  user_id    UUID NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, issue_id, user_id)
);

Production example. Issue key PROJ-42 is (tenant_id, project.key, issue_number) — never a global serial. Comments cascade-delete with issue; watchers use composite PK to prevent duplicates without a surrogate id explosion.

Trade-offs. UUID PKs: no hot insert on a global sequence, but wider indexes. BIGSERIAL per tenant/project is an alternative if keys stay internal.

Interview. “Add soft delete.” Column + partial unique indexes (WHERE deleted_at IS NULL) — and say how JQL/search excludes tombstones.

Mistake: unique constraint on issue_number alone — collisions across projects on day one.

Normalization vs denormalization

Mental model. Normalization reduces update anomalies; denormalization trades write simplicity for read speed. 3NF is a default for OLTP source of truth — not a religion.

Technical. Normalize: comments in comments, not JSON blob on issues, so pagination and permissions stay row-level. Denormalize deliberately: comment_count on issues maintained by trigger or async counter to avoid COUNT(*) on hot board queries.

Production example. Board column shows assignee avatar + name. Option A: JOIN users on every board row. Option B: denormalized assignee_display snapshot updated when user renames — acceptable if stale name for 30s is OK. Option C: read model table rebuilt from events — when search/board SLO diverges from OLTP.

Trade-offs. Denormalization without an invalidation story becomes silent drift. Say who wins on conflict (source of truth is still users).

Interview. “When is denormalization senior?” When you can name the read path, staleness budget, and reconciliation — not “because JOINs are slow.”

Indexes and why the planner ignores them

Mental model. Indexes are sorted shortcuts maintained on write. The planner picks seq scan vs index scan based on selectivity, statistics, and query shape — not your hope.

Technical. B-tree default. Composite index (tenant_id, project_id, updated_at DESC) supports board queries filtered by tenant+project sorted by recency. Left-prefix rule: index (a,b,c) helps WHERE a and WHERE a,b, not bare WHERE b.

sql
-- Board: issues in project, newest first
CREATE INDEX idx_issues_project_updated
  ON issues (tenant_id, project_id, updated_at DESC, id);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, summary, status, updated_at
FROM issues
WHERE tenant_id = $1 AND project_id = $2
ORDER BY updated_at DESC, id DESC
LIMIT 50;

Why an index might not be used.

  • Function on column: WHERE lower(summary) = 'bug' skips plain index — need expression index or trigram.
  • Low selectivity: “30% of rows match” → seq scan cheaper.
  • Stale stats after bulk import — run ANALYZE.
  • Type coercion: comparing UUID column to text without cast.
  • OR across incompatible predicates — planner gives up or bitmaps multiple indexes.
  • Leading column missing: filter only project_id without tenant_id on composite index.

Production example. Search by summary substring needs pg_trgm GIN index — a btree on summary will not help LIKE '%foo%'.

Trade-offs. More indexes → slower writes and bulk migration time. Index what you measure, not every column in the ER diagram.

Interview. “Query has an index but is slow?” Walk EXPLAIN, selectivity, leading column, and hidden seq scan on sort.

Transactions, isolation, locks, MVCC

Mental model. A transaction groups writes into one atomic unit. Isolation level defines which anomalies you accept. Postgres uses MVCC: readers don’t block writers; writers don’t block readers — but conflicts still happen.

Technical. Read committed (default): each statement sees committed snapshots. Repeatable read: transaction sees consistent snapshot — phantoms still possible on range unless serializable. Row locks: SELECT ... FOR UPDATE for transition workflows.

sql
BEGIN;
SELECT status FROM issues
  WHERE tenant_id = $1 AND id = $2
  FOR UPDATE;
-- validate transition allowed
UPDATE issues SET status = 'In Progress', updated_at = now()
  WHERE tenant_id = $1 AND id = $2;
INSERT INTO issue_history (issue_id, from_status, to_status, actor_id)
  VALUES ($2, 'To Do', 'In Progress', $3);
COMMIT;

MVCC. Updates create new row versions; old versions vacuum away. Long transactions hold back vacuum → bloat and frozen-id pressure. Keep transactions short.

Production example. Two automations transition the same issue: second transaction blocks on FOR UPDATE or fails with serialization error — better than lost update. Idempotency key unique index is another lock story.

Trade-offs. Serializable is safest, hottest under contention. Most Jira-shaped OLTP runs read committed + explicit row locks on contested rows.

Interview. “Board drag-and-drop reorder?” Transaction scope, lock ordering to avoid deadlocks, optimistic versioning with version column.

Mistake: holding a transaction open while calling Slack — connection pool exhaustion, not ‘distributed transactions.’

Replication, partitioning, sharding intro

Mental model. Scale reads with replicas; scale writes with partitioning/sharding or architectural split. Replication is not backup — it is redundancy with lag.

Technical. Primary handles writes; read replicas apply WAL asynchronously. Read-your-writes: route session to primary after mutation, or tolerate lag on board refresh. Partition large tables by tenant_id hash or time (comments by month) for maintenance windows.

Sharding intro. Split tenants across Postgres clusters when single-primary write ceiling or storage cap hits. Router maps tenant_id → shard. Cross-shard joins are avoided — global search becomes a separate system.

Production example. Atlassian-scale: hot tenant on one shard dominates IOPS — isolate noisy neighbor to dedicated shard. Comment history partitioned by created_at makes archival detach cheap.

Trade-offs. Replicas fix read-heavy issue GETs; they do not fix write-heavy comment storms. Sharding is operability tax — don’t shard at 3k RPS.

Interview. “User posts comment, refresh doesn’t show it?” Replica lag vs cache vs read-after-write routing.

SQL Deep Dive

Senior SQL is reading plans, choosing set operations, and knowing when to stop pushing logic into one query. Work the practice items before revealing.

SELECT, JOIN, aggregation

Mental model. SQL is declarative: you describe the relation you want; the optimizer chooses how. Think in sets, not loops.

sql
-- Issues with project key and comment count
SELECT p.key,
       i.issue_number,
       i.summary,
       i.status,
       COUNT(c.id) AS comment_count
FROM issues i
JOIN projects p
  ON p.id = i.project_id AND p.tenant_id = i.tenant_id
LEFT JOIN comments c
  ON c.issue_id = i.id AND c.tenant_id = i.tenant_id
WHERE i.tenant_id = $1
  AND p.key = 'PROJ'
GROUP BY p.key, i.issue_number, i.summary, i.status, i.id
HAVING COUNT(c.id) >= 5
ORDER BY comment_count DESC
LIMIT 20;

Production example. Always join on tenant_id as well as fk id — defense in depth against cross-tenant bugs if a stray UUID appears.

Trade-offs. HAVING filters after aggregation; put row filters in WHERE when possible so less data aggregates.

Interview. “Explain this query plan verbally.” Start from driving table, join order, aggregation, sort.

Subqueries, CTEs, window functions

Mental model. CTEs clarify steps; window functions compute per-row analytics without collapsing rows like GROUP BY.

sql
-- Latest comment per issue (Postgres DISTINCT ON)
SELECT DISTINCT ON (c.issue_id)
       c.issue_id, c.id, c.body, c.created_at
FROM comments c
WHERE c.tenant_id = $1
ORDER BY c.issue_id, c.created_at DESC, c.id DESC;

-- Same with window function
SELECT issue_id, id, body, created_at
FROM (
  SELECT c.*,
         ROW_NUMBER() OVER (
           PARTITION BY c.issue_id
           ORDER BY c.created_at DESC, c.id DESC
         ) AS rn
  FROM comments c
  WHERE c.tenant_id = $1
) t
WHERE rn = 1;
sql
-- Running count of open issues per project by week
SELECT date_trunc('week', i.created_at) AS week,
       p.key,
       COUNT(*) FILTER (WHERE i.status != 'Done') AS open_issues
FROM issues i
JOIN projects p ON p.id = i.project_id AND p.tenant_id = i.tenant_id
WHERE i.tenant_id = $1

Production example. Activity feed “last actor per issue” for 10k issues: window + index on (tenant_id, issue_id, created_at DESC) — not correlated subquery per row in app code.

Trade-offs. CTEs before Postgres 12 were optimization fences; modern planner can inline — still prefer readability when complex.

Interview practice — SQL

Practice 1

Why might a query be slow despite having an index?

Answer. The index may not match the predicate (function wrap, wrong leading column, implicit cast), the planner may prefer seq scan due to high selectivity or stale statistics, the query may sort/limit in a way the index cannot satisfy, or the slowness is lock wait / IO bloat — not missing index. Always EXPLAIN (ANALYZE) with production-like parameters.

Common mistake. Adding another index without reading EXPLAIN — you accumulate write overhead and still seq scan.

Practice 2

Latest record per user (e.g. most recent comment each author made)

Answer. Use DISTINCT ON (author_id) ... ORDER BY author_id, created_at DESC in Postgres, or ROW_NUMBER() OVER (PARTITION BY author_id ORDER BY created_at DESC) in a subquery filtered to rn=1. Index (tenant_id, author_id, created_at DESC). Avoid correlated subqueries per author in application loops.

Common mistake. Grouping without tie-breaker id — two comments same timestamp return arbitrary row.

Practice 3

Paginate millions of rows without OFFSET death

Answer. Keyset pagination: WHERE (updated_at, id) < ($cursor_updated, $cursor_id) ORDER BY updated_at DESC, id DESC LIMIT 50. Index must match sort order. O(page size) per page; OFFSET is O(offset).

Common mistake. Using OFFSET 500000 for ‘infinite scroll’ — each page scans half a million rows.

Practice 4

N+1 and join fan-out in SQL

Answer. N+1 is an app pattern: loop issues, query assignee each time — fix with JOIN or batch IN query. Join fanout is SQL: joining issues → comments duplicates issue columns per comment; use aggregation, subquery, or lateral join for comment counts instead of joining all comments when you only need counts.

Common mistake. LEFT JOIN comments then DISTINCT issue id — dedup after explosion instead of preventing explosion.

Practice 5

Find issues with no comments (anti-join)

Answer. SELECT i.* FROM issues i LEFT JOIN comments c ON c.issue_id = i.id AND c.tenant_id = i.tenant_id WHERE i.tenant_id = $1 AND c.id IS NULL. Or NOT EXISTS (SELECT 1 FROM comments c WHERE ...) — often clearer to humans and planner alike.

Common mistake. COUNT(c.id) = 0 with LEFT JOIN without GROUP BY — wrong semantics on multiple joins.

Practice 6

Detect duplicate watchers inserted under race

Answer. Primary key on (tenant_id, issue_id, user_id) makes second insert fail with unique violation — catch and treat as success for idempotent watch. In interview, mention INSERT ... ON CONFLICT DO NOTHING.

Common mistake. SELECT then INSERT in app without unique constraint — race creates duplicates.

Practice 7

Top 3 projects by open issue count per tenant

Answer. Window rank: RANK() OVER (PARTITION BY tenant_id ORDER BY open_count DESC) in a CTE, filter rank <= 3. Or aggregate first then join — avoid counting in window over raw issues twice if expensive.

Common mistake. LIMIT 3 globally instead of per tenant — answers wrong question.

Practice 8

Issue transition audit: show status duration

Answer. Lead/lag window on history table: LEAD(changed_at) OVER (PARTITION BY issue_id ORDER BY changed_at) - changed_at AS duration. Requires immutable history rows, not overwriting status.

Common mistake. Storing only current status — cannot answer ‘how long in QA’ without event log.

Practice 9

When would you refuse to solve this in SQL?

Answer. Full-text relevance ranking across shards, graph traversal (‘all downstream linked issues’), or ML scoring — push to search/graph service. SQL for set operations on owned data; not every hammer is JOIN.

Common mistake. Recursive CTE ten levels deep on production OLTP without index support — kills primary.

Mental model. Start from workflows: list issues by project, get issue by key, add comment, search full text. Each gets a primary store; caches and indexes are derived.

Production example. Issue transition with watchers + automation webhooks: relational transaction on issue + outbox row; search index updates async — eventual search is OK, wrong status is not.

Interview. “Everything in Dynamo?” Push back: name the transaction, the report, and the query you cannot express — senior candidates defend relational source of truth.

Mistake: ‘use Kafka because scalable’ without a consumer story — same as ‘use NoSQL because web scale’ without access patterns.

Hard truths

Distributed Systems Fundamentals

Phase 3 is not “draw Kafka.” It is naming what breaks when the happy path is only 95% of requests — and choosing contracts that survive the other 5%.

Why distributed systems are hard

The lie of distribution. On one machine, failure is binary: the process crashed or it did not. In a distributed system, failure is partial — some requests succeed, some time out, some return stale data, and you cannot tell which category you are in without extra protocol. That ambiguity is the root of most senior-design pain.

Partial failure. Your issue transition API returns 504. Did Postgres commit? Did the outbox row insert? Did the notification worker already fire? Without idempotency keys and durable workflow state, the user clicks again and you double-notify or leave the issue in “In Progress” forever. Partial failure means every step needs a defined “at-least” or “at-most” story.

Network partitions. A partition is not “the internet is down.” It is: group A can talk to the DB primary; group B can only see a replica or nothing. Both sides may still serve traffic. CAP (next section) is really about what you do during that window — not a permanent architectural tattoo.

Latency is never zero. Cross-AZ RTT is milliseconds; cross-region is tens to hundreds. Chatty synchronous graphs (issue service → permissions → audit → search → notify in one request) blow p99 budgets. At 10× traffic, tail latency dominates user experience more than average RPS.

Clocks lie. There is no global “now.” NTP skew, leap seconds, and VM pauses break “last-write-wins” unless you use version vectors, logical clocks, or the database’s transaction ordering. “UpdatedAt from the client” is not a conflict-resolution strategy.

Ordering and duplication. TCP gives ordered bytes between two sockets — not ordered events across services. Messages arrive twice (at-least-once). Retries reorder work. You design consumers to be idempotent and to tolerate gaps, or you pay for single-partition ordering (Kafka partition key) with hot-key cost.

Retries without policy. A retry storm during a brownout can turn a sick dependency into a dead one. Retries need budgets, jitter, idempotency, and circuit breaking — otherwise “make it reliable” becomes “take down the neighbor.”

Coordination cost. Leader election, distributed locks, and two-phase commit buy correctness at the price of latency, operability, and partition behavior. Senior answer: avoid coordination on the hot path; use leases, database constraints, or partition the problem so one writer owns the entity.

Request path (happy): Client → LB → Issue API → Postgres primary → 200 Same request (partial failure): Client → LB → Issue API → Postgres (commit OK) → Search index (timeout) → ??? Did user see success? Is index stale? Will retry duplicate?
Interview sentence: “I assume partial failure on every hop. Timeouts define uncertainty; idempotency and durable state define what we do after uncertainty.”

Retries, duplication, and idempotency on the wire

Duplication is the default. TCP may not duplicate, but HTTP retries, message queues, and mobile clients do. Treat every write as “may arrive twice.”

typescript
// Unsafe: double transition if client retries 504
async function transition(issueId: string, to: string) {
  await db.query('UPDATE issues SET status = $1 WHERE id = $2', [to, issueId]);
}

// Safer: idempotency key + unique constraint
async function transitionIdempotent(issueId: string, to: string, key: string) {
  await db.query(
    `INSERT INTO transitions (issue_id, to_status, idempotency_key)
     VALUES ($1, $2, $3)
     ON CONFLICT (idempotency_key) DO NOTHING`,
    [issueId, to, key]
  );
  // apply from transitions table in one transaction
}

Retry policy. Max attempts, exponential backoff with jitter, retry only idempotent operations or only on known-safe errors (408, 429, 503 with Retry-After). Never retry 400-class business failures blindly.

Cost. Retries multiply load on a degraded system — the reason circuit breakers and load shedding exist. “We’ll just retry three times” without jitter is how Jira-shaped outages become company-wide.

During a split

CAP — Not a Slogan

Partitions are guaranteed. The question is what your system does for the 60 seconds the network lies — not which triangle letter you tattoo on the architecture poster.

CAP — what it actually says

Not a slogan. CAP (Brewer, formalized by Gilbert–Lynch) says: during a network partition, a distributed data store cannot simultaneously provide both linearizable consistency (C) and total availability (A) for every request. You must choose to sacrifice one for the duration of the partition.

C — Consistency (linearizability). All clients see a single ordered timeline of operations. Not “ACID in one Postgres” alone — CAP is about replicated/shared data across nodes when messages are lost or delayed.

A — Availability. Every request to a non-failing node gets a response (not an error) in finite time. Note: a timeout from the client’s view is unavailability even if the server eventually answers.

P — Partition tolerance. The system continues despite arbitrary message loss or delay between nodes. In real clouds, partitions happen — switch misconfig, AZ isolation, cable cut, GC pause causing heartbeat miss. You do not opt out of P in production.

Normal operation (no partition): [App] --write--> [Leader DB] --sync replicate--> [Follower] [App] --read--> [Follower OK if linearizable policy allows] Partition (Leader reachable from AZ-a, not AZ-b): AZ-a apps: still talk to Leader AZ-b apps: see Follower only — stale? elect new leader? refuse writes? CAP question: during partition, do AZ-b clients get CP: error / read-only until quorum (forfeit A) AP: accept writes/reads on both sides (forfeit C — merge later)

Why partitions happen. Not only “region down.” Common causes: asymmetric routing, overloaded link, deployment blip, DNS stale, firewall rule, replica lag mistaken for health. Any distributed store with multiple nodes will hit split-brain risk without quorum rules.

CP vs AP — examples and misconceptions

LeanBehavior under partitionExample systems / patternsProduct fit
CPRefuse or degrade writes/reads without quorumZooKeeper/etcd, Consul, traditional sync-replicated SQL primaryLeader election, payment ledger, strict workflow lock
APStay available on both sides; resolve conflicts laterDynamo-style stores, Cassandra tunable, multi-master with LWWShopping cart, likes, session prefs, badge counts

Jira-shaped classification.

  • Issue permission check — CP bias: better fail closed (“cannot verify role”) than allow unauthorized transition.
  • Notification fan-out queue depth — AP bias: deliver later; don’t block the transition click.
  • Global issue key uniqueness — CP on allocate (DB primary or consensus); not “two regions invent PROJ-123.”

Misconception 1: “Pick 2 of 3 forever.” CAP applies during a partition event. Normal operation can be both consistent and available. Design is: what is your partition mode?

Misconception 2: “CA systems exist.” Without P, it is a single node — not distributed. RDBMS on one server is CA until you replicate.

Misconception 3: “AP means no consistency ever.” AP means availability during partition; you still add RYW, causal merges, and CRDTs after.

Misconception 4: “CP means always down in partition.” CP often means minority partition read-only/unavailable for writes; majority continues with quorum.

Interview line: “We’re not CAP-tagging the whole company AP. This workflow is CP on entitlement, AP on notifications, with explicit merge and idempotency rules.”

Partition drills — what you would do

Drill. Two AZs lose connectivity for 90s. Primary in AZ-a; replica promoted in AZ-b by automation mistake. Both accept writes.

CP response. Require quorum for writes (odd number of nodes); AZ-b without quorum rejects writes; ops fix routing; no split-brain writes.

AP response. Both accept; issue versions diverge; merge with version vectors or last-write-wins + audit; user may see conflict UI.

Cost. CP → short write unavailability, simpler mental model for money/perms. AP → no hard stop, expensive conflict tooling and support.

10×. More nodes ≠ safer. More nodes = more partition scenarios. Prefer odd quorum, fencing tokens, and “source of truth is primary” over clever multi-master unless product demands it.

TTL, invalidation, stampede, penetration, avalanche, hot keys

  • TTL — safety net when invalidation misses a path; not a substitute for delete-on-write on hot entities.
  • Invalidation — hard part is fan-out: one issue change may touch issue, board, search facet, permission cache. Document key naming up front.
  • Cache stampede — hot key expires; 500 pods miss together. Fix: single-flight lock, jittered TTL, refresh-ahead, stale-while-revalidate.
  • Cache penetration — requests for non-existent ids (scrapers). Fix: short TTL null cache, bloom filter, validate id format.
  • Cache avalanche — many keys expire same second (deploy reset TTL). Fix: jitter per key, stagger warmup.
  • Hot keys — viral issue, CEO’s project. Fix: local L1, read replicas, split key read-only copies, request coalescing.

When cache dies at 10×. Every request hits Postgres. Connection pool exhausts, p99 → seconds, retries amplify. Mitigations: circuit breaker to partial JSON, shed non-critical fields, pre-warm after Redis fail-over, rate limit anonymous reads.

Say out loud: “TTL is backup; invalidation on write is the contract. Stale board for 2s is OK; stale permissions is not — don’t cache authz without tight TTL + invalidation.”

Ordering, scaling, replay, lag, delivery semantics

  • Ordering — guaranteed per partition, not global topic. All events for issue-42 need key=issue-42; cross-issue order undefined — usually fine.
  • Scaling — more partitions → more parallel consumers up to partition count. Too many small partitions → overhead. Hot partition if one mega-project dominates keys.
  • Replay — reset offset or new consumer group reads history — killer feature vs classic queue.
  • Consumer lag — records behind real time; alert on lag SLA. Fix: scale consumers (≤ partitions), optimize handler, reject oversized messages.
  • Delivery — at-least-once default (commit after process). Exactly-once needs idempotent producer + transactions + cooperating sink — expensive; often idempotent consumer is enough.

Design example — issue events. Event envelope: { eventId, issueId, type, version, payload, occurredAt }. Partition key = issueId. What Kafka solves vs a queue. Multiple independent readers, ordered shard, durable replay, backpressure via log retention. Operational cost. Cluster tuning, rebalances, schema governance, monitoring lag — don’t pay it for 200 notifications/sec.

When to adopt and when to refuse

Adopt when several teams consume same event stream, replay is a requirement, throughput > single broker queue comfortably, event sourcing/audit trail is first-class.

Refuse (for now) when one background worker drains tasks, no replay, < few k msgs/sec, team lacks ops — SQS/Rabbit + outbox is simpler.

Failure modes. Rebalance storm during deploy, poison message blocking partition if handler throws without skip, disk full on retention misconfig, producer without idempotency duplicates on retry.

Trade-off sentence: “Kafka earns its keep when the second and third consumer appear. For comment email only, I’d use a queue and transactional outbox first.”

When each fits — notifications vs work distribution

Notifications (fan-out). One transition → N watchers. Pub/sub or topic fan-out (SNS → many SQS, Kafka with multiple consumer groups, Redis pub/sub for ephemeral). User-visible latency target is seconds; duplicates handled with idempotent notify id.

Fan-out cost, ordering, and failure

  • Fan-out math — 50 watchers × 500 transitions/min = 25k downstream deliveries/min — rate limit and batch.
  • Ephemeral pub/sub — subscriber offline = message gone; use queue or log for must-deliver.
  • Ordering — pub/sub usually unordered across subscribers; per-user mailbox may need partition key.
  • Backpressure — slow email provider must not block transition; decouple with queue depth metrics and shed.
  • 10× — naive “publish to 10 services sync” recreates distributed monolith; log once, consume independently.
Jira-shaped answer: “Transition writes DB + outbox. Log consumer fans to realtime pub/sub for board and email queue for SMTP. Badge counter is eventual AP — separate path.”

Load Balancing

Direct traffic, shed unhealthy nodes, and scale horizontally — without pretending every algorithm fixes hot keys.

L4 vs L7 load balancing

Mental model. A load balancer is a traffic director with health awareness. L4 (transport) sees IP + port — fast, protocol-agnostic, good for TCP passthrough and WebSocket stickiness at connection level. L7 (application) sees HTTP headers, paths, cookies — you can route /api/* to app tier and /static/* to object storage, terminate TLS, inject headers, and apply WAF rules.

L4IP, port, TCP stateDB proxy, gRPC over TLS passthrough, extreme RPSLower CPU per conn

Jira-shaped. Browser hits an L7 edge that routes /rest/api/* to Node/Java services and static hashed assets to CDN. WebSocket upgrade for live board may terminate at L7 with longer idle timeouts than generic API routes.

Senior sentence: “I’d use L7 at the edge for routing and TLS, and L4 between internal tiers only if we need raw TCP or we’ve measured L7 as the bottleneck — not by default.”

Algorithms: RR, least connections, consistent hashing

Round robin (RR) — simple, stateless, fine when requests are homogeneous and backends are equal. Breaks when one request is 200ms and another is 20s: RR ignores load.

Least connections — sends to the backend with fewest active connections. Better for long-lived requests, WebSockets, and variable latency. Needs shared state or sticky routing at the LB.

Weighted RR / weighted least conn — new smaller instances get fewer connections until warmed.

Consistent hashing — map client key (user id, tenant id, cache key) to a ring of nodes. Adding/removing a node only remaps ~1/N keys. Used for cache partitions, session stores, and some gRPC load balancers — not a substitute for health checks.

Client keys: u1, u2, u3, ... | consistent hash ring [N1]---[N2]---[N3]---[N1] | u2 -> N2 (stable unless N2 dies)

Practice. “Why not always use consistent hashing?” Hot keys: one celebrity tenant still lands on one shard. Health: a dead node’s slice must fail over — you need redundancy on the ring or replication behind each node.

Health checks, sticky sessions, horizontal scaling

Health checks — active (LB probes /health) vs passive (LB marks unhealthy after N 5xx). Deep checks (DB reachable) belong on a separate endpoint from liveness — otherwise a DB blip drains the entire fleet.

Sticky sessions — cookie or connection affinity so a user hits the same app instance. Useful for in-memory session (avoid if you can — use Redis/DB sessions). Dangerous for autoscaling: new instances get no traffic; draining is painful. Prefer stateless app + external session store.

Horizontal scaling — add identical instances behind the LB. Requires: stateless app tier, shared session/cache/DB, connection pool limits per instance, and graceful shutdown (stop accepting, drain in-flight, then SIGTERM).

Edge

Reverse Proxy & CDN

The edge is where TLS, caching policy, and abuse resistance meet — before your app tier pays per byte.

Reverse proxy role

A reverse proxy sits in front of your app servers: terminates TLS, enforces timeouts, compresses, rate-limits, caches, and hides origin topology. Clients see one host; internally you have many pods/regions.

Browser --TLS--> Reverse proxy (edge) |-- cache HIT --> response |-- cache MISS --> origin app --> DB +-- WAF / bot rules

Forward vs reverse. Forward proxy (corporate egress) represents the client. Reverse proxy represents the server. Interview questions mean reverse.

TLS at the edge — certificates rotate at the proxy; origins may use mTLS on a private network. HTTP/2 and HTTP/3 multiplexing happen at the edge; origin may stay HTTP/1.1 behind the mesh.

CDN: hashed assets vs private HTML

CDN caches static and cacheable API responses at PoPs close to users. Two policies dominate frontend-heavy products:

  • Hashed immutable assets — app.[contenthash].js with Cache-Control: public, max-age=31536000, immutable. Safe forever; deploy = new filename.
  • Private HTML / API — Cache-Control: private, no-store or short TTL with Vary: Cookie, Authorization. Never cache authenticated issue HTML as public.

Stale-while-revalidate for semi-static public docs. Surrogate keys (Fastly-style) purge all pages for project X when branding changes.

Jira-shaped. Issue REST JSON is usually origin-only with auth. Attachment downloads may be CDN-backed signed URLs. Confluence public space pages may CDN-cache anonymous HTML; logged-in view is dynamic.

Practice trade-off: “I’d CDN the static bundle and user-generated attachments via signed URLs, not the authenticated issue API — permissions change faster than TTL math allows.”

TypeScript
/** In-memory token bucket — interview reference implementation */
export class TokenBucket {
  private tokens: number;
  private lastRefillMs: number;

  constructor(
    private readonly capacity: number,
    private readonly refillPerSec: number,
  ) {
    this.tokens = capacity;
    this.lastRefillMs = Date.now();
  }

  tryTake(count = 1): boolean {
    this.refill();
    if (this.tokens < count) return false;
    this.tokens -= count;
    return true;
  }

  private refill(): void {
    const now = Date.now();
    const elapsedSec = (now - this.lastRefillMs) / 1000;
    if (elapsedSec <= 0) return;
    this.tokens = Math.min(
      this.capacity,
      this.tokens + elapsedSec * this.refillPerSec,
    );
    this.lastRefillMs = now;
  }
}

/** Sliding window log — accurate, Redis-friendly pattern */
export async function slidingWindowAllow(
  redis: { zremrangebyscore(k: string, min: number, max: number): Promise<void>;
           zcard(k: string): Promise<number>;
           zadd(k: string, score: number, member: string): Promise<void>;
           expire(k: string, sec: number): Promise<void>; },
  key: string,
  limit: number,
  windowMs: number,
): Promise<boolean> {
  const now = Date.now();
  const windowStart = now - windowMs;
  await redis.zremrangebyscore(key, 0, windowStart);
  const count = await redis.zcard(key);
  if (count >= limit) return false;
  await redis.zadd(key, now, `${now}:${Math.random()}`);
  await redis.expire(key, Math.ceil(windowMs / 1000));
  return true;
}

Distributed rate limiting at 1M users

Problem. Each app instance with an in-memory bucket is wrong: users hop instances; attackers rotate IPs. Centralize counters in Redis (or a dedicated rate-limit service) with atomic INCR + EXPIRE or Lua scripts for token bucket.

Client --> API gateway --> rate-limit check (Redis) | allowed --> app | 429 + Retry-After

Design API for 1M users (practice):

  • Dimensions: per API key, per user id, per tenant, per IP (unauthenticated), per route class (read vs write).
  • Headers: X-RateLimit-Limit, Remaining, Reset on every response; 429 when exceeded.
  • Sharding Redis: hash key by tenant to avoid single hot key; local approximate counters (Redis Cell / GCRA) for high-cardinality keys.
  • Fail open vs closed: product choice — billing API fails closed; read-heavy search may fail open with logging if Redis is down.
  • Sync vs async: check synchronously at gateway; heavy abuse analysis async via events.

Numbers. 1M DAU, 100 req/user/day → ~1.2k avg RPS, ~3–5k peak. Redis handles millions of ops/s on a small cluster — the design problem is key cardinality and fairness, not raw throughput.

Senior line: “Rate limits protect the system and set expectations. They are not a substitute for auth, input validation, or queue-based absorption for fan-out work.”

Failure

Reliability Patterns

Systems fail partially. Seniors design for that: timeouts, bounded retries, isolation, and honest degradation.

Redundancy, failover, timeouts, retries

Redundancy — no single instance of anything on the critical path. Multi-AZ as a baseline; multi-region when RTO/RPO demand it.

Failover — automated (health-based DNS/LB) vs manual (runbook). Practice stating RTO: “DNS TTL 60s + warm standby ≈ 2 min user-visible blip.”

Timeouts — every outbound call gets one, shorter than the client’s timeout. Cascading slowness is a timeout budget problem: if A waits 30s for B and B waits 30s for C, one slow leaf stalls the fleet.

Retries — only on idempotent operations or with idempotency keys; cap max attempts; use exponential backoff + jitter so retries don’t align into a retry storm.

TypeScript
function backoffMs(attempt: number, base = 100, cap = 10_000): number {
  const exp = Math.min(cap, base * 2 ** attempt);
  const jitter = Math.floor(Math.random() * exp * 0.3);
  return exp + jitter;
}
Retry storm: SES blips → every app retries email at t=1s → you DDoS yourself. Jitter + queue + circuit breaker.

Circuit breakers, bulkheads, graceful degradation

Circuit breaker — closed (normal) → open (fail fast after error threshold) → half-open (probe). Stops hammering a sick dependency. Pair with fallbacks that are honest (“notifications delayed”) not silent wrong data.

Bulkheads — separate thread pools / connection limits per dependency so one slow search cannot exhaust all DB connections for issue writes.

Graceful degradation — issue transition succeeds; activity stream omits avatar URLs if avatar service is down. Define which features are tier-1 vs tier-2.

Issue PATCH (tier-1) ------> primary DB (reserved pool) |--> audit log queue +--> search indexer (breaker OPEN -> skip, catch up later) +--> email worker (bulkhead: max 50 concurrent)

Practice. “What fails first at 10×?” Usually connection pools, not CPU. Name bulkheads before you name Kubernetes.

Exactly-once intent

Idempotency

At-least-once delivery is reality. Idempotency keys, dedupe tables, and unique constraints make that safe.

Why idempotency matters

Networks retry. Browsers double-submit. Webhooks redeliver. Message queues are at-least-once. Without idempotency, “create charge” twice means angry customers and finance tickets.

Definition. Performing the same operation multiple times with the same logical intent produces the same outcome as once — no duplicate side effects.

HTTP. GET/PUT/DELETE are idempotent by spec; POST is not — so payments and creates need an Idempotency-Key header (Stripe-style) or a natural unique key (order id).

Coordination

Distributed Locks

Locks across machines are leases with failure modes. Know Redis patterns — and when to refuse them.

Why locks are hard across machines

On one machine, a mutex is cheap and well-defined. Across machines you inherit: partial failure (holder dies mid-critical-section), clock skew, network partitions, and GC pauses (your process stops while still “holding” the lock).

A “lock” in Redis is really a lease: SET key token NX PX ttl. If TTL expires before work finishes, another worker can enter — you may run two writers unless you validate the token on unlock and use fencing.

Martin Kleppmann’s critique stands: a naive Redis lock is not a safe distributed lock without careful token checks, TTL tuning, and often fencing tokens on the storage layer.

Redis locks, lease, TTL, fencing

Correct-ish pattern:

  1. Acquire with random token: SET lock:issue:42 <token> NX PX 30000
  2. Do work; refresh lease if long (extend only if token matches — Lua script)
  3. Release with compare-and-del Lua: delete only if value == token
  4. Fencing token — monotonic counter passed to DB/storage so stale lock holders cannot commit (e.g. issue version must be > last seen fence)
TypeScript
// Release only if we still own the lock (Redis Lua sketch as TS logic)
async function releaseLock(redis: Redis, key: string, token: string): Promise<boolean> {
  const script = `
    if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
    else
      return 0
    end`;
  const result = await redis.eval(script, 1, key, token);
  return result === 1;
}

When to AVOID distributed locks

Prefer, in order:

  • Unique constraints + idempotent upsert — one row wins; others get conflict or no-op
  • Single writer per partition — Kafka partition key = issue id; ordering without locks
  • Optimistic concurrency — UPDATE … WHERE version = $expected
  • DB advisory locks — if all writers hit same Postgres, pg_advisory_xact_lock is simpler than Redis + fencing

Use a distributed lock when you truly need mutual exclusion across heterogeneous workers on a resource Redis doesn’t own — and you accept ops complexity. Scheduled cron “only one leader” is a common acceptable case (with lease + watchdog).

Interview: “I’d try optimistic locking on the issue row before I’d introduce Redlock for Jira transitions.”

Data scale

Replication & Sharding

Replicas for read scale; shards for write scale — each with lag, hot spots, and rebalance tax.

Primary-replica and read replicas

Primary-replica — one writer (primary), N read replicas streaming WAL/binlog. Reads scale; writes don’t. Replication lag means a user may not see their own write on a replica — need read-your-writes routing (sticky to primary after write, or session token).

Multi-primary — writes on multiple nodes; conflict resolution required. Useful geo-write latency; painful for relational invariants. Most Jira-shaped OLTP stays single-primary per shard.

Writes ----> Primary ---- WAL ----> Replica 1 (reads) |-------------> Replica 2 (reads) +-------------> Replica 3 (reports)

Vertical vs horizontal partitioning, sharding

Vertical partitioning — split by table/service (issues DB, attachments metadata, audit). Good first split.

Horizontal partitioning (sharding) — split rows by key (tenant_id, project_id). Each shard is a full DB with its own primary.

Hot shards — one mega-tenant dominates a shard. Mitigations: sub-shard by project, dedicated shard for whale tenant, rate limits, async denormalization.

Rebalancing — move ranges with dual-write or copy + catch-up + cutover. Plan years before you need it; consistent hashing reduces remapping on add/remove.

tenant_id hash --> shard A (tenants 0-999) |--> shard B (tenants 1000-1999) |--> shard C (whale tenant isolated)
When sharding is premature: < few TB, < ~10k sustained write RPS on well-indexed Postgres, team can’t operate cross-shard queries. Vertical split + replicas + cache first.

Practice: shard or not?

Consistent hashing — route shard = ring(tenant_id). Adding a node moves only adjacent keys. Often implemented at app router or Vitess/Citus layer.

Cross-shard queries — avoid. Design access patterns per shard key. Global search/analytics → separate derived store.

Practice question. “10M issues, 50k writes/s peak?” Probably sharded by project_id or tenant_id. “500 writes/s?” Replicas + partitioning large audit table maybe; not 16 shards day one.

Cross-service writes

Distributed Transactions

You don’t get ACID across services. Sagas, outbox, and idempotent consumers are the senior toolkit.

Two-phase commit and its costs

2PC — coordinator prepares all participants (hold locks), then commits or aborts. Blocks on coordinator failure; participants hold locks during uncertainty → throughput collapse under latency.

Seniors rarely propose 2PC across microservices in interviews. It’s CP, slow, and operationally scary. Use when a single datastore can own the transaction boundary.

Sagas: orchestration vs choreography

Saga — sequence of local transactions with compensating actions. Issue transition saga: (1) update issue (2) emit event (3) index search. If (3) fails, retry (3); don’t undo (1) if business says transition stands.

Orchestration — central workflow engine decides next step. Choreography — services react to events. Orchestration easier to debug; choreography fewer coupling points but harder tracing.

Transition API --> update DB (local tx) --> outbox row (same local tx) --> relay --> search worker --> index | fail --> retry / DLQ (no 2PC)

Transactional outbox, inbox, dual-write

Dual-write problem — write DB then publish to Kafka: crash between them → inconsistency. Fix: transactional outbox — insert event row in same DB transaction as business write; separate relay publishes and marks sent.

Inbox pattern — consumer stores incoming event id uniquely before processing (pairs with idempotency).

Identity

AuthN & AuthZ

Sessions and tokens get users in; RBAC/ABAC and tenant scoping keep data in the right place.

Sessions, OAuth, JWT, S2S

Session cookies — server-side session store (Redis/DB), HttpOnly Secure SameSite cookie. Good for browser apps; CSRF protection required. Atlassian cloud sessions are long-lived with refresh and device binding patterns.

OAuth 2 / OIDC — delegate identity to IdP; your app gets tokens. Use authorization code + PKCE for SPAs. Scopes express delegated permission, not your internal RBAC entire matrix.

JWT — signed claims, stateless verification. Watch expiry, rotation, revocation (short TTL + refresh, or introspection). Don’t put secrets in JWT payload — it’s base64, not encrypted.

S2S (service-to-service) — mTLS, signed service JWTs, or workload identity (IAM). Never share a user cookie between services.

RBAC/ABAC, token storage, tenant isolation

RBAC — role → permissions. ABAC — attributes (tenant, project, issue security level). Jira mixes both: project role + issue-level security.

Token storage (browser). Access token in memory; refresh in HttpOnly cookie or secure rotation endpoint. Avoid localStorage for bearer tokens (XSS exfiltration).

Tenant isolation. Every query includes tenant_id from auth context — never from client body alone. Row-level security in Postgres is a defense-in-depth layer, not a substitute for app checks.

Defensive only: assume tokens leak and XSS happens — minimize blast radius with short TTL, scoped permissions, and server-side enforcement on every mutation.

Derived read model

Search

Fast text retrieval is a separate store fed by events — permissions still come from truth.

Inverted index, tokenization, ranking, shards

Inverted index — term → list of doc ids with positions/frequencies. Tokenization: lowercase, stemming, stop words, language analyzers. Ranking — TF-IDF/BM25 + boosts (title > body, recency, project match).

Shards/replicas — shard = horizontal split of index; replica = copy for read scale and failover. Routing key often tenant_id or project_id to localize queries.

Practice: Search Jira issues

Node.js Architecture

Senior Node is not “JavaScript on a server” — it is event-driven I/O, explicit pooling, failure-aware shutdown, and knowing exactly what blocks the loop.

Event loop, async I/O, and what blocks

Mental model. Node is single-threaded JavaScript on a multi-threaded libuv runtime. Your code runs on the event loop; libuv handles thread-pool I/O (fs, dns, some crypto) and OS async notifications (sockets). Throughput comes from non-blocking I/O, not from parallel JS.

Phases (simplified): timers → pending callbacks → idle/prepare → poll (I/O) → check → close Request ──► epoll/kqueue ──► callback queued ──► event loop tick ──► your .then / handler

What blocks the event loop (say in interview).

  • CPU-heavy sync JS: JSON.parse of 50MB, regex catastrophic backtracking, tight loops
  • Sync native calls: bcrypt.hashSync, large fs.readFileSync, child_process.execSync
  • Massive microtask chains starving the loop
  • Not blocking: awaited network I/O, Postgres pool query, Redis — threads/pool work elsewhere

  4. Stop background job consumers / cron

export function wireGracefulShutdown(app: { close(): Promise<void> }, deps: {
  pool: { end(): Promise<void> };
  jobWorker: { stop(): Promise<void> };
}) {
  let shuttingDown = false;
  app.addHook("onRequest", async (_req, reply) => {
    if (shuttingDown) reply.code(503).send({ error: "shutting_down" });
  });

  const shutdown = async (signal: string) => {
    if (shuttingDown) return;
    shuttingDown = true;
    app.log.info({ signal }, "shutdown start");
    await app.close();
    await deps.jobWorker.stop();
    await deps.pool.end();
    process.exit(0);
  };

  process.on("SIGTERM", () => void shutdown("SIGTERM"));
  process.on("SIGINT", () => void shutdown("SIGINT"));
}

Hints. Refill on every tryTake, not on a timer — fewer moving parts. Store lastRefillMs. Cap tokens at capacity. For 429, compute seconds until one token arrives for Retry-After.

TypeScript
export class TokenBucket {
  private tokens: number;
  private lastRefillMs: number;

  constructor(
    private readonly capacity: number,
    private readonly refillPerSec: number,
  ) {
    this.tokens = capacity;
    this.lastRefillMs = Date.now();
  }

  tryTake(count = 1): boolean {
    this.refill();
    if (this.tokens < count) return false;
    this.tokens -= count;
    return true;
  }

  secondsUntilAvailable(count = 1): number {
    this.refill();
    const deficit = count - this.tokens;
    if (deficit <= 0) return 0;
    return Math.ceil(deficit / this.refillPerSec);
  }

  private refill(): void {
    const now = Date.now();
    const elapsedSec = (now - this.lastRefillMs) / 1000;
    if (elapsedSec <= 0) return;
    this.tokens = Math.min(this.capacity, this.tokens + elapsedSec * this.refillPerSec);
    this.lastRefillMs = now;
  }
}

type Reply = { status(n: number): { header(k: string, v: string): unknown } };

export function rateLimitHook(bucket: TokenBucket) {
  return async (_req: unknown, reply: Reply): Promise<void> => {
    if (bucket.tryTake()) return;
    const wait = bucket.secondsUntilAvailable();
    reply.status(429).header("Retry-After", String(wait));
    throw new Error("rate_limit_exceeded");
  };
}

Explanation. Token bucket models sustained rate plus burst — the interview-friendly choice for public APIs. Refill-on-use avoids setInterval drift and keeps the class testable without fake timers.

Failure cases. Per-process buckets diverge behind a load balancer — two instances double effective quota. Clock skew across machines matters only after you centralize in Redis. Returning 429 without Retry-After causes thundering herds.

Performance. O(1) per request. Memory is O(keys) — one bucket per tenant/user if you map keys to instances. At scale, move token state to Redis with Lua for atomic refill+decrement.

  maxAttempts?: number;
  baseDelayMs?: number;
  maxDelayMs?: number;
  retryOn?: (err: unknown, res?: Response) => boolean;

const sleep = (ms: number, signal?: AbortSignal) =>
  new Promise<void>((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);
    const t = setTimeout(resolve, ms);
    signal?.addEventListener("abort", () => { clearTimeout(t); reject(signal.reason); }, { once: true });
  });

function parseRetryAfter(res: Response): number | undefined {
  const h = res.headers.get("Retry-After");
  if (!h) return undefined;
  const sec = Number(h);
  if (!Number.isNaN(sec)) return sec * 1000;
  const when = Date.parse(h);
  return Number.isNaN(when) ? undefined : Math.max(0, when - Date.now());
}

const defaultRetryOn = (err: unknown, res?: Response) => {
  if (res) return res.status === 429 || res.status >= 500;
  return err instanceof TypeError; // fetch network failure
};

export async function withRetry<T>(
  fn: (attempt: number) => Promise<T>,
  opts: RetryOpts = {},
): Promise<T> {
  const maxAttempts = opts.maxAttempts ?? 4;
  const baseDelayMs = opts.baseDelayMs ?? 200;
  const maxDelayMs = opts.maxDelayMs ?? 8_000;
  const retryOn = opts.retryOn ?? defaultRetryOn;
  let lastErr: unknown;

  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      return await fn(attempt);
    } catch (err) {
      lastErr = err;
      const res = (err as { response?: Response }).response;
      if (attempt === maxAttempts - 1 || !retryOn(err, res)) throw err;
      const retryAfter = res ? parseRetryAfter(res) : undefined;
      const exp = Math.min(maxDelayMs, baseDelayMs * 2 ** attempt);
      const delay = retryAfter ?? Math.floor(Math.random() * exp);
      await sleep(delay, opts.signal);
    }
  }
  throw lastErr;
}

Explanation. Full jitter spreads retry times so a fleet of clients does not realign after an outage — the classic fix for retry storms. Honoring Retry-After is part of being a good API citizen.

Failure cases. Retrying POST without idempotency keys creates duplicates. Infinite retries on 400-class errors waste resources. Ignoring AbortSignal leaves hung shutdown during deploy.

Performance. Worst case latency ≈ sum of delays — cap attempts and max delay explicitly. For high fan-out workers, use per-destination circuit breakers alongside retries.

}

export class CircuitBreaker {
  private state: CBState = "closed";
  private failures = 0;
  private openedAt = 0;
  private halfOpenInFlight = false;

  constructor(
    private readonly failureThreshold = 5,
    private readonly cooldownMs = 30_000,
    private readonly isFailure: (err: unknown) => boolean = () => true,
  ) {}

  getState(): CBState { return this.state; }

  async exec<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === "open") {
      if (Date.now() - this.openedAt < this.cooldownMs) throw new CircuitOpenError();
      this.state = "half-open";
      this.halfOpenInFlight = false;
    }
    if (this.state === "half-open") {
      if (this.halfOpenInFlight) throw new CircuitOpenError();
      this.halfOpenInFlight = true;
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (err) {
      if (this.isFailure(err)) this.onFailure();
      throw err;
    } finally {
      if (this.state === "half-open") this.halfOpenInFlight = false;
    }
  }

  private onSuccess(): void {
    this.failures = 0;
    this.state = "closed";
  }

  private onFailure(): void {
    this.failures += 1;
    if (this.state === "half-open" || this.failures >= this.failureThreshold) {
      this.state = "open";
      this.openedAt = Date.now();
      this.failures = 0;
    }
  }
}

Explanation. The breaker protects the caller and gives the downstream time to recover. Half-open is the subtle state — allow exactly one trial request, not a full traffic slice.

Failure cases. Counting 4xx as failures opens the circuit on client bugs. Shared breaker state per process means each pod learns independently — acceptable for interview; production may need a shared sliding window.

Performance. Fail-fast while open is O(1) — saves thread pool and sockets during outages. Pair with bulkheads so one dependency cannot trip every breaker.

type Job<T> = { id: string; payload: T; attempts: number; visibleAt: number; maxAttempts: number };

export class MemoryQueue<T> {
  private jobs = new Map<string, Job<T>>();
  dlq: Job<T>[] = [];

  constructor(
    private readonly visibilityMs = 30_000,
    private readonly maxAttempts = 5,
  ) {}

  enqueue(id: string, payload: T): void {
    if (this.jobs.has(id)) return; // dedupe by id
    this.jobs.set(id, {
      id, payload, attempts: 0, visibleAt: Date.now(), maxAttempts: this.maxAttempts,
    });
  }

  poll(now = Date.now()): Job<T> | undefined {
    for (const job of this.jobs.values()) {
      if (job.visibleAt <= now) {
        job.visibleAt = now + this.visibilityMs;
        return { ...job };
      }
    }
    return undefined;
  }

  ack(id: string): void {
    this.jobs.delete(id);
  }

  nack(id: string): void {
    const job = this.jobs.get(id);
    if (!job) return;
    job.attempts += 1;
    if (job.attempts >= job.maxAttempts) {
      this.jobs.delete(id);
      this.dlq.push(job);
      return;
    }
    job.visibleAt = Date.now() + this.visibilityMs;
  }
}

Explanation. Visibility timeout gives at-least-once semantics: if the worker dies mid-handle, the job reappears. DLQ preserves poison messages for inspection instead of infinite spin.

Failure cases. Process crash after handle but before ack → duplicate processing. In-memory queue vanishes on restart — fine for sketch, not production. No ordering guarantee across workers unless single partition.

Performance. Poll scan is O(n) — production queues partition by key. Back-pressure: cap queue depth and reject enqueue with 503 when full.

TypeScript
import { Worker } from "node:worker_threads";

type Task<T, R> = { payload: T; resolve(v: R): void; reject(e: unknown): void };

export class WorkerPool<T, R> {
  private workers: Worker[] = [];
  private idle: Worker[] = [];
  private queue: Task<T, R>[] = [];
  private active = 0;
  private closed = false;

  constructor(private readonly size: number, private readonly workerScript: string) {
    for (let i = 0; i < size; i++) this.spawn();
  }

  private spawn(): void {
    const w = new Worker(this.workerScript);
    w.on("message", (msg: { ok: boolean; result?: R; error?: string }) => {
      this.active -= 1;
      const task = (w as Worker & { current?: Task<T, R> }).current;
      if (!task) return;
      (w as Worker & { current?: Task<T, R> }).current = undefined;
      if (msg.ok) task.resolve(msg.result as R);
      else task.reject(new Error(msg.error ?? "worker_error"));
      this.idle.push(w);
      this.pump();
    });
    this.idle.push(w);
  }

  run(payload: T): Promise<R> {
    if (this.closed) return Promise.reject(new Error("pool_closed"));
    return new Promise((resolve, reject) => {
      this.queue.push({ payload, resolve, reject });
      this.pump();
    });
  }

  private pump(): void {
    while (this.idle.length && this.queue.length) {
      const w = this.idle.pop()!;
      const task = this.queue.shift()!;
      (w as Worker & { current?: Task<T, R> }).current = task;
      this.active += 1;
      w.postMessage(task.payload);
    }
  }

  async shutdown(): Promise<void> {
    this.closed = true;
    while (this.active > 0) await new Promise((r) => setTimeout(r, 10));
    await Promise.all(this.workers.map((w) => w.terminate()));
    this.workers = [];
    this.idle = [];
  }
}

Explanation. Worker pools isolate CPU-heavy work (PDF render, markdown parse, image resize) from the event loop. Pool size ≈ CPU cores — more threads add context-switch cost without throughput gain.

Failure cases. Large postMessage payloads copy memory — prefer SharedArrayBuffer or file paths. Uncaught worker exceptions must reject the in-flight task and respawn worker. Shutdown race: reject queued tasks explicitly if you need stricter semantics.

Performance. Throughput bounded by cores; queue depth adds latency under burst — expose queue length metric. For very small tasks, thread overhead may exceed benefit — batch in worker.

type Stored = { statusCode: number; body: string; requestHash: string };

export interface IdempotencyStore {
  get(key: string): Promise<Stored | null>;
  putIfAbsent(key: string, value: Stored, ttlSec: number): Promise<boolean>;
}

function hashBody(body: unknown): string {
  return createHash("sha256").update(JSON.stringify(body ?? null)).digest("hex");
}

export function idempotencyMiddleware(store: IdempotencyStore, ttlSec = 86_400) {
  return async (
    req: { method: string; headers: Record<string, string | undefined>; body: unknown },
    handler: () => Promise<{ statusCode: number; body: unknown }>,
  ): Promise<{ statusCode: number; body: unknown; replayed: boolean }> => {
    const method = req.method.toUpperCase();
    if (method !== "POST" && method !== "PATCH") return { ...(await handler()), replayed: false };

    const key = req.headers["idempotency-key"] ?? req.headers["Idempotency-Key"];
    if (!key) return { ...(await handler()), replayed: false };

    const requestHash = hashBody(req.body);
    const existing = await store.get(key);
    if (existing) {
      if (existing.requestHash !== requestHash) {
        return { statusCode: 409, body: { error: "idempotency_key_reuse" }, replayed: true };
      }
      return { statusCode: existing.statusCode, body: JSON.parse(existing.body), replayed: true };
    }

    const result = await handler();
    const stored: Stored = {
      statusCode: result.statusCode,
      body: JSON.stringify(result.body),
      requestHash,
    };
    const won = await store.putIfAbsent(key, stored, ttlSec);
    if (!won) {
      const again = await store.get(key);
      if (again && again.requestHash === requestHash) {
        return { statusCode: again.statusCode, body: JSON.parse(again.body), replayed: true };
      }
      return { statusCode: 409, body: { error: "idempotency_conflict" }, replayed: true };
    }
    return { ...result, replayed: false };
  };
}

Explanation. Idempotency keys turn at-least-once networks into exactly-once effect from the client’s perspective. Store response, not just a lock — clients retry to get the original 201 body.

Failure cases. Store down on first attempt → client retries may double-create unless DB has unique constraint backup. Key scoped per tenant/user — global keys collide across customers. Caching 500 responses traps clients in failure.

Performance. One Redis GET/SET per POST — negligible vs DB write. Prune keys by TTL; monitor cardinality per tenant for abuse.

function sign(payload: CursorPayload): string {

  const [body, sig] = token.split(".");
  if (!body || !sig) return null;

  const a = Buffer.from(sig);

): Promise<{ status: number; body: unknown }> {
  const sig = headers["x-signature-256"] ?? headers["X-Signature-256"];
  if (!verifySig(rawBody, sig, secret)) {
    return { status: 401, body: { error: "invalid_signature" } };
  }

  const event = JSON.parse(rawBody.toString("utf8")) as { id: string; type: string; data: unknown };
  if (!event.id) return { status: 400, body: { error: "missing_event_id" } };

  if (await store.seen(event.id)) {
    return { status: 200, body: { ok: true, duplicate: true } };
  }

  await store.mark(event.id, 72 * 3600);
  queue.enqueue(event.id, event);
  return { status: 200, body: { ok: true } };
}

Explanation. Webhooks are at-least-once — signature proves authenticity, id store proves dedupe. Fast 200 + async worker is the production pattern for payment and integration providers.

Failure cases. Marking seen before enqueue loses event if queue write fails — production uses outbox or mark-after-enqueue with reconciler. Raw body must be preserved — re-parsing JSON changes whitespace and breaks HMAC.

Performance. Verify + dedupe is O(1). Worker concurrency scales independently. Rate-limit ingress per sender IP.

type CounterStore = {
  incrBy(key: string, delta: number): Promise<number>;
  get(key: string): Promise<number>;
};

function shardIndex(key: string, shards: number): number {
  let h = 0;
  for (let i = 0; i < key.length; i++) h = (h * 31 + key.charCodeAt(i)) >>> 0;
  return h % shards;
}

export class DistributedCounter {
  constructor(
    private readonly store: CounterStore,
    private readonly shards = 8,
  ) {}

  private shardKey(key: string, i: number) { return `${key}:s${i}`; }

  async increment(key: string, delta = 1): Promise<number> {
    const i = shardIndex(key, this.shards);
    return this.store.incrBy(this.shardKey(key, i), delta);
  }

  async get(key: string): Promise<number> {
    const parts = await Promise.all(
      Array.from({ length: this.shards }, (_, i) => this.store.get(this.shardKey(key, i))),
    );
    return parts.reduce((a, b) => a + b, 0);
  }
}

Explanation. Redis INCR is atomic per key — sharding spreads hot-key write load (view counts on viral issue). Reads sum shards — slight race gives approximate total, acceptable for display metrics.

Failure cases. Non-atomic multi-shard increment during read can drift — fine for views, wrong for billing. Flush job double-counts if not reset keys atomically — use GETSET or dedicated flush script.

Performance. Write O(1) to one shard; read O(shards) — keep shard count modest (8–64). HyperLogLog alternative when exact count unnecessary.

Interview follow-ups. How is this different from a CRDT? When would you use Kafka aggregation instead of Redis counters?

Design Jira

Problem

Design a multi-tenant issue tracking system: projects, issues, workflows, boards, comments, attachments, search, notifications, and audit. Users collaborate in real time on boards; admins configure permissions and workflows per project.

Functional requirements

Create/read/update issues; workflow transitions with guards; Kanban/Scrum boards; JQL-style search; comments and @mentions; watchers; file attachments; project/space permissions (roles); webhooks and REST API; plugin extension points (out of hot path).

Clarifying questions

Multi-tenant SaaS or single org? Real-time board mandatory or poll OK? JQL full grammar or subset? Plugins in scope? Mobile offline? Compliance (SOC2, data residency)? Expected largest tenant size?

Scale estimates

Assume 500k tenants, 5M DAU, 80 req/user/day → 400M req/day → ~4,600 avg RPS, peak ~14k RPS (3×). Read/write 15:1 → ~900 WPS peak. Issues: 2B total, 50M active; avg issue row 4 KB metadata + 20 KB comments over life. New issues 500k/day. Attachments 200k/day × 2 MB avg → 400 GB/day to object store. Search: 10% of reads → 1.4k search RPS peak.

API design

REST resources: POST /projects, POST /issues, GET /issues/{{id}}, PATCH /issues/{{id}} with If-Match: version, POST /issues/{{id}}/transitions with idempotency-key header, GET /boards/{{id}}/snapshot, GET /search?jql=... cursor pagination. WebSocket /live/board/{{id}} for card moves. Errors: 409 on version conflict, 403 on permission, 422 on invalid transition.

Data model

Core OLTP (Postgres): tenants, projects, issues (tenant_id, project_id, status, version, rank), transitions, comments, permissions (subject, resource, action), watchers. Denormalize issue_search_doc for index pipeline. Attachments metadata in DB, blobs in S3. Audit: append-only audit_events (tenant_id, actor, action, entity, payload_hash, ts).

High-level architecture

Client → CDN (static) / API Gateway (auth, rate limit) → Issue Service (modular monolith or core domain) → Postgres primary (writes) + replicas (reads) → Redis (session, board snapshot cache, idempotency) → Kafka: issue.events → Search indexer, Notification worker, Audit sink, Webhook dispatcher → Elasticsearch (search) / OpenSearch → S3 (attachments) → WS fan-out service (board presence + moves)

Component deep dive

Transition engine. Validate permission + workflow guard in one DB transaction: read issue version, check allowed transition, update status/rank, insert transition row, emit outbox event. Never call email synchronously. Multi-tenancy. Every table carries tenant_id; connection pool sets SET app.tenant_id or ORM scoping; cross-tenant queries impossible at API layer; largest tenants may get dedicated shard or noisy-neighbor rate limits. Permissions. RBAC (project roles) + issue security levels + optional object-level grants; evaluated server-side on every API — never trust UI hide alone; cache decisions per (user, project) TTL 120s, bust on role change event. Search. Async index of summary, description, comments; query ES then filter by permission bitmap or store allowed_principals[] in doc with periodic reconcile job. Notifications. Transition emits issue.assigned etc. to Kafka; fan-out to watchers async; respect user channel prefs and digest. Audit. Append-only audit_events: actor, IP, action, before/after hash, immutable; stream to SIEM; 7-year retention with monthly partitions.

Caching

Redis: issue detail (TTL 60s, invalidate on write); board snapshot (TTL 30s, key=board_id+filter_hash); permission bitmap cache (TTL 120s). CDN: static assets immutable; attachment downloads via signed URL. Cache-aside for issue GET; stampede protection via singleflight on hot keys.

Queues & async

Kafka topic issue.events partitioned by issue_id (ordering per issue). Consumers: search indexer (at-least-once, idempotent upsert by issue_id+version), notification (fan-out to watchers queue), audit (append), webhooks (retry + DLQ). Outbox pattern from Issue Service ensures no lost events if crash after commit.

Database

Postgres primary for OLTP; read replicas for issue GET and board load. Partition audit_events by month. Consider sharding by tenant_id when single primary exceeds ~10k WPS — cross-tenant queries (admin) go to federated layer. Connection pooling (PgBouncer) mandatory at scale.

Consistency

Issue transition: strong consistency + RYW for actor (return new state in PATCH). Board for other users: eventual (WS or 2s poll). Search: eventual bounded 30s. Notifications: eventual. Permissions: read from primary on write path; cache on read with invalidation on grant/revoke.

Failure scenarios

Postgres primary down → fail writes, serve stale reads from replica with banner. Redis down → bypass cache, higher latency. Kafka lag → search stale, notifications delayed — alert on consumer lag. WS node loss → client reconnect + catch-up REST. Duplicate transition → idempotency key prevents double apply.

Security

Tenant_id on every query; row-level security in Postgres optional defense-in-depth. OAuth/API tokens scoped per tenant. Encrypt attachments at rest; TLS everywhere. Audit all permission changes, issue deletes, admin impersonation with actor + target. Plugin iframe sandbox + CSP. Rate limit per tenant API key. SOC2: logical separation, encryption keys per tenant tier optional.

Observability

SLI: issue view p99, transition success rate, search lag, notification delivery time. Trace id from gateway through outbox to consumers. Metrics: RPS per tenant (hot tenant detection), Kafka lag, cache hit rate, WS connections. SLO dashboards per tenant tier.

Scaling strategy

Horizontal stateless API pods; scale WS separately. Read replicas for GET; scale Kafka consumers with lag. ES data nodes for search. Multi-AZ; active-passive DR for Postgres with RPO 5 min. Largest tenant → dedicated shard or rate limit tier.

Bottlenecks at 10×

Hot tenant on one shard; permission check N+1 on board load; WS fan-out for 500 users on one board; JQL on OLTP without index; outbox table write amplification; attachment egress costs.

Trade-offs

Modular monolith vs microservices early (monolith + async extract search). Eventual search vs synchronous index (async wins). OT vs last-write for description (version + 409). Real-time WS vs SSE vs poll (WS for board, poll for low-collab).

Follow-ups

Workflow DSL design; custom fields schema; marketplace plugin isolation; data export GDPR; cross-project boards; mobile sync.

0–5 min: clarify tenant scale, real-time, search scope. 5–12 min: numbers + APIs. 12–20 min: diagram + data model. 20–35 min: deep dive transition + permissions + search/async. 35–42 min: failures + security + audit. 42–45 min: trade-offs + evolution.

Backend / Node / Distributed Question Bank

Practice questions for senior backend interviews — Node.js, databases, distributed systems, caching, messaging, reliability, and security. Answer aloud, then reveal. Not claimed as official interview questions from any company.

mediumnodeQ1

1. What blocks the Node.js event loop in production?

Short answer. CPU-bound sync work, large JSON.parse/stringify, sync bcrypt, unbounded loops, native addons doing sync I/O.

Deep explanation. The event loop runs one JS thread. Any synchronous CPU or blocking libuv call delays timers, sockets, and health checks. At scale, one hot handler stalls all requests on that worker. Fix: worker threads, offload to queue, bounded work, streaming.

Common misconception. Only database calls block Node.

Senior follow-up. How do you detect event-loop lag in production?

easynodeQ2

2. Why use a connection pool for Postgres in Node?

Short answer. Opening a TCP+TLS+auth connection per request is expensive; pools reuse connections with bounded concurrency.

Deep explanation. Pool size ≈ (cores × 2) is a starting heuristic, but real limit is Postgres max_connections and query latency. Too large a pool → DB contention; too small → queueing in app. Monitor wait time on pool.acquire().

Common misconception. Unlimited connections scale linearly.

Senior follow-up. What happens when pool is exhausted under load?

mediumnodeQ3

3. How does cluster module help — and what does it not fix?

Short answer. Forks workers per CPU to use multiple cores; each worker has its own event loop and memory.

Deep explanation. It does not share in-memory state — sessions in RAM need Redis/sticky LB. It does not help one worker blocked by CPU. Graceful shutdown must drain connections before exit.

Common misconception. cluster makes Node multi-threaded for JS.

Senior follow-up. When would you prefer containers over cluster?

hardnodeQ4

4. Design graceful shutdown for a Node API.

Short answer. Stop accepting, drain in-flight requests, close pool/queue connections, then exit; respect K8s terminationGracePeriodSeconds.

Deep explanation. SIGTERM → set draining flag → server.close() → wait for active count with timeout → close DB pool → flush metrics → exit 0. In-flight jobs: stop dequeuing new work, finish or checkpoint current batch.

Common misconception. Kill process immediately on deploy.

Senior follow-up. What if shutdown exceeds the grace period?

mediumnodeQ5

5. Streams vs loading entire file into memory?

Short answer. Streams process chunks — constant memory for large uploads/downloads.

Deep explanation. pipe() from request to S3/GCS avoids buffering 4GB in heap. Backpressure: pause source when sink is slow. Error handling must destroy both sides on failure.

Common misconception. Node handles big files automatically without streams.

Senior follow-up. How do you resume a multipart upload?

easynodeQ6

6. Why is JSON.parse on a 50MB body dangerous?

Short answer. Single allocation and sync parse blocks the event loop and can OOM the process.

Deep explanation. Set body size limits at reverse proxy and framework. For huge payloads use streaming parser or direct-to-object-store upload via pre-signed URL.

Common misconception. V8 handles any JSON size.

Senior follow-up. Where should size limits live — nginx or app?

hardnodeQ7

7. How do worker_threads fit a CPU-heavy image thumbnail job?

Short answer. Offload CPU work to worker pool so HTTP handlers stay responsive.

Deep explanation. Main thread posts job + buffer path; worker runs sharp/libvips; reply with result or error. Pool size bounded by CPU. Alternative: separate microservice/queue if jobs are minutes long.

Common misconception. Just use async/await for image processing.

Senior follow-up. When is a queue better than worker_threads?

mediumnodeQ8

8. Explain libuv thread pool vs event loop.

Short answer. Event loop runs JS and non-blocking callbacks; libuv pool runs some blocking fs/crypto/dns ops off the main thread.

Deep explanation. Pool default size 4 — heavy fs can queue. Not a substitute for proper async drivers. DNS lookup blocking behavior has bitten many deploys.

Common misconception. All I/O is non-blocking on the event loop.

Senior follow-up. What symptom shows thread pool starvation?

mediumdatabaseQ9

9. When does a composite index (a, b, c) not help query WHERE b = ?

Short answer. Left-prefix rule: index helps (a), (a,b), (a,b,c) — not bare b or c alone.

Deep explanation. Planner may seq scan if selectivity is low or stats stale. EXPLAIN ANALYZE is the truth. Covering index includes SELECT columns to avoid heap fetch.

Common misconception. Any column in the index helps any query.

Senior follow-up. How do partial indexes change the story?

harddatabaseQ10

10. Explain MVCC in Postgres in an interview.

Short answer. Readers don't block writers; each transaction sees a snapshot; dead tuples need vacuum.

Deep explanation. UPDATE creates new row version; old visible until xmin/xmax rules say otherwise. Long transactions block vacuum → bloat → slower scans. Repeatable read prevents phantom reads for indexed scans but not all anomalies without careful SQL.

Common misconception. MVCC means no locks ever.

Senior follow-up. What causes 'could not serialize access' errors?

mediumdatabaseQ11

Deep explanation. Page 10000 with OFFSET 200000 scans/discards rows. Cursor stable if tie-breaker column unique. Offset OK for admin pages with small max page.

Common misconception. OFFSET is always fine with an index.

Deep explanation. Not a pick-once logo — per operation. Payment ledger CP; notification badge AP. Real systems tune per feature with explicit lag contracts.

Common misconception. CAP means pick C or A forever.

Senior follow-up. Draw CAP for search index vs issue title.

mediumdistributedQ19

19. How does consistent hashing help sharding?

Short answer. Maps keys and nodes to a ring; add/remove node moves only adjacent key ranges.

Deep explanation. Virtual nodes spread load evenly. Hot key still hot — need application-level split or cache. Contrast with hash mod N where rescale reshuffles everything.

Common misconception. Consistent hashing eliminates hot keys.

Senior follow-up. When is hash mod N acceptable?

Deep explanation. Prefer DB unique constraint, single-partition Kafka consumer, or assign ownership in DB. Redis lock needs fencing token so stale holder cannot commit.

Common misconception. Redlock is always safe.

mediumdistributedQ21

Deep explanation. That partition's consumer lags while others idle. Mitigate: salt key + merge downstream, dedicated fan-out service, or accept disorder for that entity.

Common misconception. More partitions always fixes hot keys.

mediumdistributedQ24

24. What is quorum read/write (Dynamo-style)?

Short answer. R + W > N replicas → overlap guarantees you read latest write (with version vectors for conflicts).

Deep explanation. Tunable: W=1 R=N fast write slow read vs W=N R=1 opposite. Conflicts need application merge or LWW with known loss.

Common misconception. Quorum means strong SQL consistency.

Senior follow-up. When is sloppy quorum acceptable?

easycachingQ25

25. Cache-aside vs read-through?

Short answer. Cache-aside: app reads cache, on miss loads DB and sets cache. Read-through: cache library loads DB on miss.

Deep explanation. Write-aside invalidates or updates on write. Read-through simplifies app but cache must know loader. Stampede: many misses on hot key — use singleflight or probabilistic early expiry.

Common misconception. Cache always stays in sync automatically.

Senior follow-up. What happens when cache dies at 10× traffic?

mediumcachingQ26

26. Cache penetration, avalanche, stampede — define and fix.

Short answer. Penetration: queries for non-existent keys — bloom filter or cache null with short TTL. Avalanche: many keys expire together — jitter TTL. Stampede: thundering herd on one hot key — lock/singleflight.

Deep explanation. At 10× launch, synchronized TTL expiry can DDOS your DB. Monitor miss rate spike correlated with expiry.

Common misconception. Longer TTL fixes everything.

Senior follow-up. Design invalidation for issue detail + board snapshot.

mediumcachingQ27

Deep explanation. Write-back rare for authoritative data. Redis as write-back buffer needs AOF/fsync policy understood. Issue transitions should not use write-back to Redis as SoT.

Common misconception. Write-back is always faster and safe.

Senior follow-up. When is write-through worth the latency?

30. When is Redis the wrong primary store?

Short answer. When you need durable complex queries, large values, or authoritative financial/issue history without another SoT.

Deep explanation. Redis memory cost, persistence lag (AOF/RDB), no ad-hoc joins. OK for sessions, rate limits, locks, ephemeral presence — not issue graph.

Common misconception. Redis with AOF is a database replacement.

Senior follow-up. Pick Redis types for session vs leaderboard vs idempotency.

mediumcachingQ31

31. CDN caching authenticated content — pitfalls?

Short answer. Shared cache key without Vary/Auth leaks data across users; wrong Cache-Control on JSON is a SEV.

Deep explanation. Use private, no-store for API. Attachments via short-lived signed URL to CDN. Never cache Set-Cookie responses.

Common misconception. CDN always speeds up API.

Senior follow-up. Separate cache policy for hashed JS vs issue API.

mediummessagingQ32

32. At-least-once vs at-most-once vs effectively-once?

Short answer. At-least-once: retry until ack — duplicates possible. At-most-once: fire and forget — loss possible. Effectively-once: at-least-once + idempotent consumer.

Deep explanation. Queues ack after process → crash redelivers. Kafka offset commit timing matters. DLQ for poison messages after N tries.

Common misconception. Exactly-once is the default in SQS.

Senior follow-up. Design comment-notification with DLQ.

hardmessagingQ33

33. Transactional outbox pattern — why?

Short answer. DB commit and message publish are two systems — crash between them loses or duplicates events.

Deep explanation. Write business row + outbox row in same TX; relay process polls outbox → publishes → marks sent. Inbox on consumer for dedupe. Dual-write without outbox is a bug.

Common misconception. Publish to Kafka after commit is always safe.

Senior follow-up. What if relay publishes but fails to mark sent?

mediummessagingQ34

34. Kafka consumer group rebalancing pain?

Short answer. Partition reassignment stops consumption briefly; slow consumer extends rebalance.

Deep explanation. Static membership, cooperative sticky assignor, reduce max.poll.interval, scale consumers ≤ partitions. Rebalance storm during deploy if many consumers bounce.

Common misconception. More consumers always speeds up.

Senior follow-up. Consumer lag growing — first three checks?

easymessagingQ35

35. What is a dead letter queue for?

Short answer. Messages that fail processing after retries — isolate poison pill without blocking main queue.

Deep explanation. Alert on DLQ depth. Replay after fix with idempotency. Include original headers + error reason for debug.

Common misconception. DLQ deletes bad messages.

Senior follow-up. How do you safely replay DLQ at 2am?

mediummessagingQ36

36. Ordering guarantees in Kafka?

Short answer. Order preserved within one partition; not across partitions.

Deep explanation. Partition key = issue_id → all events for issue ordered. Global order impossible at scale without single partition. Trade hot key vs ordering scope.

Common misconception. Kafka orders all messages globally.

Senior follow-up. What if you need order across issue and comment?

hardmessagingQ37

37. Saga orchestration vs choreography?

Short answer. Orchestrator: central state machine sends commands. Choreography: services react to events without central coordinator.

Deep explanation. Orchestration easier to debug and enforce timeouts; choreography looser coupling but hard to trace. Both need compensating transactions for failure.

Common misconception. Events mean no central failure point automatically.

Senior follow-up. Compensate failed payment capture in issue upgrade saga.

mediummessagingQ38

38. Backpressure in message consumers?

Short answer. Slow consumer must not unbounded-buffer memory — pause fetch, scale workers, or drop to DLQ with policy.

Deep explanation. Prefetch count, max.in.flight, rate limit dequeue. Producer faster than consumer → lag → SLA miss. Monitor age of oldest unprocessed message.

Common misconception. Queue absorbs infinite backlog free.

Senior follow-up. When do you reject publish vs queue deeply?

mediumreliabilityQ39

39. Retry with exponential backoff and jitter — why jitter?

Short answer. Synchronized retries create retry storms that amplify outages.

Deep explanation. Full jitter: random(0, min(cap, base×2^attempt)). Cap max attempts and total deadline. Only retry idempotent or safe methods.

Common misconception. Retry immediately forever.

Senior follow-up. How do retries make a brownout a blackout?

easyreliabilityQ40

40. Circuit breaker states?

Short answer. Closed: normal. Open: fail fast after threshold. Half-open: probe if recovered.

Deep explanation. Prevents hammering sick dependency. Half-open allows one trial request. Metrics: open count, failure rate. Not a substitute for fixing root cause.

Common misconception. Circuit breaker retries internally forever.

Senior follow-up. CB open — what should API return to user?

hardreliabilityQ41

41. Define SLO, SLI, SLA — interview clarity.

Short answer. SLI: measured metric (p99 latency). SLO: internal target (99% requests <300ms). SLA: contractual consequence with customer.

Deep explanation. Error budget = 1 - SLO — spend on releases vs freeze. Alert on burn rate, not every blip. Product chooses SLO, not only ops.

Common misconception. SLA and SLO are the same.

Senior follow-up. Issue transition SLO — what SLI do you pick?

mediumreliabilityQ42

42. Bulkhead pattern?

Short answer. Isolate resource pools so one dependency's failure doesn't exhaust all threads.

Deep explanation. Separate connection pools per downstream; thread caps per call type. Issue API still serves reads if search pool exhausted.

Common misconception. One big pool is efficient.

Senior follow-up. Timeout per downstream vs global request timeout?

mediumreliabilityQ43

43. Health check: liveness vs readiness?

Short answer. Liveness: process up — fail → restart. Readiness: can serve traffic — fail → remove from LB.

Deep explanation. Readiness should check DB connectivity; liveness should not flap on slow DB. Startup probe for slow init.

Common misconception. Same endpoint for both.

Senior follow-up. What if DB down — kill pod or drain?

hardreliabilityQ44

44. Design idempotent POST /transitions in Node.

Short answer. Client sends Idempotency-Key; server stores key→response; unique constraint prevents double transition.

Deep explanation. Same key + same body → replay stored 200. Same key + different body → 409. TTL keys 24h except financial forever.

Common misconception. GET is the only idempotent method.

Senior follow-up. Webhook at-least-once with idempotency — walk through.

easyreliabilityQ45

45. Why timeouts on every outbound call?

Short answer. Without deadline, thread/socket waits forever; cascading queue buildup.

Deep explanation. Set timeout < client timeout. Propagate context deadline (OpenTelemetry/gRPC). Partial results better than hang if BFF design allows.

Common misconception. TCP will eventually timeout anyway.

Senior follow-up. 504 to client but DB committed — what now?

mediumsecurityQ46

46. JWT in localStorage vs httpOnly cookie?

Short answer. httpOnly Secure SameSite cookie for session — XSS cannot exfiltrate token easily.

Deep explanation. JWT in localStorage readable by any XSS script. BFF + cookie common for SPAs. Short-lived access + refresh rotation if JWT. mTLS for S2S.

Common misconception. JWT is stateless so storage doesn't matter.

Senior follow-up. How do you invalidate JWT before expiry?

hardsecurityQ47

47. Multi-tenant isolation — defense in depth?

Short answer. tenant_id on every row + RLS + middleware guard + audit; never trust client tenant header alone.

Deep explanation. Integration tests that attempt cross-tenant IDOR. Logs include tenant. Cache keys include tenant. S2S tokens scoped per tenant.

Common misconception. UUID obscurity is enough.

Senior follow-up. Bug: missing tenant filter in one endpoint — impact?

mediumsecurityQ48

48. Rate limiting: token bucket vs sliding window?

Short answer. Token bucket allows bursts with steady refill; sliding window smooths count over rolling interval.

Deep explanation. Distributed: Redis INCR + TTL or dedicated limiter service. Layer at gateway + sensitive endpoints. Return 429 + Retry-After.

Common misconception. Rate limit only at CDN.

Senior follow-up. Race on Redis INCR without atomic script?

easysecurityQ49

49. AuthN vs AuthZ — server responsibility?

Short answer. AuthN: who. AuthZ: what they can do — always enforced server-side on every mutation.

Deep explanation. UI hiding button is UX not security. Capability cache with short TTL OK; source of truth is permission service or DB join.

Common misconception. Frontend RBAC is sufficient.

Senior follow-up. How audit issue delete and permission change?

mediumsecurityQ50

50. SSRF when fetching user-supplied URL?

Short answer. Server-side fetch of webhook URL can hit internal metadata (169.254.169.254).

Deep explanation. Block private IP ranges, require allowlist, no redirects to internal, separate network segment for fetcher.

Common misconception. Only HTTPS URLs are safe.

Senior follow-up. Preview unfurl for issue links — threat model?

hardsecurityQ51

51. Secrets management in Node deploy?

Short answer. Secrets in env from vault/K8s secrets at runtime — not in git, not baked in image layers.

Deep explanation. Rotate without redeploy if possible. Least privilege IAM for S3/DB. Audit secret access.

Common misconception. .env in repo is fine if private.

Senior follow-up. How rotate DB password with connection pool?

mediumsecurityQ52

52. TLS termination — where and what trust?

Short answer. Terminate at LB or service mesh; re-encrypt east-west with mTLS optional.

Deep explanation. Cert rotation automation. HSTS on public edge. Internal plaintext only inside trusted mesh with network policy — document threat model.

Common misconception. TLS once at edge means internal is trusted forever.

Senior follow-up. What headers must not pass through from client to origin?

mediumnodeQ53

53. How do you structure a Fastify/Express service for testability?

Short answer. Separate route registration, handlers, and data layer; inject config and db pool; health at /healthz.

Deep explanation. App factory pattern: buildApp(deps) for tests with mocks. Graceful shutdown hook. Correlation id middleware first.

Common misconception. Controllers must be singletons.

Senior follow-up. Where put validation — schema at boundary.

harddatabaseQ54

54. Read replica lag vs read-your-writes?

Short answer. User writes primary, reads replica — may not see own write until replication catches up.

Deep explanation. Route user's session reads to primary after write (sticky session flag), or sync replication for critical reads, or client passes read-after-write token.

Common misconception. Replicas are always consistent.

Senior follow-up. Board load after creating issue — which read path?

mediumdistributedQ55

55. What is a fencing token?

Short answer. Monotonic token from lock service included with write — storage rejects stale holder's write after lease expiry.

Deep explanation. Without fencing, delayed old worker can overwrite new data after lock lost. Zookeeper/etcd sequential nodes common source.

Common misconception. TTL lock alone prevents double write.

Senior follow-up. When lease expires mid-transaction?

mediummessagingQ56

56. Event schema evolution — compatibility rules?

Short answer. Additive changes forward compatible; breaking changes need new topic/version or dual-write period.

Deep explanation. Consumers ignore unknown fields. Never rename in place. Schema registry enforces. Document deprecation timeline.

Common misconception. JSON needs no schema.

Senior follow-up. Remove field from IssueCreated event — safe how?

easycachingQ57

57. What is TTL and when is it not a strategy?

Short answer. Time-to-live expires cache entry — good for bounded staleness.

Deep explanation. If writes frequent and TTL short → low hit rate. If TTL long → stale reads. Event invalidation + TTL backup is typical.

Common misconception. Infinite TTL with nightly flush.

Senior follow-up. Issue assignee changes every minute — cache TTL?

12 decision records

Architecture Decision Records

Practice explaining why, not buzzwords. Each ADR follows Context → Decision → Alternatives → Trade-offs → Consequences. Kafka, microservices, and NoSQL are not automatically correct — constraints decide.

Senior move: name the constraint first ('we need replay for analytics' → Kafka; 'user waits on screen' → sync OLTP). Then reject one alternative with a concrete failure mode.

ADR: Postgres vs NoSQL

Context. Multi-tenant issue tracker: rich queries (project + status + assignee + text), ACID transitions, tenant isolation, 50M issues growing 20%/year. Some teams want flexible custom fields.

Decision. Postgres as system of record for issues, comments, permissions, and transitions. Document/KV store only where access pattern is truly key-value (e.g. per-issue activity blob, session, idempotency keys) — not as the primary issue graph.

Alternatives. Mongo for everything; Dynamo for issues; Postgres only; polyglot with event sync.

Trade-offs. Postgres wins when you need joins, constraints, and ad-hoc admin queries. NoSQL wins when access pattern is fixed, write volume per key is huge, and you can denormalize aggressively. Custom fields push toward JSONB columns or EAV — not automatic NoSQL.

Consequences. Search still needs Elasticsearch/OpenSearch — Postgres is not your inverted index. Migrations and connection pooling become the ops focus. Revisit NoSQL for a hot shard only after measuring a specific key skew.

ADR: Redis vs DB cache

Context. Issue detail p99 is 180ms at 2k RPS; 70% reads are repeat views of the same 5k popular issues. Postgres CPU is climbing. Team proposes 'Redis in front of everything.'

Decision. Cache-aside Redis for issue detail + board snapshot with explicit TTL (60–120s) and event-driven invalidation on write. Do not cache permission matrices without tenant-scoped keys and short TTL. Postgres remains source of truth.

Alternatives. Postgres query cache; CDN for JSON; materialized views only; Redis as primary store.

Trade-offs. Redis is fast but adds invalidation complexity and another failure domain. DB read replicas help read scaling without stampede risk if queries are bounded. Write-through to Redis on every comment is usually wrong — write volume + invalidation fan-out.

Consequences. Document cache key schema and invalidation events in the ADR. Alert on Redis memory and hit rate. Cold start: stagger TTL + singleflight on hot keys.

ADR: REST vs events

Context. Issue transition must update DB, audit log, search index, and notify watchers. Today: synchronous REST chain from API → 4 downstream HTTP calls; p99 spikes when search is slow.

Decision. REST for command/query from clients. After successful DB commit, publish domain events (outbox → Kafka/SQS) for search, notifications, analytics. Clients get 202/200 with issue state; side effects are async with idempotent consumers.

Alternatives. Keep sync REST fan-out; GraphQL subscriptions for everything; event sourcing for issues.

Trade-offs. Events decouple latency and failure domains but add eventual consistency UX. REST stays simpler for CRUD and debugging. Event-first without outbox risks lost messages on crash between commit and publish.

Consequences. Define user-visible consistency: 'search lags ≤30s' is acceptable; 'transition must be atomic in DB' is not negotiable. Consumers must be idempotent; DLQ + replay runbook required.

ADR: Kafka vs message queue

Context. Notification pipeline: 500 events/sec average, 5k/sec peak on release day. Need retry, DLQ, and multiple independent consumers (email, in-app, push, analytics). Ordering per issue preferred but not global.

Decision. Kafka (or Kafka-like log) when you need replay, multiple consumer groups, and retention for reprocessing. SQS/Rabbit when workload is task queue with competing consumers and no replay requirement. Here: Kafka with partition key = issue_id for per-issue ordering; email worker is separate consumer group.

Alternatives. Kafka because scalable; single SQS queue; Rabbit with one queue per channel.

Trade-offs. Kafka is not free: ops, partition planning, consumer lag monitoring. A queue is simpler for fire-and-forget tasks. Kafka wins when analytics and notifications both need the same stream without duplicating publish.

Consequences. Monitor consumer lag per group. Hot partition if one celebrity issue gets 10k watchers — mitigation: sub-partition by batch id or fan-out worker before Kafka.

ADR: Monolith vs microservices

Context. 40 engineers, one product (Jira-like), shared release train, heavy cross-feature transactions (issue + comment + permission). Search team wants independent deploy cadence.

Decision. Modular monolith for issue/comment/permission core with strict module boundaries and CI import lint. Extract search and notification delivery as services only where deploy independence and different scaling profile justify network + transaction cost.

Alternatives. Full microservices day one; never split; serverless everything.

Trade-offs. Microservices do not fix org problems by themselves — they add distributed failure modes. Monolith avoids 2PC on issue transition. Split when team is blocked on release or resource profile diverges (search CPU vs OLTP).

Consequences. Core monolith keeps ACID transitions simple. Search service accepts eventual consistency contract. Document S2S auth and correlation IDs before second service ships.

ADR: Sync vs async

Context. User clicks 'Assign to me' — must see updated assignee immediately. Same action triggers email to 200 watchers and search index update.

Decision. Sync path: validate permission, update Postgres, return new issue JSON (read-your-writes). Async path: enqueue notification + search index jobs via outbox. Never block the HTTP response on email SMTP or Elasticsearch.

Alternatives. Async everything including the DB write; sync fan-out to all downstreams; websocket-only updates.

Trade-offs. Sync minimizes user confusion but limits tail latency budget. Async maximizes throughput but needs status UX for long operations. Senior rule: sync what the user waits for; async what they tolerate lag on.

Consequences. API returns consistent issue entity; badge/email may lag. Idempotent workers; user sees 'Notifications sending' only if SLA requires it.

ADR: SQL vs NoSQL (access-pattern lens)

Context. Analytics dashboard: 'issues closed per team per week' plus operational queries by issue id. Write pattern: append-only events; read pattern: aggregate by team/time and point lookup by id.

Decision. SQL warehouse (BigQuery/Snowflake/Postgres replica) for aggregates. OLTP stays Postgres. If point lookups at billions of rows/day with fixed key-only access, add KV (Dynamo/Redis) — not replace SQL for reporting.

Alternatives. NoSQL for analytics because scale; one Mongo cluster for all; CSV exports.

Trade-offs. The question is access pattern, not religion. SQL handles ad-hoc aggregates with known cost if indexed/partitioned. NoSQL handles predictable key access at extreme QPS. Mixing without boundaries creates dual-write hell.

Consequences. ETL from OLTP to warehouse with lag SLA. Operational APIs never hit the warehouse.

ADR: WebSocket vs polling

Context. Live board: 30 users, remote card moves, presence avatars. Infra team prefers no persistent connections at edge. Mobile clients on flaky networks.

Decision. WebSocket (or SSE) for board room when product commits to sub-second remote updates; fallback to poll every 15–30s on disconnect. REST remains source for full board snapshot on reconnect. Do not WS the entire issue graph.

Alternatives. WS always; poll every 1s; long poll forever; Firestore.

Trade-offs. WS saves bandwidth at steady state but costs connection memory and complicates load balancers. Polling is correct when freshness of 30s is fine. Senior answer states reconnect, auth, and backpressure — not protocol zeal.

Consequences. Auth on connect (cookie/session upgrade). Heartbeat + idle timeout. On reconnect: GET snapshot + apply missed events by version vector or since cursor.

ADR: Strong vs eventual consistency

Context. Payment for premium tier (strong), like count on comment (eventual), issue title after edit (read-your-writes), global search index (eventual).

Decision. Classify per entity/action. Money: serializable/strong in ledger DB. Issue transition: transactional in OLTP + async index. Likes: counter with periodic reconcile or CRDT if high write contention. Document each UX contract.

Alternatives. Eventual everywhere for simplicity; strong everywhere via 2PC; ignore consistency labels.

Trade-offs. Strong consistency costs latency and availability under partition. Eventual is fine when users expect lag or when approximate counts are OK. Wrong: eventual for inventory deduction without reservation pattern.

Consequences. Product sign-off on lag numbers. Tests assert RYW after mutation. Search shows 'index updating' if lag > SLA.

ADR: Single DB vs sharding

Context. Postgres at 2TB, 8k write TPS peak on transitions, one tenant (enterprise) generates 40% of writes. Vertical scale exhausted.

Decision. Shard by tenant_id (or tenant group) when cross-tenant queries are rare or can be federated. Keep global metadata (users, billing) on a catalog DB. Avoid shard until replica + partitioning + archive prove insufficient — sharding hurts ad-hoc queries and migrations.

Alternatives. Shard by issue_id immediately; one DB forever; NewSQL automatically.

Trade-offs. Single DB simplifies transactions and joins. Sharding buys write headroom at cost of cross-shard queries, rebalancing, and operational pain. Hot tenant may need isolation to dedicated shard, not whole-system shard.

Consequences. Router layer maps tenant → shard. Background jobs for cross-shard admin. Rebalance playbook before production shard.

ADR: CDN vs origin

Context. Global users fetch attachments (PDFs, images) and static API docs. Authenticated issue JSON must not leak via shared cache.

Decision. CDN for public/immutable assets (hashed JS, public docs, signed attachment URLs with short TTL). Origin handles authenticated API with Cache-Control: private/no-store. Pre-signed S3 URLs so bytes bypass app server.

Alternatives. CDN cache all API responses; no CDN; origin serves everything.

Trade-offs. CDN reduces latency and origin load for cacheable bytes. Wrong cache headers on private JSON is a SEV. Signed URLs shift auth to token scope and expiry — not 'security through obscurity.'

Consequences. Separate cache policies per path. Pen-test shared cache keys. Monitor CDN 403/404 on expired signatures.

ADR: Server cache vs client cache

Context. Issue list refetched on every navigation; mobile app also caches locally. Stale assignee after colleague's change causes wrong triage.

Decision. Server: Redis/cache-aside for hot lists with invalidation on write. Client: short staleTime + background revalidate; optimistic only for user's own actions. ETag/If-None-Match on GET issue for bandwidth. Never client-only cache for shared collaborative fields without version checks.

Alternatives. Client cache only to reduce server load; server cache only; no cache.

Trade-offs. Client cache improves perceived speed offline-ish; server cache protects DB. Both without coordination → stale UI. Version column or updatedAt in response lets client merge intelligently.

Consequences. Document staleTime per resource. 409 on stale write. Server invalidates list cache keys on issue update pattern.

            Backend & System Design Glossary

            Searchable definitions at senior density — throughput, consistency, messaging, reliability, and ops. Filter to drill weak areas.

            RPS

            Simple. Requests per second.

            Technical. Throughput measure for an API or service.

            Interview. Estimate peak from DAU × actions ÷ seconds.

            QPS

            Simple. Queries per second.

            Technical. Often DB or search read load.

            Interview. Distinguish read QPS from write TPS in designs.

            Latency

            Simple. Time one operation takes.

            Technical. p50/p95/p99 — tail matters at scale.

            Interview. Name p99 budget before picking sync fan-out.

            Throughput

            Simple. Work completed per unit time.

            Technical. RPS, records/sec, bytes/sec.

            Interview. Throughput up, latency may rise — Little's Law.

            Availability

            Simple. Fraction of time system works.

            Technical. Often 99.9% = 8.7h downtime/year.

            Interview. Define what 'up' means — health check depth.

            Durability

            Simple. Data survives failures.

            Technical. Disk replication, fsync, backups.

            Interview. Redis AOF ≠ Postgres durability story.

            Replication

            Simple. Copies of data on multiple nodes.

            Technical. Leader/follower, async/sync.

            Interview. Replica lag vs read-your-writes.

            Partitioning

            Simple. Splitting data by key range or hash.

            Technical. Horizontal scale within one logical DB.

            Interview. Not the same word as network partition.

            Sharding

            Simple. Partitioning across separate DB instances.

            Technical. Each shard owns key subset.

            Interview. Cross-shard queries become expensive.

            CAP

            Simple. During partition: pick consistency or availability.

            Technical. Not a one-time architecture choice.

            Interview. Apply per feature — ledger vs badge.

            Consistency

            Simple. All readers see same data at same time.

            Technical. Strong vs eventual spectrum.

            Interview. Define per action in interview.

            Eventual consistency

            Simple. Replicas converge if no new writes.

            Technical. Lag bounded in SLA not in math.

            Interview. OK for search index, not for balance.

            Quorum

            Simple. R+W>N replica overlap.

            Technical. Dynamo-style tunable consistency.

            Interview. Conflicts still need resolution.

            Leader

            Simple. Primary that accepts writes.

            Technical. Followers replicate.

            Interview. Failover promotion story.

            Follower

            Simple. Replica that applies leader log.

            Technical. Can serve stale reads.

            Interview. Lag monitoring essential.

            Cache-aside

            Simple. App loads cache on miss.

            Technical. App invalidates on write.

            Interview. Most common pattern.

            Write-through

            Simple. Write updates cache and DB together.

            Technical. Consistent cache, slower writes.

            Interview. When read-after-write must hit cache.

            Write-back

            Simple. Write cache first, flush later.

            Technical. Fast, risk on crash.
